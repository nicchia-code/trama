# Regole dei Task

## task
- A Task that is not technical must reference at least one Model element, and may add Requirements. A Technical Task must reference no Model element, only Requirements if any. Every reference must resolve to an existing Model element or Requirement section when the Task is created. Un Task scritto con una Proposal deve risolversi nel Model con la Proposal applicata, alla consegna e all'approvazione (`rules#proposal`).
- Any move between the three columns is allowed, in either direction, from the command line (and always for the agent). The Board offers no move at all: it sends none and the editor accepts none, whether by drag, by buttons or by message.
- A Task may be linked to a Proposal when it is created; the Proposal must exist, in any status. Tasks that carry no link are never grouped. I Task nati da una Proposal (scritti con essa o creati alla sua approvazione) le appartengono; un Technical Task nato con la Proposal fa parte del suo design. I Task creati all'approvazione hanno tutti lo stesso istante di creazione e fra loro si ordinano per identità.
- Design grouping, solo per `trama board` della riga di comando: the Tasks linked to the same Proposal form one design, listed in the order they were created. A design with fewer than two Tasks is not shown as a group. The column of a design is derived: To do when every Task is in To do, Done when every Task is in Done, In progress in every other case (including a mix of To do and Done). La Board del pannello non raggruppa i Task: ognuno ha la sua scheda con il tag della sua Proposal (vedi `ui#task`).
- A Task is runnable when it is in To do and not blocked. The next runnable Task is the oldest runnable Task in creation order, worked out again each time it is asked: a Task that waits for the Task that fixes its Drift becomes runnable once that Task is Done, so the fixing Task runs first and the waiting one right after it. No other order is imposed between Tasks.
- A run (Run all) asks for the next runnable Task, implements it, and asks again, until there is none; it considers every Task. Non c'è più una corsa sui soli Task di un design. A run skips the Tasks that are blocked and goes on past a Drift: the Drift the agent files during the run leaves its Task In progress, blocks only the Tasks it concerns, and does not end the run. A run ends when no Task is runnable. Its report says what the agent implemented, the Drifts it filed, and the Tasks in To do left unrun, each with the Drift or the fix Task it waits for.
- Il gruppo di una corsa parallela: partendo dal Task eseguibile più vecchio e seguendo l'ordine dei Task eseguibili, si aggiunge ogni Task che non riguarda la stessa cosa di nessuno di quelli già scelti, finché il gruppo ha N Task o non ne resta nessuno, dove N è il valore di `--max` di `trama task next --batch` (vedi `tech#task`), cioè `trama.maxParallelAgents`. «Riguardare la stessa cosa» fra due Task segue la stessa regola che vale fra un Task e un Drift (vedi sotto). Il primo Task del gruppo è sempre il prossimo Task eseguibile, quindi l'ordine fra un Task di correzione e chi lo aspetta resta quello di prima.
- Il pre-flight: ogni Run (un Task, `Run all`, il Run automatico) come primo passo, prima del primo gruppo, scansiona una volta i riferimenti esatti dei Task che stanno per partire, cioè quelli eseguibili in To do del suo ambito come `trama task next` li sceglie, anche di Proposal diverse. L'ambito è deduplicato; una sezione di Requisiti vale il suo elemento; niente Transition aggiunte, niente General né Aree (`tech#task`). Archivia solo Drift senza origine, mai Task: una differenza che è il lavoro di un Task che parte non è un Drift. Un sotto-agente per Machine, al massimo N insieme; con una sola Machine la confronta l'agente del Run senza sotto-agenti. Un Drift trovato blocca i Task che riguardano lo stesso elemento e il Run continua sugli altri.
- Un pre-flight fallito o interrotto chiude il suo controllo con esito fallito, scrive la riga di avviso `Pre-flight scan failed: the Run continues without it.`, ripetuta nel resoconto, e il Run parte lo stesso. Il pre-flight non cambia il ricordo dell'ultimo scan globale.
- Una corsa parallela realizza insieme i Task di un gruppo, uno per sotto-agente, aspetta che finiscano tutti, anche quelli fermati da un Drift, e solo allora chiede il gruppo seguente. Un gruppo di un solo Task si realizza senza sotto-agente.
- La scansione mirata di fine corsa parte solo se la corsa ha portato almeno un Task in Done, se nessun Task del suo ambito è bloccato alla fine (in `Run all` tutti i Task, nel Run automatico le sue correzioni e origini, per un Task singolo quel Task) e se la verifica finale di test, lint e build passa. Il suo ambito è l'unione dei riferimenti al Modello dei Task portati in Done dalla corsa, con le Transition che entrano negli elementi nominati, calcolato come lo scope di una Proposal (`tech#proposal`): un riferimento `requirements/<area>#<elemento>` vale come l'elemento; una General nominata (`requirements/<area>#General`) entra nell'ambito e si confronta solo nel codice che la corsa ha toccato; un'Area intera `requirements/<area>` non aggiunge nulla. Una corsa di soli Task su General scansiona. Con l'ambito vuoto non parte nessuna scansione e il controllo si chiude dopo la verifica. Lega i Task che archivia al design del Task singolo della corsa, se ne ha uno; dopo `Run all` o un Task senza design non li lega. Non realizza quei Task e non scansiona mai tutto il Sistema. Il resoconto della corsa elenca i Task e i Drift archiviati da quella scansione.
- Asked to implement one named Task, the agent still stops at once if that Task is blocked (see below): the order and the skipping apply only to runs over several Tasks.
- The agent takes a Task when it moves it to In progress with the command line run in the terminal Trama started for the agent (the one marked with `TRAMA_AGENT`). A move by the developer never takes a Task, and neither does a move made by an agent outside that terminal, which cannot be told from the developer's. Moving a taken Task to To do or Done, by the agent, clears the mark; moving it to In progress again keeps it.
- A Task taken by the agent cannot be moved by the developer: not with the command line run without `TRAMA_AGENT`. The Board has no way to move a Task. The refusal says the agent is working on it and points to `task take-back`. Moves by the agent are always allowed.
- Riprendere un Task è una decisione del developer: toglie il segno di Task preso e lo lascia In progress. Il comando `task take-back <id>` non è rifiutato con `TRAMA_AGENT` o `CURSOR_AGENT` impostata; l'agente è istruito a lanciarlo solo su richiesta esplicita del developer, come in `General`. La Board non ha un pulsante per farlo.
- When the agent's hook says it is idle, when the command running in the agent terminal ends or when that terminal is closed (by anyone, Trama's `trama.autoExit` included), every Task that carries that terminal's mark is released and goes back to To do, so it can be run again. A Task is not released by a command end the terminal cannot report; then the hook, the close of the terminal or `task take-back` frees it.
- Uno spostamento dell'agente in In progress che non dice da quale terminale o chat arriva (`TRAMA_AGENT` impostata senza un `TRAMA_TERMINAL` riconosciuto) prende il Task lo stesso, senza un terminale che lo tenga. Un Task preso così è rilasciato da qualsiasi fine che rilascia i Task presi: l'hook a riposo, la fine del comando o la chiusura di qualsiasi terminale dell'agente, o la fine del turno, l'interruzione o la chiusura di una conversazione della chat del progetto.
- `Run all` is unavailable while any Task is taken by the agent, and when no Task in To do is runnable. `Run all` e il Run di un Task non sono disponibili nemmeno mentre l'agente di risoluzione lavora (vedi `drift-resolution`).
- Con `trama.submitWhileRunning` spento (predefinito, anche per un valore assente o non riconosciuto), `Run all` e il Run di un Task non sono disponibili mentre un Run lanciato da Trama non è finito: lo stesso Run che rende indisponibili `Resolve all` e `Resolve` (vedi `drift-resolution`), scan di fine corsa compreso, fra quelli che la finestra conosce (i propri e, con il coordinatore dell'autopilota attivo, quelli delle altre finestre del progetto). Un Run automatico dell'autopilota conta come gli altri. Una richiesta di Run che arriva comunque all'editor in quel momento è rifiutata come per gli altri motivi. Scan, design, import e Resolve Drifts non dipendono dall'impostazione. Con l'impostazione accesa valgono soltanto le regole precedenti.
- A Task is blocked when an open Drift blocks it or when it is the origin of a Drift fixed in the code and the Task created for that fix is not Done. A Done Task is never blocked. Blocking is derived from the Drifts, the Tasks and their references each time it is asked; it is never stored on the Task.
- An open Drift blocks its origin Task, if it has one, and every Task that is not Done and concerns the same thing as the Drift. A Drift filed by a Scan has no origin. A Task concerns the same thing as a Drift when one of their references is the same as one of the other's or inside it: an element contains its States and Transitions, and a Machine or Feature contains its Machines and States. A Requirement section of an element also counts as that element, and the element and everything inside it as that section. The General section of an Area is equal only to itself, so it concerns only the Tasks that name it. This holds for Technical Tasks, which have only Requirement references.
- Moving a blocked Task to In progress is refused to the agent, whatever its column, and so is keeping a blocked In progress Task with another move to In progress. The refusal names the Drift that blocks it (ID and title), or the fix Task it waits for. Moves of the developer, and moves of the agent to To do or Done, are not affected. A blocked Task already In progress is not moved.
- Chiudere un Task senza modifiche, da To do o In progress, lo porta in Done con una nota non vuota, che resta nel Task. È accettato solo per un Task di correzione (con un Drift) il cui Drift è `fix-code`, oppure `dismissed` con questo Task come suo `task`; è rifiutato, dicendo perché, per un Task già Done, per un Task senza Drift, per un Drift in un altro stato e per una nota assente o vuota. Per il resto vale come lo spostamento in Done: stesse regole per l'agente e per il developer (un Task preso resta rifiutato al developer), toglie il segno di Task preso, scrive l'istante di arrivo in Done e sblocca l'origine. Nello stesso passo il Drift passa a `dismissed` (`rules#drift`).
- Un Task di correzione comincia con la verifica della premessa: chi lo realizza rilegge il codice citato dal Drift e, se fa già ciò che dicono il Model o il Requisito, non cambia nulla e lo chiude senza modifiche, con una nota su ciò che ha verificato, invece di inventare una modifica. Il resoconto della corsa elenca a parte i Task chiusi senza modifiche, con la nota. È un'indicazione per la skill `trama-implement`.
- Un Task chiuso senza modifiche non conta come portato in Done dalla corsa: non fa partire la scansione mirata di fine corsa e non entra nel suo ambito. Non conta nemmeno nel numero dei Task finiti dall'ultimo scan globale.
