# Trama: implement

You implement one **Task** so that the code behaves as the **Model** says and is built as the **Requirements** say. The Model wins. If following it or a Requirement is impossible, or you discover it is wrong or incomplete in an important way, you **stop working on that Task** and file a **Drift**: you never silently deviate and you never edit the Model or the Requirements. The Drift blocks the Task and the other Tasks that concern the same thing. Asked for one named Task, you stop there and take no other. Asked for several Tasks (every Task in "todo"), you hand them out as sub-agent places free up and go on: the Drift leaves its Task in `doing`, and `trama task list` with `runnable` skips the Tasks it blocks.

## Hand-over

A new Proposal starts as a **Draft**, not approvable. Finish every file, then run `trama proposal move <id> open` without `proposal show` before it: read the changes in the hand-over's output. If they do not match what you meant, reopen the Proposal with `trama proposal edit <id>`, fix the files, and hand it over again. If the hand-over is refused, fix the reported problems and hand it over again. Only after it succeeds tell the developer to review it. A Proposal meant for a Drift is attached to that Drift when the Drift is filed, before it is handed over, so it never shows up alone. Before every later file change, call `trama proposal edit <id>` again: it returns an open Proposal to Draft, so hand it over again when finished.

## Announcing cards

When you know you must file a Drift (see "When you must file a Drift"), announce it before you write it up: `trama announcement new --input -` with `{"kind":"drift","title":"<title>"}` prints an announcement ID. Pass it when you file the Drift: `trama drift new --input -` with `announcement` set to it; if the Drift carries a Proposal, announce only the Drift and pass the same ID to `trama proposal new --input -` (field `announcement`) too. The end-of-run scan (step 7) announces its cards as `trama-scan` says. A sub-agent announces the cards it files exactly as you do. The Board shows a ghost of each card meanwhile. Never wait for a ghost to show and never skip or delay a card because of it; an unknown ID is only noted in the output.

## Announcing the check

Once the run has moved at least one Task to Done, announce its **check** right after the last Task, before step 6: `trama announcement new --input -` with `{"kind":"check","title":"<title>","phase":"verifying"}` prints its ID. The title says the work, in English: `Final check after Task <short number>` for a Task asked by name, `Final check after all Tasks` for every Task in "todo". If step 7 finds a non-empty scope to scan, run `trama announcement move <id> scanning` when that scan starts and use this check; that end-of-Run scan covers only the completed Tasks' scope, never the whole System, as step 7 says. Otherwise keep the check open for step 8. Close the check after step 8 and before the report in every case: `trama announcement move <id> delivered` when it succeeded, and `trama announcement move <id> failed` when the check of step 6 fails and you cannot fix it, when the scan of step 7 fails or stops, or when the Run stops before its check is over. A sub-agent never announces a check. Never wait for the ghost to show; an unknown ID is only noted in the output.

When the run has sub-agents and moved at least one Task to Done without `unchanged`, start one sub-agent right after announcing the check, before step 6. Give it the permanent IDs of those Tasks and the language the instruction asks for. It reads `trama history list --json`, `trama history show <id> --json` for the entries that look related, and `trama task show <id> --json` for each Task; it groups the Tasks by macro-feature as step 8 says, and returns the entries, each with the JSON ready for `trama history new --input -` or `trama history edit <id> --input -`. It runs no writing command, announces nothing and touches no code. Step 8 uses what it returns; if it did not come back or gave no valid entries, the agent writes them itself.

With the Advisor Scanner on, step 7 never runs: announce no Scanning phase, and keep the check in Verifying until step 8.

## Hard rules

- NEVER edit `.trama/model/`, `.trama/requirements/` or the generated `trama-req-*` skills.
- Agents may approve or reject a Proposal, discard a Draft or resolve a Drift only when the developer explicitly asks for that decision in the conversation. Without that request, do not decide and do not ask the developer about it: stop and tell them the decision is theirs, on the Board. A request to design, implement Tasks or prepare a Drift resolution does not by itself authorize deciding it.
- Every question to the developer goes through `trama question new`, as the "Asking" section of `trama-design` says, waiting rules included (`timeout: 0`, no timers or polling): never with your own question tool, and never as a round written in the conversation.
- NEVER implement behaviour that contradicts the Model, or code that contradicts a Requirement, to get something working.
- Do not touch code unrelated to the Task.

## Naming cards

Every live Proposal, Task and Drift has a temporary **short number** (`P3`, `T3`, `D3`) besides its **permanent identity** of eight characters.

- Name cards to the developer by short number and title, for example "Task T3 – title" or "Drift D2 – title", also in the final report. A closed card (for example a Task in Done) has no number: use its permanent identity.
- In every command you run and every file you write (`trama task move`, `task`, `proposal`, the body of a Proposal) use **only the permanent identity**, taken from `--json` (field `id`; the number is the field `number`) or from the file name. **Never write a short number in a file**: it changes from one working copy to another.
- Give every card you create, and its announcement, a **short title**: at most five words, about 40 characters, a name for the card rather than a sentence describing the work (for example "Testo fantasma" instead of "Descrivere Start from Scratch e guidare le richieste scritte con un testo fantasma"). Put the detail in the body, even when the title loses information. No command checks the length of a title. Titles that Trama or a skill composes from another title stay as they are: `Fix code to match the …`, `Import: <Feature>`, the titles of checks.

## Notes on the ghost

While your work waits on the Board it has a ghost, and you tell the developer what you are doing with notes: `trama announcement edit --input -` with `{"note":"<one line>"}`, passed as `trama announcement edit --input - <<'JSON'`, the object and `JSON`. Without an ID the note goes to every ghost still waiting of your terminal or conversation (never to a comparison). Declare a note at the start of each stage of the run: the pre-flight, each group of Tasks, the final verification, the targeted scan and the History. A sub-agent that implements a Task writes none; one that compares a Machine writes on its own comparison, as `trama-compare` says. Write 3 to 6 notes for the whole job, never one per command. A note is one sentence of at most 120 characters (a longer one is cut) saying what you do and why, for the developer: no first person, no Trama command names and no short numbers of cards, in the language of the instruction when it asks for one (for example «Compares agent-terminal with the code before the Tasks run»). A note changes nothing else about the ghost and is never needed to deliver a card.

## Language

When the instruction asks you to write in a language, everything you generate for Trama that the developer reads goes in that language: the bodies, descriptions and introductions of Proposals, Model files, Requirements, Tasks and Drifts; the titles of Proposals, Tasks, Drifts, Areas and Requirement fragments, and of announcements; the names of the System, Features, Machines, Actors and States; new identifiers (IDs of Features, Machines and Actors, Event names), transliterated into the allowed ASCII letters (`città` → `citta`, an Event `PAGAMENTO_RIUSCITO`); the text of questions and their options, and your replies in the conversation. Without a language in the instruction, nothing here changes.

- **Always in English**, whatever the language: technical terms are never translated: commands and tools (`git pull`, `npm install`), names of products, services, libraries and languages, and Trama's own terms (Proposal, Task, Drift, Board, Run, Scan). Also always English: code and its comments, commit messages, the project's own documentation; the headers Trama reads in files ("States", "Events", "General", "What happens", "What should happen", "Where in the code", "Fix options", "Already present"), the `(initial)` and `(final)` markers, the keys of Specs and the front matter fields. Trama's interface (panel, editor, command line) stays in English.
- **A language changes nothing already written.** When you edit a file written in another language, keep its existing text and write only the new or rewritten text in the chosen language; never translate the whole file.
- **No first person in Trama's texts.** In what you write for Trama (questions, contexts and options of rounds, titles and bodies of Proposals, Tasks and Drifts, History entries), Trama is always "Trama" and you are "the agent": no "I", "me", "my", "we", "our", and in Italian no "io", "noi" or first-person verbs. Your replies in the conversation are not Trama's texts and do not change. Text already written is not rewritten.
- **Self-contained Tasks.** The body of a Task is understood without the conversation that produced it: it says what must be true when done, with the conditions and consequences as the Model says them, and every decision of the interview that concerns it, because whoever implements it does not see that conversation.

## Advisor Scanner

This section applies only when the instruction says "The Advisor Scanner is on". Without that sentence, skip it and follow the steps as written.

With it, the Run does not scan: the advisors check the code against the Model during the run instead. They are omp's advisors.

- **No pre-flight.** Announce no check for it and run no `trama task list` with `runnable` and `scope`. Start at step 1.
- **No targeted scan.** Step 7 never runs, and no Scanning phase is announced: after step 6 the check goes straight to step 8, History, and closes as the "Announcing the check" section says.
- **Advisor notes.** When the advisor finds that the code of a Task departs from the Model, the Requirements or the Task, it sends a note. Correct that code before moving the Task to Done; do not file a Drift for it.
- **Drifts from the advisor.** The advisor files a Drift only for code outside the Tasks of this run. Such a Drift has no origin (no `task`) and carries no `notBlocking`: it blocks every Task not Done that concerns the same thing. A Task already In progress that it blocks is not stopped: finish it, and the Run goes on with the others. The advisor gives no blocker judgement, and you give none for its Drifts.
- **Sub-agents.** A sub-agent that implements a Task has the advisor too; it does steps 2 to 5 for its Task as above.

## Steps

**Pre-flight, before the first Task.** Every Run starts with a pre-flight, before it asks for the first Tasks and before any code is read. Announce its check with `trama announcement new --input -` with `{"kind":"check","title":"<title>","phase":"scanning"}` and keep its ID. The title says the work, in English: `Pre-flight before Task <short number>` for a Task asked by name, and `Pre-flight before all Tasks` for every Task in "todo".

With the Advisor Scanner on (see "Advisor Scanner"), there is no pre-flight: announce no check for it, run no `trama task list` with `runnable` and `scope`, and go straight to step 1. The pre-flight paragraphs below do not apply to such a Run, except the Proposal filters, which still apply to every `trama task list` with `runnable`.

Then run `trama task list --input -` with `runnable: true`, `scope: true` and the filters of the Run: `proposals` or `notProposals` (lists of Proposal IDs), as the instruction gives them; or `tasks` for a named Task; or no filter for every Task in "todo". It prints the exact references of the runnable Tasks (the ones `trama task list` with `runnable` would choose, blocked Tasks excluded), each once: a Requirement section counts as the element it is about, and no Transition, General section or Area is added. A reference is already compared when a recorded comparison covers it with the same code and the same text: such references are left out of the list and printed under `## Already compared`, and they are not compared again. With `--json` it gives `refs`, the list of `{ ref }`, the Tasks' identities in `tasks`, plus `alreadyCompared` with the references already compared. If no reference remains to compare (the list is empty, or every reference is already compared), the pre-flight is done. Otherwise compare the Machines among the remaining references (never those under `## Already compared`) following `trama-compare`, once: with a single Machine among them, do it yourself, running `trama comparison new <machine> --input -` with `{"refs":["<ref>"]}` on its references; with more than one Machine, give each Machine to its own sub-agent, all at once, up to the maximum number of sub-agents the instruction allows (20 when it gives no limit), in whatever way your agent starts sub-agents, and wait for all of them, the slowest included. References that belong to no Machine (an Actor, a Feature, a Requirement section with no element) stay with the Run's agent. Tell each sub-agent that this is the pre-flight of a Run and to compare only its Machine's references: file only Drifts with no origin (no `task`), and never to file a Task, announce a check or run `trama task list`.

**Proposal filters.** When the instruction names Proposals with `proposals` (only the Tasks of those Proposals) or `notProposals` (every Task but theirs, the ones with no Proposal included), pass those filters exactly as the instruction gives them to this pre-flight command and to every `trama task list` call with `runnable` of the Run, and add no other Proposal filter.

A difference that is the work of a Task about to start is not a Drift: do not file it. A Drift the pre-flight finds blocks the Tasks that concern the same element, and the Run goes on with the others. Close the check when the pre-flight is over: `trama announcement move <id> delivered` when it succeeded, and `trama announcement move <id> failed` when it failed or stopped. A failed or stopped pre-flight does not stop the Run: write the line `Pre-flight scan failed: the Run continues without it.`, repeat it in the report, and go on with the first Tasks. The pre-flight announces no card by hand and no second check: each Machine comparison is announced by its `trama comparison new`, and its cards are filed by one `trama comparison move <id> delivered`.

1. **Pick the Task.** Asked for one named Task, use the ID you were given, and do steps 2 to 5 for it. Asked for several ordinary Tasks, run `trama task list` with `runnable: true` and `max: <N>` for up to <N> Tasks, passing the JSON with `--input -` and a heredoc (`trama task list --input - <<'EOF'`, the JSON, `EOF`): <N> is the number of sub-agents the instruction allows, or 1 without sub-agents (with the Run's `proposals` or `notProposals` filters, if the instruction gives any). It prints one Task per line, short number and title (with `--json`, the list `batch`, each with `id` and `number`): up to <N> runnable Tasks that do not concern the same thing, and none that concerns a Task In progress the agent has taken, the first being the next runnable Task. `max` is the maximum number of sub-agents the instruction allows, an integer of 1 or more; 20 when the instruction gives no limit. It skips the blocked Tasks, moves nothing, and recomputes the answer each time, so a Task that waited for the Task fixing its Drift comes back, after it, once that Task is Done.
   - **With sub-agents**: start one sub-agent for each free place, up to <N> at once, in whatever way your agent starts sub-agents, and give each one a Task from the batch. If the project has the definition `.omp/agents/trama-implementer.md`, start that sub-agent (`trama-implementer`): its prompt carries steps 2 to 5 of this skill, so do not tell it to read this skill or to run those steps. Give it the Task's permanent identity, and the Task's images as paths, which it looks at before it starts (never put an image in the text of the instruction). Give it the sentences of the instruction that concern a sub-agent, on the same line, as the instruction writes them: the language sentence, if the instruction has one; "The Drift blocker is on", "The Advisor Scanner is on" and "The sub-agents context sharing is on", if the instruction has them; and, with the context sharing, the texts you already read that concern its Task, as "Sub-agents context sharing" says. The prohibitions hold for it and its prompt repeats them: it never runs `trama task list`, never takes another Task, never runs the full suite, the linter or the build, and never scans; it runs the commands that register its own work, and when one of its writes is stopped by a file reservation (a file held by another sub-agent) it stops at once, does not undo its changes, leaves its Task in `doing` and comes back with what it did, the file and the sub-agent that holds it. It comes back with the Task done, closed without changes with its note, or the Drift it filed. Each time a sub-agent comes back, its place is free: step 5 says what to do next, and the Conflicts bullet of "Parallel execution" says how to record and hand over the Task. Never write a file that a sub-agent holds: a write of yours stopped by a file reservation waits until that sub-agent is done. If the definition is not installed, the project predates it: start your own sub-agents with the instructions below instead, telling each one the Task's permanent identity and to do steps 2 to 5 of this skill for that Task only: move it to `doing`, read it once with `trama task show <id>`, check its premise (step 3), implement it and run only its own tests, then move it to `done`, close it without changes as step 3 says, or file a Drift as described below, announcing it, and leave the Task in `doing`. Tell it never to run `trama task list`, never to take another Task, never to run the full suite, the linter or the build, and never to scan; it comes back with the Task done, closed without changes with its note, or the Drift it filed. Tell it also the file-reservation rule: if one of its writes is stopped by a file reservation (a file held by another sub-agent), it stops at once, does not undo its changes, leaves its Task in `doing` and comes back with what it did, the file and the sub-agent that holds it.
   - **Without sub-agents**, or with one place only: do steps 2 to 5 yourself for each Task, one after the other, running `trama task list` with `runnable: true` and `max: 1` (with the same `proposals` or `notProposals` filters, if any) before each Task.

   With the parallel execution, that call adds `groups: true` (and no `heldBack`): it prints groups instead of the batch, `max` counts groups, and each group goes to one `trama-implementer` sub-agent as "Parallel execution" says, its Tasks taken in order.

   Read a Task once, with `trama task show <id>`. That text is the Model and the Requirements for this Task. A Machine reference includes the State tree and the Events with who receives them. A State reference includes the outgoing Transitions, including those inherited from the States that contain it, marked as inherited. An Event reference includes the Transitions that react to it. A reference to a whole Area includes the text of every section. Under `## Requirements` are the Requirements attached to the referenced elements, and every General section that has text, written in full. A Technical Task references no Model element; implement it as a normal engineering task from the Requirements in that text.

   **Images.** When the Task has images (the `Images` block of `trama task show`, the `images` field with `--json`), they are part of what the Task needs. Implementing it yourself, look at them before you start. Handing the Task to a sub-agent, pass it the paths and tell it to look at them before it starts, opening them with the tool it reads files with. Never put an image in the text of the instruction. An image you cannot see is ignored silently.
2. **Start it.** `trama task move <id> doing`. If the move is refused because the Task is blocked, nothing changed. Asked for one named Task: stop, take no other Task, and report the Task and the Drift (or fix Task) the refusal names; only the developer can decide on that Drift. In a run over several Tasks `trama task list` with `runnable` never names a blocked Task, so a refusal means something changed since you asked: leave that Task and go on with the other Tasks you were given.
3. **Read the code.** The Model and the Requirements for this Task are the `trama task show` text already read. Read the code that implements them and follow its conventions. For this Task, do not run `trama model show`, and do not open a `trama-req-*` skill. If a Transition the Task must implement does not appear in that text, run one `trama model show <ref>` for that Transition, and do not resume the tour.

   **Check the premise first, for a fix Task.** A Task that fixes a Drift says so on its Column line (`from Drift <id>`), and its text carries the Drift's two sides and its Where in the code. Before writing any code, re-read the code at Where in the code and at the Task's references, and compare what it does with What happens. If it already does what What should happen says (the Model or the Requirement), change nothing: run `trama task move <id> done --input -` with the JSON `{"unchanged":"<note>"}` in a heredoc, the note saying what you checked (the code and the behaviour); this also dismisses the Drift. Then skip step 4 and step 7 for that Task, and list it in the report's closed-without-changes list. Otherwise continue with step 4. A Task with no Drift skips this check.
4. **Implement.** Write the code, including every Transition's condition and consequence exactly as the prose in the Task text says, and the States around it that the Task depends on. Follow every Requirement in that text, including the General sections written there. Add or update tests for the behaviour. While writing, run the tests added or changed for this Task and the existing tests of the behaviour this Task changes. Do not run the project's full suite, the linter or the build after the Task. After the code, do not read the Model again.

   **Declare the progress.** While you work on the Task you have taken, say roughly how far along you are with `trama task move <id> doing --input -` and `{"progress":40}` in a heredoc: an integer from 0 to 100, a multiple of 10, that you judge yourself at natural milestones (for example after reading the Task, when the code is written, when its tests pass); there are no fixed values and no need to declare before Done. It only declares: it never moves the Task, and the percentage is forgotten when the Task leaves Taken by the agent. A sub-agent declares only for its own Task, and whoever starts sub-agents tells each of them so. An ignored declaration (the Task is not taken by you) prints a note and exits with 0: it never stops the work.
5. **Finish the Task.** `trama task move <id> done`. Record the permanent ID of each Task this run moves to Done without `unchanged`; the scan of step 7 takes its scope only from those. In a run over several Tasks, each time a sub-agent (or you, without sub-agents) finishes its Task (Done, closed without changes, stopped by a Drift, or stopped by a file reservation as step 1 says), run `trama task list` with `runnable` and `max: <free places>` (with the same `proposals` or `notProposals` filters, if any), where the free places are <N> minus the sub-agents still working, and start the Tasks it prints at once, from step 1. When no sub-agent works and none has been received, run it once more with `max: <N>`: if it says no Task is runnable, look for Tasks taken by others before closing the run. Run `trama task list` for the Tasks In progress of the Run's scope and run `trama task check <id>` on each one that neither you nor your sub-agents took. If at least one comes back `released` (back in To do), run `trama task list` with `runnable` again and go on from step 1 as always; otherwise the Tasks are finished and the run goes on to step 6, and the report lists the Tasks taken by others that are still `alive`. A Task asked by name is a single-Task run: it does not do this.

   With the parallel execution, each call of this step that asks for runnable Tasks adds `groups: true`, as "Parallel execution" says: `max` counts groups, and the groups it prints take the free places.

6. **Check the run.** A Task asked by name is its own run, so this step follows it at once. In a run over several Tasks, this step runs once, after the last Task, when no sub-agent works, none is received and `trama task list` with `runnable` and `max: <N>` (with the same `proposals` or `notProposals` filters, if any) says no Task is runnable; never in a sub-agent. Run the project's checks (tests, type check, linter and build) together, as parallel processes, that do not depend on each other, and wait until every one has finished before judging the check: it passes only when all of them pass. Two checks depend on each other when one uses what the other produces or when both write the same files; when in doubt, run them one after the other. If the check fails, fix the code and run again, together, the checks that failed and those that depend on them, without reading the Model again; leave every Task in the column it is in. If you cannot tell which Task broke the check, say so in the report and stop, without another reading tour and without step 7.
7. **Scan the completed Tasks' scope.** Only when the check of step 6 passed, the run moved at least one Task to Done without `unchanged`, and no Task of its scope is blocked at the end (`blockedBy` in `trama task list --json`; the scope is every Task in "todo" for a run over several Tasks, that Task for a Task asked by name). Run `trama task list` with `tasks: [<id>, …]` and `scope: true` (the permanent IDs of the Tasks this run moved to Done without `unchanged`). If the scope is empty, do not scan; go on to step 8 with the check open. Otherwise, follow the steps of `trama-scan` on exactly the references in this `## Scan scope`, in this same run, comparing each Machine with `trama-compare` on its references (`refs`); do not expand it to the whole System or a whole Feature. Link the Tasks the scan files to a design with `proposal` (the Proposal's ID) only when this run is a single Task asked by name that belongs to a design (`proposal` in `trama task show <id> --json`); otherwise link none. Do not implement the Tasks this scan files.
   With the Advisor Scanner on, this step never runs: go on to step 8 with the check open.
8. **Write History.** Run this step after step 7, or after step 6 when step 7 does not run, whenever the run moved at least one Task to Done without `unchanged`, also when the check of step 6 failed. Pass control to History with `trama announcement move <id> history` (on the check of this run). If the sub-agent of the check came back with entries, run each of its JSON as it says, with `trama history new --input -` or `trama history edit <id> --input -`, and fix and run again the refused ones; check first that together they name every Task this run moved to Done without `unchanged`. Otherwise read the entries with `trama history list --json`, and `trama history show <id> --json` for those that look related. Group the Tasks of this run by macro-feature, reading their titles, bodies, their Proposals (`trama task show <id> --json`) and the entries already written: when an entry already tells the same feature, update it with `trama history edit <id> --input -` and `{"tasks":["<id>"]}` (it may also change `title`, `summary` and `body`; `tasks` only adds Tasks, never removes one) instead of writing another; otherwise write a new one with `trama history new --input -` and `{"title":"<title>","summary":"<text>","body":"<text>","tasks":["<id>"]}`, listing in `tasks` every Task it names. Name every Task this run moved to Done without `unchanged` at least once, by its permanent ID; a Task closed without changes is never named. Write title, summary and body in the language the instruction asks for; the title is one line, the summary one line of at most 280 characters. A refused command changes nothing and names each problem: fix it and run it again. Only this skill writes entries after a run: a sub-agent never writes them, and a run interrupted before this step writes none. Then close the check as the "Announcing the check" section says, and go on to the report.
9. **Report.** Say what you implemented, in domain terms, the Drifts you filed (each with its Task), anything you noticed that was outside the Tasks, the Tasks closed without changes, each with its note in a list of its own, the Tasks still in "todo" left unrun, each with the Drift or the fix Task that blocks it, as the last `trama task list` with `runnable` lists them, the references the pre-flight found already compared (`## Already compared`), the Tasks and Drifts the scan of step 7 filed, and the History entries you wrote or updated, each by its title.

## When you must file a Drift

Stop working on the Task at once and file a Drift when any of these is true:

- The Model cannot be implemented as written (contradiction, impossible condition, an Event nothing can emit).
- The Model is silent on a case that the Task forces you to handle, and the choice changes what the user sees or what data is kept.
- Doing the Task right requires a State or Transition the Model does not have.
- A Requirement cannot be followed (it conflicts with the Model, another Requirement, or the platform), or the Task forces a construction choice the Requirements should decide and do not.

Before running `trama drift new`, re-read the code at the place you name in `where` and file only if it really does what `happens` says. A resolved Drift counts as closing a difference when it was fixed in the code, its Proposal was accepted, or the developer dismissed it by decision; a Drift dismissed by its own fix Task (closed without changes) does not, so a difference that comes back is filed again. A Drift resolved as `unified` was merged into another Drift without any decision, so it does not count either.

Then:

1. Decide which case applies. If the code is right and the Model forgot a case, begin a Proposal with the `trama-design` skill, without its interview (list your choices in the Proposal body): `trama proposal new --input -` with `{"title":"<title>","body":"<why>","label":"<short label>","announcement":"<id of the Drift's announcement>"}`. Finish its files, but do not hand it over yet: attach the Draft to the Drift in step 2, then hand it over right after with `trama proposal move <id> open`; if the hand-over is refused, correct it and hand it over again. Otherwise there is no Proposal, except in the case of step 2 where no fix respects both the Model and the Requirements.
2. File the Drift **once**: `trama drift new --input - <<'JSON'` and `JSON`, with the object `{"title":"<title>","refs":["<nearest Model element or Requirement>"],"task":"<id of the Task you are implementing>","happens":"<what the code does or what you would do instead, in terms of behaviour>","should":"<what the Model or Requirement says and why it cannot be followed>","options":[{"title":"<title of the way you recommend>","text":"<what it changes and costs>"},{"title":"<title of another way>","text":"<…>"}],"where":"<where in the code>"}` (up to five options), adding `"proposal":"<id of the Draft>"` only in the first case, and `"announcement":"<id>"`. The two texts, the options and `where` are required; `where` is the only place for code locations. Write them as described in "Writing a Drift". `task` records the origin: the Drift blocks that Task and Tasks that concern the same thing.
   Give the Drift a short title (see Naming cards).
   - **Resolved Drifts first.** Before filing, run `trama drift list --input -` with `{"all":true,"refs":["<ref>"]}` for the references of the difference. A difference that a resolved Drift closed stays closed while the Model or the Requirement there still says the same thing: do not file it again. If it is back after a fix of the code or an adaptation of the Model, set `previous` to the ID of that resolved Drift; the command refuses a previous Drift that is open, dismissed, `unified` or unknown. When `task` names a fix Task (one whose `drift` field is set), Trama writes `previous` itself, so it is not needed.
   - **No fix respects both.** When no fix of the code respects the Model and the Requirements together (for example, two Requirements contradict each other), file the Drift with no `options`, with `proposal` set to the Draft that repairs the Model or the Requirements, as in step 1. A Drift without Fix options is refused without a Proposal.
3. Leave the Task in `doing`; the developer decides whether the code or the Model changes. Asked for one named Task, stop here. In a run over several Tasks, go on with the free places as step 5 says: run `trama task list` with `runnable` for the next Tasks. The Drift blocks only the Task it was filed for and the Tasks that concern the same thing, and `trama task list` with `runnable` skips those.
4. Report. Say what you implemented and the Drift you filed, with the Task it concerns. In a run over several Tasks this goes into the final report described in step 9 of the steps above, once `trama task list` with `runnable` says no Task is runnable. A sub-agent reports to the main agent instead, which writes the one final report.

Small choices that stay below Diagram level and that no Requirement covers (names, data structures, how an effect is carried out) are yours to make; do not file Drifts for them.

## Writing a Drift

The developer reads a Drift at a glance, as a programmer, but not as a code review. Write the two sides, and the fix options, at the level of behaviour.

- **Say what the System does and what it should do**, in the words of the domain ("the cart total ignores the coupon"), not how the code does it.
- **Name no variable, function, class, field or file** in `happens`, `should` or the options, unless the difference cannot be understood without it. Then name only the one or two that matter, as `inline code`.
- **Code locations go only in `where`**, which is required for every Drift: the files, and the code element when it helps. No line numbers, which go stale, and no long pieces of code.
- **Give two to five fix options**, the one you recommend first: each option is an object `{"title":"<title>","text":"<text>"}`. Each is a different way to reach what should happen, not a step of one plan, and says in terms of behaviour what changes and what it costs. About 60 words each, short Markdown, no headings or tables inside an option. Titles differ. A Drift filed with fewer than two, more than five, or an option missing its title or text is refused.
- **Fix options reach what should happen** without changing the Model or any Requirement, and respect every Requirement that applies to the elements of the Drift, not only those it names. An option that asks for an exception to, or a change of, the Model or a Requirement is not a fix option: that way goes to a Drift with a Proposal.
- **Use short Markdown:** short paragraphs, a bulleted list when there are several separate points, **bold** for the one or two terms that carry the difference. No headings inside a section, no tables, about 100 words per side.

## Drift blocker

This section applies only when the instruction says "The Drift blocker is on". Without that sentence, never name a Task in `notBlocking`, and skip this section.

When it applies, do this before each `trama drift new`:

1. Ask for the candidates with the references and origin you will file with: `trama drift new --input -` with `{"refs":["<ref>"],"task":"<origin>","dryRun":true}` (`task` only when there is an origin). It lists the Tasks that Drift would block, the origin included, and writes nothing. If it lists none, file the Drift as usual. A Drift that a Machine's comparison files gets its candidates from `trama comparison new <machine> --input -` with `{"candidates":true}` instead, as `trama-compare` describes.
2. Judge each candidate: does the difference you found touch that Task, its references or what it changes? Leave free only the Tasks the difference does not touch, with a one-line reason for each, in Italian. Judging only removes blocks: never leave free a Task the difference touches, and never name a Task the command did not list.
3. Pass each Task you leave free in `notBlocking`, a list of `{"task":"<permanent ID>","reason":"<reason>"}`. Pass none when the difference touches every candidate.

The judgement is made once, at filing: a Drift keeps the Tasks it leaves free and blocks every other one, including the Tasks created later about the same thing.

When you start sub-agents, pass them the sentence "The Drift blocker is on" together with this section, and ask each one to report the permanent IDs of the Drifts it registered and, for each, whether it blocks any Task.

### Final resolution of the Drifts that block nothing

Keep the permanent ID of each Drift you file that blocks no Task: it blocks none when every candidate was left free, or when there was no candidate. Sub-agents report the same, as above.

When the work is over (after the final check and the end-of-Run scan, if there is one), gather those Drifts into one resolution, unless none is left:

1. Leave out a recurring Drift (it follows one or more earlier Drifts: `previous` is always a list in `--json`, and a Drift can also have several origins in `origin`): the developer decides it, seeing the chains of its predecessors. A Drift left out stays open.
2. For each remaining Drift, record the recommended decision: when it has an attached Proposal, `proposal`, and the resolution carries that Proposal's changes as the trama-resolve-drifts skill describes; otherwise `fix-code` with option 1.
3. Announce it with `trama announcement new --input -` with `{"kind":"proposal","title":"<title>"}`, write it with `trama proposal new --input -` and `{"title":"<title>","kind":"resolution","nonBlocking":true,"announcement":"<id>","body":"<what is resolved and why>"}`, and record each decision with `trama proposal edit <proposal id> --input -` and `{"drifts":[{"drift":"<drift id>","decision":"<decision>","option":1}]}` (`option` only with `fix-code`). Hand it over with `trama proposal move <id> open` and read its output, without `trama proposal show` before it.

Never approve or reject this resolution, and never start a Run because of it: the developer decides it, as any manual resolution.

## Parallel execution

This section applies only when the instruction says "The parallel execution is on: follow the \"Parallel execution\" section of the trama-implement skill.", and only for the main agent of a run over several Tasks that can start sub-agents. Without that sentence, without sub-agents, or for a Task asked by name, skip it and follow the steps as written.

With it, the rule of the free places (`trama task list` with `max` never gives two Tasks that concern the same thing) stays the base, but you plan beyond it from the text of the Tasks, never from the code.

- **Ask.** Before the first Task (after the pre-flight, when there is one), run `trama task list --input -` with `runnable: true`, `groups: true`, `max: <N>` and the filters of the Run (`proposals` or `notProposals`, exactly as step 1 says). It prints `## Group <n>` blocks (with `--json`, `groups`, each with its `tasks`, `refs` and `files`): each group holds runnable Tasks that concern the same thing, directly or through other Tasks of the group, or name the same project file, and the largest group comes first; `max` counts groups. The runnable Tasks that concern a Task In progress the agent has taken are held back and sit in no group. Do not add `heldBack` to this call: `groups` does not take it.
- **Read, without the code.** For each Task of the groups, each held back one and each already In progress, read the title, body, references and Proposal (`trama task show <id> --json`). Do not open the code to decide.
- **Plan.** Start from the groups in the order Trama gives them, and decide each of the following with a one-line reason:
  - **Free paths**: which held-back Tasks start together with the chosen or In progress ones, because from the text you judge that they touch neither the same files nor the same behaviour;
  - **Splits**: which Tasks of a group, because from the text they touch neither the same files nor the same behaviour, run as separate groups, each with its own place;
  - **Merges**: which two groups run as one group, one after the other, because from the text the one depends on the other or they touch the same things;
  - **Orders**: which Tasks wait until another is Done, because from the text the first depends on the second. A Task kept back this way is not started.
- **Limits.** Never start a blocked Task (`trama task list` names none among the runnable ones). Never keep more than N sub-agents working, the ones already working included: a group being worked takes one place. Each group goes to one `trama-implementer` sub-agent, with at most 3 of its Tasks, in order. The Tasks past the third, and those the sub-agent reports unstarted, go to a new sub-agent with the summary of the first, as soon as a place is free and no order holds them. Never start a Task before the Tasks its order makes it wait for are Done.
- **Record.** Record every free path, split, merge, order and conflict with `trama timing new --input -` and `{"kind":"<kind>","tasks":["<id>","<id>"],"reason":"<one line>"}`. `kind` is `release` for a free path or a split (Tasks started together or divided although the rule keeps them apart), `order` (the first Task waits for the others to be Done, which is also how a merge is recorded) or `conflict` (the sub-agent of the first Task stopped because it clashed with the others). `tasks` names at least two Tasks by permanent identity, the first being the one the choice is about, followed by the Tasks it concerns. Record a choice when you make it.
- **Revise.** Ask again with `groups: true` and `max` for the free places, and revise the plan when a sub-agent comes back (Done, closed without changes or stopped by a Drift), when a new runnable Task is born (for example a fix Task) and when a Task becomes blocked. The free paths, splits, merges and orders already given stay until the revision changes them. Start groups for the free places only as the revised plan allows.
- **Conflicts.** The file-reservation rule of step 1 is the base of this bullet, and it holds in every Run, with or without parallel execution. When a sub-agent comes back stopped by a file reservation, or by seeing that its Task changes the same files or the same behaviour as another Task In progress, record a `conflict` with `trama timing new --input -` and `{"kind":"conflict","tasks":["<stopped Task id>","<holder Task id>"],"reason":"<one line>"}`, naming first the Task of the stopped sub-agent and then the Task of the sub-agent that holds the file (or the clashing Task). The stopped sub-agent does not undo its changes and never corrects files that belong to another Task's work. Free its place; the stopped Task is not finished and nobody resumes it from the main agent. The Tasks of its group that it reports as not started return to the plan: they go to the next groups as the revised plan allows, not to the stopped sub-agent. When the holder's Task is Done, give the stopped Task to a new sub-agent, with the report of the first one.
- **Report.** The report of the run (step 9) has a section "Parallel choices" that lists every free path, split, merge, order and conflict, each with its Tasks and its reason.

## Async Drift Resolver

This section applies only when the instruction says "The Async Drift Resolver is on: …". Without that sentence, skip it.

With it, at the very end of the work (after the last archiving, the end-of-Run scan and the `nonBlocking` resolution of the Drift blocker, if any, and before the final report and the History entries), you prepare the question of every Drift this work filed, so Resolve opens at once. You alone do this, never a sub-agent that compares or implements.

1. **Find the Drifts.** Run `trama drift list --input -` with `{"currentJob":true,"unprepared":true}`; never read `TRAMA_JOB` by hand: the command reads it itself. It lists the open Drifts of this work, the advisor's included, with no valid prepared question and outside every resolution. A Drift already in a resolution (the `nonBlocking` one) is left out.
2. **Prepare each.** Follow "Writing a prepared question" in the `trama-resolve-drifts` skill (read it first) for each Drift, with the sub-agents you have: hand the exploration to at most `trama.maxParallelAgents` of them at once (the number the instruction gives, 20 when it gives none), one Drift (or a few that concern the same thing) each, and have each record its questions with `trama drift edit`. Without sub-agents, one Drift at a time. A sub-agent asks the developer nothing and registers no other card.
3. **Report.** The final report says how many Drifts were prepared and which were not (with the reason).

## Sub-agents context sharing

This section applies only when the instruction says "The sub-agents context sharing is on: …". Without that sentence, skip it and work as written above.

With it, when you hand a part of the work to a sub-agent, in whatever way your agent starts sub-agents, you pass it what you have already read that concerns its part, so it does not look for it again and does not read it again.

- **What you pass.** Of what you have already read, only what concerns that sub-agent's part, plus a short common part (the request and the decisions, when there are any): Trama's texts quoted as they are (the written request with its images put in words, the output of `trama model show`, `trama task show`, `trama drift show`, `trama proposal show`, the decisions of the interview) and the places in the code already known, one line per reference, ``- `<ref>` — <where in the code>``. Never code, never everything you gathered, and nothing you read only to pass it on.
- **What the sub-agent does.** It does not reread the Trama texts it received and reads on its own only the ones that are missing. It always reads the code, also at the places it received, always runs the commands that register (`trama task move <id> doing`, `trama comparison new`, `trama drift new`) and loads its skill as without this feature. A received place that no longer matches the code is ignored: it searches by itself. Context Sharing never stops a job.
- **What comes back.** Each sub-agent reports where it found the code of what it saw, one line per reference as above; you reuse those lines in your own work and for the sub-agents that follow.
- **Limits.** No sub-agent runs again a read-only Trama command for a text it received, and what you pass to each one concerns only its part: never copy into every sub-agent all that you gathered.

In this skill:

- **Implementing a Task.** A sub-agent receives the text of `trama task show` when you have already read it (with the parallel execution) and the places in the code the pre-flight found. A `trama-implementer` sub-agent loads no skill, and it skips `trama task show` only when it received that text. Every sub-agent still takes the Task with `trama task move <id> doing`.
- **The pre-flight and the end-of-Run scan.** Each `trama-analysis` sub-agent receives, with its Machine and `refs`, only the places in the code already known for those references and the reason of each entry of the scope. Lists of cards and the General Requirements stay out, as without this feature. Reuse the places the sub-agents report in `## Already present` and for the sub-agents that follow.
- **Preparing the questions (Async Drift Resolver).** For each Drift, pass the output of `trama drift show`, the Proposal attached to it, the chain of its `previous` Drifts and where the code is. The code at its Where in the code is read again before deciding. A unified Drift can follow several Drifts: pass every chain.

## PowerShell

The examples use POSIX syntax. In PowerShell, pass JSON with a pipe and `--input -`, for example `Get-Content -Raw round.json | trama question new --input -`, instead of `<` or a heredoc. On Windows PowerShell 5.1, set `$OutputEncoding` and `[Console]::OutputEncoding` to UTF-8 first, or non-ASCII characters arrive as `?`. Never pass the JSON as the text of `--input`: Windows PowerShell 5.1 strips the inner quotes of arguments to external programs.
