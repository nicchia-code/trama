# Changelog

## 0.0.15

- omp is checked before every launch (design, scan, import, Run, Run all, Resolve Drifts, Unify Drifts, Ask more and Quick Task, in a terminal or in omp Chat): Trama finds the program (`trama.ompPath`, else the first `omp` in the editor's PATH, `~/.bun/bin` or `~/.local/bin`; `omp.exe` on Windows) and, when it is missing, starts nothing and shows `Trama: omp is not installed. Trama runs every agent with omp.` with `Install omp` and `Open Settings`. Otherwise it runs `omp update --check` and, with a newer version, `omp update` behind a progress notification `Updating omp to <version>…`, with no confirmation; a failed check or update lets the launch go on with the omp of before and tells why once per check. The outcome holds for an hour for every window and the same program (`ExtensionContext.globalState`, `trama.ompUpdateCheck`) and is forgotten when `trama.ompPath` changes or the installer ends. The folder of the omp found and the folder of bun go in front of the PATH of every omp process.
- Cursor is no longer supported, as an editor or as an agent (ADR 0013): only omp, in VS Code. The setting `trama.agent` is removed (a value left in the user settings is neither read nor rewritten), and so are Cursor's chat with its hooks, the Advisor of the chat and `CURSOR_AGENT`, which identifies no agent any more (`TRAMA_AGENT` does).
- The commands `trama hook cursor` and `trama advisor review` are removed and now exit with a usage error like any unknown command; the hooks are `trama hook idle` and `trama hook start <pid>`, and `trama advisor show` stays. The Trama skills no longer name Cursor's tools (`AskQuestion`, `AwaitShell`) or its sandbox: the developer is asked only with Trama's question round.
- Announcements belong to an agent terminal only: `chat` and `conversation` are gone from the announcement files and type, and a file that still has one (written when Cursor's chat could announce) is a reading error, skipped and never converted or deleted. `trama announcement new` is refused without `TRAMA_TERMINAL` (an omp Chat conversation has the one of the terminal it replaces), and `trama proposal new` without it creates the Proposal with no announcement and no error.
- The omp Chat view of the bottom panel is removed: omp Chat lives in the secondary sidebar only.
- omp Chat is on by default (`trama.ompChat`); only `false` in the user settings turns it off.
- New setting `trama.ompChatApproval` (`ask`, the default, or `yolo`, read only from the user settings): with `ask`, omp asks permission in omp Chat as it does in the terminal; with `yolo`, it runs every command without asking.
- The Windows package is smoke-tested with `trama.exe --help`, `project new` and `model check`; the `hook cursor` step and the release note on Cursor's hook form on Windows are gone.

## 0.0.14

- The Board has no `System Activities` column: three columns remain, `Backlog`, `Active` and `History`. Ghosts stand at the bottom of the column of their card, after the real cards and before the button at the foot, in the order announced: Proposals (design requests and Resolve included) and Drifts (Unify included) in `Backlog`, Tasks in `Active`; a column with only ghosts still shows its empty text above them. Ghosts of checks, scans, comparisons and works have no column and are not drawn on the Board. A ghost's details dialog gives the focus back to the column the ghost stood in when it goes away. The column of a ghost is decided by the pure `ghostColumn` in `src/core/ghost-column.ts`.
- Status bar item of the ghosts with no column: one item `Trama Activities` (id `trama.activities`, left group, lower priority than every other item of Trama, so last of the group), in every window open on a Trama project, also with the panel closed, shown only while a check, scan, comparison or work ghost (Import, Quick, Ask) exists. Its text is the spinning `loading~spin` icon, the title of the most recent ghost and ` +<N>` for the others; its tooltip lists kind and title, phase, `Running for <duration>` (recomputed every 30 seconds) and the latest note; its accessible name ends with `. Show details`. Clicking it runs `trama.showActivities` (not in the command palette): with one ghost it opens the panel on the Board with that ghost's details, with several a QuickPick that follows the announcements and opens the chosen ghost's details. The host reads the announcements itself on the `.trama/**` watcher, reusing `ghostColumn` and the ghost texts of the Board; the texts are English whatever `trama.language` says. Navigation options (`NavigateOptions.ghost`) carry the ghost to the panel.
- omp Chat: a conversation saved at rest comes back at rest, with its history and no Run in progress on the Board; only a conversation that was working gets its Run back. `extension/README.md` is back, short, on the Settings tab (groups Agent, Models, Project and Features), which always writes to the user settings.
- omp Chat (`trama.ompChat`, on by default, in the `Features` group; turned off only by `false` in the user settings, a workspace value does not count): the jobs Trama starts with omp open as conversations in the `omp Chat` view, declared in its own container of the secondary sidebar (VS Code 1.106 or later; the context key `trama.ompChatVisible` is a boolean), one conversation and one `omp acp --yolo` process per job, with the same rules as the omp terminal (instruction, role and model, announcement, taken Tasks, question rounds, `trama.autoExit`, run check). By default every command runs without asking (omp's permissive mode, only for these processes); the session receives only the MCP servers of omp's native files (`.omp/mcp.json`, `~/.omp/agent/mcp.json`). A conversation can be stopped, closed, sent messages while the agent works, and switched to another model; open conversations resume after a window reload. When omp cannot be started the job runs in the terminal with a notice. New ADR 0012 records that ACP returns for omp Chat only; ADR 0004 stays superseded and ADR 0011 stays valid.
- Removed `trama.submitWhileRunning`: Run and Run all are always unavailable while a Trama run is in progress; a leftover value is ignored.
- The optional features leave the `Experimental` group of the Settings tab and the wizard's Advanced step for a `Features` group, last, with five checkboxes off by default. Their keys are renamed without migration: `trama.experimentalDriftBlocker` is now `trama.driftBlocker`, `trama.experimentalAdvisorScanner` is `trama.advisorScanner`, `trama.experimentalParallelExecution` is `trama.parallelExecution`, `trama.experimentalAsyncDriftResolver` is `trama.asyncDriftResolver`, and `trama.experimentalContextSharing` is `trama.subagentsContextSharing` (titled Sub-agents Context Sharing). The old keys are no longer read: a value left in the user settings is ignored and not rewritten, so whoever had one of these features on must turn it on again.
- The README is rewritten as a short introduction with how to install and use Trama, without images; `docs/images/` is removed. `docs/cli.md` no longer links to it.
- The Advisor of Cursor's chat no longer adds the notes of a background review to the agent's next tool result: Cursor delivers them with the round's result, and Trama only keeps them in memory for the Task or final review. The `Note in attesa` state is removed; after a round with notes the agent goes back to listening, or, if files changed meanwhile, the next tool result asks for the next round as before.
- The Advisor of Cursor's chat asks for its continuous review as a round in the background: with the result of the tool that changed files, a watched agent is told to start `trama-advisor` with `run_in_background: true` for a new review identity, naming the files changed since its last round and, when the transcript is known, the transcript and the byte position of its conversation since then (`0` at the first round). For a watched agent `afterFileEdit`, `afterShellExecution` without `matcher` and `postToolUse` send the editor `transcript_path` when Cursor gives it non-empty (the state file never holds paths or notes); the editor derives a sub-agent's transcript as `<folder of the main transcript>/subagents/<sub-agent conversation>.jsonl`, measures it with `fs.stat` when it prepares a round and never reads it. At most one round runs per watched agent; files changed meanwhile are asked for with the next tool's result. Cursor delivers the result and the notes of each round to the agent, Trama keeps the notes in memory for the review of the Task and the final review, which are now asked for in the foreground ("Ignore the result of any earlier background review") and make a round still going no longer count. `~/.cursor/agents/trama-advisor.md` is still the only definition, started in the background for rounds and in the foreground for those reviews, and ends with the result for the agent. The `trama-implement` skill tells the agent and its sub-agents never to wait for or check on a round and to correct the code when Cursor delivers a round's result. Background rounds need Cursor 3.27.6 or later; earlier versions are neither recognised nor reported. `docs/cli.md` and the README describe it.

## 0.0.12

- Notes on announcements (`agent.DECLARE_ANNOUNCEMENT_NOTE`): `trama announcement edit [<id>]` with `{ note }` declares one line about what the agent is doing and why. With the announcement's ID the note goes only to that announcement, comparisons included; without it, to every announcement still waiting that belongs to the agent's terminal (`TRAMA_TERMINAL`) or Cursor conversation (`TRAMA_CHAT`), comparisons excepted, and with none the command says so and exits with 0. A note is one line (line breaks become spaces); over 120 characters it is saved cut to 119 plus `…` and the command says so. An announcement keeps its last 6 notes with their instants, and a note equal to the previous one only renews its instant. A note changes no phase, title, `touched`, Draft binding, delivery or withdrawal, and does not count as the agent's activity. The announcement file has `notes` (`{ at, text }`), the Board snapshot carries `notes` and `announced` for each announcement, and `ownedBy` in `src/core/announcements.ts` is now the one rule that says which announcements a terminal or a conversation owns (also used when a conversation ends). The skills `trama-design`, `trama-setup`, `trama-scan`, `trama-implement`, `trama-import` and `trama-resolve-drifts` have a "Notes on the ghost" section saying when to declare a note, and `trama-compare` says to write on the comparison's own ID.
- Ghost details on the Board: each ghost in System Activities is one button (reached with Tab, opened with a click, Enter or Space; still not counted and not draggable) that shows the agent's latest note under its phase, on one line with the full text as tooltip, and opens a read-only dialog with its kind, title, `Running for <duration>` (kept current while open), a paragraph that explains the ghost by kind and phase, and the `Agent notes` (the latest highlighted, the earlier ones under it, each with its `HH:MM`, or `No notes from the agent yet.`). The dialog follows the ghost's phase and notes, closes by itself when the ghost goes away or the panel closes, and gives the focus back to the ghost when closed. The pure logic (explanations, duration, notes) is in `extension/src/webview/board/logic.ts`.

## 0.0.11

- Unify Drifts: `trama drift new` accepts `unifies`, a list of at least two open Drifts, and files one unified Drift while closing the merged ones as `resolution: unified` with `unifiedInto` (all or nothing). A Drift can now have several origins and several precedents: in the file `origin` and `previous` are a string for one value and a list for several, and the Snapshot and `--json` always carry `origin`, `previous`, `unifies` and `unifiedInto` as lists (`snapshot.unifiedDrifts` has the merged Drifts). The unified Drift blocks every origin, fixing its code sends every origin not Done back to To do, and a `unified` Drift is not counted among the Drifts already resolved, is never a `previous` and refuses `drift move`. `drift show`, `drift list` and `project show` mark it. The skills `trama-resolve-drifts`, `trama-scan`, `trama-implement`, `trama-import` and `trama-compare` know about several origins and precedents; update skills to refresh installed copies.
- **+ Add Work Item** at the foot of Backlog uses the same split-button component as Reject and Dismiss Drift (dashed border, `ChevronUp` arrow, menu above the button) in a full-width mode: the main part grows and shrinks, the arrow never shrinks and never leaves the column.

The host still prepares them; one constant in `extension/src/webview/board/index.tsx` turns them back on. The `Trama stopped following …` notices stay.
- Add Quick Task (the arrow of **+ Add Work Item**) opens a new, bare chat with the agent: no instruction, skill or request, on the model of `trama.execution`. With omp it is a terminal named `Quick`, in the area or the tab chosen by `trama.terminalLocation`, running `omp [--model <m>]` with no hook, no overlay and none of the options of Trama's other instructions; it takes the focus, shows the ghost `Quick` until omp exits or the terminal closes, and is never a Run. The overlay is the same file as the Advisor Scanner's, `launch.yml` in the extension's storage: `--config` is passed only when it has content, `--advisor` and `TRAMA_ADVISOR_SCANNER` stay tied to the Advisor Scanner. A failed search or write never stops a launch; skills, sub-agents and `.omp/WATCHDOG.yml` are never excluded, and Cursor's chat is unchanged.
- Rework with feedback: **Reject** rejects at once, without a feedback box. Reject and **Dismiss Drift** are split buttons, on the Board and in the Diagram's details, whose arrow offers **Rework with feedback**: a rejected Proposal is redone by an agent following the developer's text, and the first Proposal it opens takes its place (`reworks`); an open Drift is resolved by the agent alone following the text, without closing it first. The work counts as Resolving, and the skills know how to redo a rejected Proposal.
- Task images: a Proposal's Task can carry images for whoever implements it, kept locally in `.trama/task-images/<task id>/` (not versioned) and managed with the `images` and `removeImages` fields of `trama proposal edit`. The panel previews them in the Task's details; the folder follows the approval, the rejection and the end of the Task. The `trama-design`, `trama-setup` and `trama-implement` skills explain how a request's images reach the Tasks.

## 0.0.9

- Setup wizard: Get Started is now a step-by-step wizard, `extension/src/webview/wizard/`, shared by Get Started and the Settings tab. Its steps are `Path`, `omp`, `Models`, `Project`, `Folders` (only with Import from Code) and `Advanced`, then a `Summary` that lists every value, marks the ones that change with `changed` and `was <value>`, and takes each row back to its step. Every step starts from the user settings (`globalValue`, else the manifest default); Back and Next keep the choices; nothing is saved or created before the summary is confirmed, and closing the panel or cancelling forgets everything. Its modes are the first setup (Get Started), Settings (the **Guided setup** button at the top right of the Settings tab, which shows the wizard instead of the form) and Empty Model (the Diagram's **Import from Code** and **Start from Scratch** buttons and the **Trama: Import from Code** command in a project with an empty Model, which open the wizard in the Settings tab with that path chosen). `Next` that cannot be used says why in its tooltip.
- `Path` chooses Import from Code or Start from Scratch and, with several workspace folders, the folder to initialize; Start from Scratch on a folder with files shows its warning in the step, no longer in a modal dialog. `omp` checks omp (`omp models`) at the chosen path and shows the result without blocking. `Models` suggests the models of the omp at the path chosen in the wizard even before it is saved, and `Next` waits for a valid number of sub-agents. `Advanced` can be skipped, and Skip brings its values back to the initial ones.
- The confirmation writes only the changed keys, in the order of the steps, in the user settings and stops at the first failure (the keys already written stay, nothing is initialized, the summary shows the reason and the confirmation can be repeated); then, in the first setup, it initializes the chosen folder with the chosen skills folder (same refusal and same dialog for customised skills as before) and goes on with the path. The modal dialog for a folder with files and the folder picker of the initialization are removed from the editor; `trama project new` is unchanged. Messages: `openGuidedSetup`, `agentCheckWanted`, `folderChildrenWanted` and `confirmSetup` (webview to host), `guidedSetup`, `workspaceFolders`, `guidedSetupResult`, `agentCheck` and `folderChildren` (host to webview), and `modelSuggestionsWanted` with an optional agent and omp path; `initialize` no longer exists.
- Import from Code, excluded folders: `Folders` shows the first level of the chosen folder as a tree with a box per entry, without the names that start with a dot and, in a git repository, without what `git check-ignore` ignores. What you uncheck goes to the agent in the import instruction («Do not import these paths and do not ask which folders to import: `a`, `b/c`.», or «Import every folder and do not ask which folders to import.»), and the `trama-import` skill then does not ask for the folders. The exclusions are not saved and do not change later scans or Runs. The command with a non-empty Model imports as before, with no sentence about folders.
- The settings controls of the Settings tab are now the shared component `webview/settings/field.tsx`, also used by the wizard; the `Checkbox` shows the indeterminate state.
- `trama task check <id>`: asks about the health of whoever holds a Task the agent has taken (`agent.CHECK_TASK`). Answers `not-taken` or `unknown-holder` (`agent: true` or `cursor`) without contacting the editor; otherwise sends the `check-task` message to an open window of the project (found as for `trama question new`) and waits up to 5 seconds for `alive` (with the holder) or `released` (with the reason), else `unavailable`. Exits 0 for every outcome, writes nothing and does not count as the agent's activity. The window side is `onCheckTask` of `createQuestionServer`, wired in `extension/src/host/questions.ts` to `checkTaskHolder` (`extension/src/host/task-check.ts`): a terminal this window follows gets the terminal check (`checkAgentTerminals` now takes an optional terminal and returns what it found), any other held Task the release of Tasks no window follows; a release puts the Task back in To do with the Board notice. `trama-implement` step 5 runs `task check` on the Tasks taken by others before closing a multi-Task Run; the command reference of `docs/cli.md` is regenerated.

## 0.0.8

- Identity prefix on compound lines: the Cursor shell hook writes the literal `TRAMA_CHAT=… TRAMA_JOB=… ` before every `trama` invocation of a compound line (`cd x && trama model show`) instead of `export`ing the variables before the whole line, so no variable stays in the session's shell.
- Tasks taken per conversation: a Task taken by a Cursor chat conversation (or its sub-agents) has `agent: cursor:<conversation>` (from `TRAMA_CHAT`); `editor-chat.AGENT_STOPPED`, `AGENT_INTERRUPTED` and `CONVERSATION_CLOSED` release only that conversation's Tasks and the project chat's (`agent: cursor`), and a progress declaration is accepted only from the same conversation. The `releaseTasks` and `declareProgress` holder is `cursor:<conversation>`.
- Announcements with the conversation: an announcement with `chat: cursor` may carry `conversation`, the Cursor conversation it belongs to (read and written by `src/core/announcements.ts`, absent in old files). `originFromEnv` takes it from `TRAMA_CHAT`; `trama announcement new` with `phase: scanning` takes the oldest waiting scan check of the same terminal or conversation (a conversation also takes one of the chat with no conversation and writes its own in it, never another conversation's); when the host binds a chat job to its conversation it writes `conversation` into the launch announcement if it still waits. Title synchronization keeps the field.
- Drifts of the chat have their job: in Cursor's chat `TRAMA_JOB` arrives with the `trama` commands the hook completes, so `trama drift new` and `trama comparison move <id> delivered` write `job` there too, for the Drifts of the chat and of `trama-advisor`. `trama drift list` accepts `currentJob: true`, which lists only the Drifts whose `job` equals the command's `TRAMA_JOB` (nothing, with a note and exit 0, when there is none; a usage error together with `job`) and combines with `unprepared` and the other filters. The "Async Drift Resolver" sections of `trama-scan`, `trama-implement` and `trama-import` use `{"currentJob": true, "unprepared": true}` in a terminal and in the chat alike, with no hand-read `TRAMA_JOB`, and the advisor's Drifts are prepared in the chat too.
- The Advisor Scanner now also applies to Runs sent to Cursor's chat: `configuredAdvisorScanner()` no longer requires omp, and a Run's instruction carries the chat sentence (skip the pre-flight and the targeted end-of-run scan, have the `trama-advisor` sub-agent review the code when Trama asks, tell the sub-agents) in place of the omp one; the `trama-implement` skill tells the chat agent and its sub-agents to act at once on every text that begins with `Trama's Advisor`.
- Cursor's chat sub-agents: Get Started, Update Agent Skills and the check when Trama opens now write both user definitions, `~/.cursor/agents/trama-analysis.md` and the new `~/.cursor/agents/trama-advisor.md` (the Advisor Scanner's reviewer, which ends every review with `trama advisor review`), with the current `trama.scan` (empty inherits the chat's model). The opening check rewrites either one when it differs; Cursor's hooks stay out of that check.
- Context Sharing instruction and skills: with `trama.experimentalContextSharing` on (read when a job is about to start; off, absent or not a boolean leaves every instruction exactly as before), every instruction that carries «Run at most N sub-agents at once.» (design, scans, implement, implement all, each Run of a sequence by model, Resolve Drifts, import) also carries, on the same line, right after the Async Drift Resolver sentence (or, without it, where it would be: after the limit, sub-agent, parallel execution and Drift blocker sentences, before the question and language ones), «The experimental context sharing is on: pass each sub-agent what you have already read that concerns its part, as the "Experimental context sharing" section of your skill says.», the constant `CONTEXT_SHARING_SENTENCE` in `extension/src/host/prompts.ts` added by `agentPrompt`; the command line does not read it. The skills `trama-design`, `trama-scan`, `trama-compare`, `trama-implement`, `trama-import` and `trama-resolve-drifts` have an "Experimental context sharing" section, valid only with that sentence: the main agent passes each sub-agent, of what it has already read, only what concerns its part (Trama texts quoted as they are and the places in the code already known, one line per reference), never code and never everything it gathered; the sub-agent rereads no Trama text it received, always reads the code, runs the commands that register and loads its skill as before, ignores a place that no longer matches, and reports where it found the code of what it saw, which the main agent reuses in `## Already present`. Update skills to refresh installed copies.
- `trama.experimentalContextSharing` (Experimental Context Sharing) is a checkbox in the Experimental group, after the Async Drift Resolver, off by default and application-scoped, read from the user settings only (`configuredContextSharing`). The description of `trama.maxParallelAgents` now also names the exploration of a Drift resolution. `README.md` and `extension/README.md` describe the setting.
- The `trama-resolve-drifts` skill no longer limits its exploration sub-agents to four at once: it runs at most N at once, where N is the limit in Trama's instruction («Run at most N sub-agents at once.», `20` if it gives none), with Context Sharing on or off; the prepared question follows the same limit. Update skills to refresh installed copies.
- The agent's command is now written into its terminal only when the shell is ready, so it starts whole and alone whatever the length of the instruction instead of losing its tail and its Enter and staying typed at the prompt (a line over 1024 bytes on macOS, 4096 on Linux, as happened with Run all). Ready means the terminal's shell integration is active (`terminal.shellIntegration` already present, or `onDidChangeTerminalShellIntegration` for that terminal): the line is then written once with `shellIntegration.executeCommand`; if it does not activate within 10 seconds of the terminal's creation, the line is written once with `sendText`. Nothing is written into a terminal closed meanwhile, and its work ends with `terminal.CLOSED` as for any closed terminal. The job, the announcement and the sent instant still start when the terminal opens, and neither call shows the terminal area or moves the focus.
- Resolutions from a prepared question: `proposal.md` has `prepared: true` (valid only with `kind: resolution`; `proposal new` accepts `prepared`; `proposal list`, `proposal show`, `project show`, the Snapshot and the `--json` outputs carry it). A prepared resolution no longer stops Resolve while it awaits a decision, so several can wait together. `writePreparedResolution` in `src/core` writes and hands over such a resolution from the answer, with no agent, and returns the refusal (the Draft is discarded) when it cannot.
- `trama.experimentalAsyncDriftResolver` (Experimental Async Drift Resolver) is a checkbox in the Experimental group, after the Parallel Execution, off by default and application-scoped, read from the user settings only. With it on, the instructions that may file Drifts (scans, implement, implement all, each Run of a sequence by model, import) end with the sentence «The Async Drift Resolver is on: before finishing, prepare the resolution question of every Drift filed in this job, as your skill says.», right after the Drift blocker's; Design, Resolve Drifts and setup never carry it.
- Instant Resolve: with `trama.experimentalAsyncDriftResolver` on, Resolve on a Drift with a valid prepared question launches no agent and shows no ghost: the host opens the question at once as a one-question round labelled `Prepared question` (a `prepared` job in the window, counted as resolving), and writes and hands over the resolution from the answer (`prepared: true`), or launches the resolution agent with the answer when the answer needs it or the hand-over is refused. A skipped question or a lost editor leaves the Drift open and the question prepared; resolutions awaiting a decision no longer stop such a Resolve.
- Skills of the Async Drift Resolver: `trama-resolve-drifts` has a "Prepared question" section (how a prepared question is written with `trama drift edit`, and how to work when the instruction says the developer already answered it, writing the resolution with `prepared: true`), and `trama-scan`, `trama-implement` and `trama-import` have an "Async Drift Resolver" section, valid only when the instruction says so, that makes the main agent prepare the question of each Drift of the work at the end (`trama drift list` with `job` and `unprepared`, sub-agents up to `trama.maxParallelAgents`) and report how many were prepared. `docs/cli.md` and `extension/README.md` describe the commands, fields and setting.
- Task progress: while it has taken a Task, the agent (and each sub-agent, for its own Task) declares a coarse percentage with `trama task move <id> doing` and `{ "progress": 40 }` (0 to 100, multiples of 10). It only declares: it never moves or takes the Task, and a declaration from another agent, the developer or for a Task not taken changes nothing and prints a note (exit 0). The value lives in `.trama/progress/<task id>` (local, ignored by git), is forgotten whenever the Task leaves Taken by the agent, and reaches the Snapshot and the `--json` outputs as `progress`. The Active card shows a cyan `Progress` bar and `40%`; `trama project show`, `task list` and `task show` mark the Task "(agent working, 40%)". The `trama-implement` skill tells the agent to declare it at natural milestones.
- The Drift delegation is removed: `trama.driftAutoPilot`, `trama autopilot show` and `trama autopilot move`, the automatic resolution (`automatic` and `job` on `proposal new`), the automatic Run, the coordinator's barrier, `Resolve all` and `critical` are gone, and no Drift resolves itself. Resolve on a Drift card gathers only that Drift, asks the decisions and hands over a resolution to review; the Tasks that come out of it start by hand. The end of an agent's turn releases the Proposals and Drifts it delivered or filed, so their buttons become available again.
- The quick design request is removed, with its «Quick request…» button, its one-line input box, its command and its message to the host. A design request is only the written one: **+ Add Work Item** at the foot of the Work Items column creates the empty file `.trama/requests/<id>.md` and opens it in the editor, and the Board toolbar no longer has an Add Work Item button.
- Non c'è più la corsa per i soli Task di un design: il pulsante **Run this design** e la sua azione sono rimossi, e il pre-flight, la scansione di fine corsa e i titoli non hanno più quell'ambito. **Run Ready Tasks** si chiama **Run all**, sia sul pulsante sia nei messaggi.
- La Board chiama le colonne Work Items, Ready, In progress e Done; il pulsante della barra **Run all To do** diventa **Run Ready Tasks**. In fondo a Work Items c'è solo **+ Work Item**, in fondo a Ready solo **Run all**, anche quando la colonna è vuota. I motivi del pannello dicono «No Task is Ready» e «All the Ready Tasks are blocked: …».
- Un controllo finale fallito di un Run automatico non ferma più i Task indipendenti: il Run può dichiarare, con `trama agent-event failed --task <id>` dopo il controllo fallito, il Task che ha rotto la verifica. Solo quel Task e i Task che riguardano la stessa cosa restano fermi; gli altri proseguono in una raccolta successiva. Senza un Task dichiarato, la prosecuzione automatica resta ferma come prima.
- La scheda Settings suggerisce i modelli nei tre campi dei ruoli (`trama.analysis`, `trama.scan`, `trama.execution`) con una tendina nativa dello stesso campo: per omp i modelli di `omp models --json`, per la chat di Cursor l'elenco che Cursor tiene nel suo database di stato, per la chat di Copilot i modelli messi a disposizione dell'editor. Con Claude Code, o quando l'elenco manca, il campo resta un testo semplice. Scegliere un suggerimento lo salva subito; un nome scritto a mano resta valido come prima.
- A failed final check of an automatic Run stops that Run's automatic continuation: the coordinator authorizes no further Task of that Run, so the independent ones do not start, and the unfinished ones carry the reason as `autopilot failed`. Collections started after the Run are not held.
- A Done Task keeps its short number (`T3`) while its design still has a Task in To do or In progress, and loses it together with the design's other Tasks on the first read that finds them all Done. A Done Task without a number never takes one, even when its design reopens.
- An empty written design request, and the request started by Start from Scratch, shows a grey ghost text at the start of its tab until the first character is typed: «Describe the change to design…» for a design request, «Describe the application to build…» for the setup request. The text is only on screen: the file stays empty, is never saved or sent, and a request already sent shows none.
- Specs (`.trama/specs.yaml`) is written by an approved Proposal and read by the agent from a generated `trama-specs` skill, beside the `trama-req-*` skills: its fields with entries, the reasons of the entries the agent chose itself, and the notes. The skill is regenerated when the approval, `trama skills update` or a change of `specs.yaml` runs, and removed when Specs is deleted; an invalid Specs keeps the skill as it was and says why. Its name and description count in the Requirement skills' budget.
- The Board shows the Tasks of one Proposal, when there are at least two, as one design card named after the Proposal: it stands in the column its Tasks add up to (Ready, In progress or Done), is closed until expanded to show each Task with its status dot, counts its finished Tasks (for example «2/5 done»), and has **Run this design**, which asks the agent to implement the design's Tasks still in To do. The card is dated by its latest finished Task in Done. A Task alone from its Proposal, or with no Proposal, stays a card of its own; a Task linked to a Proposal keeps the tag with that Proposal's title.
- **Trama: Initialize Project** is removed, with its command `trama.init`. A folder without a Trama project opens **Trama: Open** on Get Started, where you choose **Import from Code** or **Start from Scratch**; Start from Scratch in a folder with visible files first warns that it already contains files. The extension starts in every window once the editor has finished starting, so the status bar's «Trama» button is there even without a project, and it writes nothing to the workspace until you set a project up.
- Drift delegation is one menu, `trama.driftAutoPilot`, with `disabled` (the default), `enabled` (non-critical Drifts are delegated) and `yolo` (critical Drifts too). It is read only from your user settings. It replaces the two checkboxes `trama.autoFixDrifts` and `trama.autoFixCriticalDrifts`, which are no longer read and never rewritten.
- The panel's tabs are, in order, Board, Diagram, Requirements and Settings; it still opens on the Diagram. The design buttons «Quick request…» and «Add Work Item…» are only on the Board, and no longer on the Diagram or Requirements toolbars. With an empty Model the Diagram says so, links to the Board, and offers «Import from Code» and «Start from Scratch» beside each other.
- The agent's terminal opens as a tab in the active editor group by default (`trama.terminalLocation` defaults to `editor`); only the user value `panel` opens it in the terminal area.
- `trama.submitWhileRunning` is a checkbox, `false` by default. The former text values are read as `false` and never rewritten; `true` lets a run start while another one is in progress.
- Start from Scratch on the Diagram of an existing project with an empty Model opens the setup request at once, without the warning about the folder's visible files and without initializing anything.
- A `setup` Proposal handed over (`trama proposal submit`) while the Model has no Feature and no Actor is approved at hand-over, with the same effects as the developer's approval. When that approval refuses it (stale, requiring Proposals not approved yet, a Task that cannot be created), it stays open and the output says why. `submit` accepts `--skills-dir` like `approve`.
- **Dismiss Drift** on the panel closes an open Drift without changes and discards its attached Proposal, a Draft or a handed-over one, with no feedback. It is refused, changing nothing, while the Drift sits in an undecided resolution or while Resolve Drifts runs. `trama proposal discard` refuses a Draft attached to an open Drift, and points at the Drift.
- **Approve** and **Reject** on a Proposal wait for the end of the turn of the agent that delivered it: while that agent is still finishing its turn, both buttons on the Board and the Diagram are disabled with «The agent is still finishing», and the panel's commands refuse with a message. The wait ends when that agent's turn ends (idle, command end, terminal closed, chat ended or interrupted). `trama proposal approve` and `reject` never wait.
- The `trama-specs` skill counts in the Requirement skills' budget only while it exists: an invalid Specs adds nothing to the budget unless its skill is already written, which keeps counting it.
- The Specs tab says «This project has no Specs yet.» only when `specs.yaml` is missing. With an invalid `specs.yaml`, it shows the errors and what it can read, without claiming the project has no Specs.
- The panel's text buttons on the Board and the Diagram show a Codicons icon before their text (for example Run Ready Tasks with `play`, Resolve Drifts with `wand`, Scan with `search`, Approve with `check`, Dismiss Drift with `circle-slash`); the Done column's toggle is a chevron, and the Show details and Show tasks toggles change their chevron with their text.

## 0.0.3

- The Trama panel has a fourth tab, Settings, that lists every `trama.*` setting in groups (Agent, Models, Drift autopilot, Runs, Project) with its title and explanation, and the control that fits it. Changes are saved at once in your user settings, never in the workspace's; raising the Drift autopilot asks for confirmation first in a modal question. The tab shows a workspace value when it overrides a setting, and it follows a Trama setting changed from anywhere (the editor's settings, a settings file, the tab) at once. `trama.maxParallelAgents` is now an integer setting, a whole number of at least 1.
- The Settings tab no longer shows the technical key of a setting, neither on the page nor in its explanation; a failed save names the setting by its title, as `Trama: could not save Max Parallel Agents: <reason>.`.
- In the Settings tab each setting's explanation is no longer on the page: an «i» next to its title opens it in a bubble when hovered or focused, closed by leaving it, losing focus or Esc, and an enum's bubble lists every value with the chosen one marked `(current)`.
- A fix Task can be closed without changes when the code already does what its Drift says: `trama task move <id> done --unchanged <note>` moves it to Done with the note and its Drift to Dismissed in one step. Such a Task is marked `(no changes)` and carries a `no changes` badge with its note on the Board, and is not counted by the Scan button or scanned at the end of a run. The `trama-implement` skill checks the Drift's premise against the code before writing any code, and reports the Tasks closed without changes apart.
- Withdrawing the automatic-resolution delegation during a Run no longer marks the Tasks that had not started as failed: they stay in their column without a badge, and a Task already started finishes normally.
- In the automatic Run, a fix Task closed without changes is a success: it is not reported as failed, carries no `autopilot failed` badge, and its origin becomes runnable as after any Done fix Task; the `trama-implement` skill no longer reports it with `trama agent-event failed`.
- A failed final check of an automatic Run stops that Run's further groups: its Tasks not yet Done carry an `autopilot failed` badge with the reason, the Resolve Drifts tooltip names the failure, and `trama drift autopilot` lists it instead of showing nothing.
- A window whose project changes while a question round is still open no longer shows that round over the other project's panel: the round waits out of sight, its answers kept, and comes back when the window is on its project again; the window's other rounds wait behind it, and no answer is lost or left orphaned.
- The editor title bar shows an Open Trama icon at the right of every editor group in a window with a folder open, also without a Trama project and also while the panel is the active tab; on an unsent design request it sits to the right of Send to agent. The `Open` command is now titled `Open Trama` in the palette.
- The `trama-scan`, `trama-implement` and `trama-import` skills follow the Drift rules: Fix options reach what should happen without changing the Model or the Requirements; a Drift without Fix options comes with a Proposal when no fix of the code respects both; they read the resolved Drifts on the same references before filing and name a recurring one with `--previous`. `trama-import` files a Drift for each difference between the documentation and the code, instead of a doubt; its doubts keep only the code that looks buggy where the documentation says nothing, and behaviour it could not determine.
- `drift new --previous <id>` records the resolved Drift a new one follows, making it recurring; a Drift whose origin Task fixes another Drift follows that one by itself. Recurring Drifts are left out of the Drift autopilot in every mode.
- `drift show` of a recurring Drift has a `Follows Drift <id> <title> (<resolution>)` line under its title; `drift list` and the textual `board` mark it `(recurring)`; the Snapshot and the JSON of these commands carry `previous`.
- The Board card, the resolution rows and the Diagram details of a recurring Drift show a `recurring` badge whose tooltip and accessible name say `Recurring: follows Drift <id> – <title>`.
- `drift list --ref <ref>` (repeatable) keeps only the Drifts that concern the same thing as one of the references, with the test that decides Task blocks; combined with `--all` it shows the resolved ones too. A reference that does not resolve is a usage error.
- `drift new` with no `--option` files a Drift without Fix options, which needs `--proposal` (its Draft fixes the Model or the Requirements); without it the filing is refused. One or more than five options are still refused.
- An approval no longer starts a scan of the Features it touched, from the panel, from the command line or through a Drift: the `trama.autoScan` setting and the «Scan now» notice are removed. A leftover `trama.autoScan` value is ignored and not rewritten; manual scans are unchanged.
- A Proposal's scan scope is computed from the Model and Requirements whenever it is needed (validation, hand-over, approval and `proposal show`) and is no longer saved at approval; the `## Scan scope` of an open Proposal is always current. Approved Proposals that saved one keep it as history.
- Registrations on one Proposal (`proposal edit`, `proposal delete`, `proposal resolve-drift`, and the Task files written inside a Proposal) run one after the other under a lock per Proposal, so sub-agents writing at the same time no longer lose each other's files or recorded bases. The lock is a file in `proposals/.locks/`, kept out of Git; a lock older than 30 seconds is taken as left by a dead process.

## 0.0.2

- Windows (win32-x64) is packaged and smoke-tested by the release workflow, and a manual run can release a single platform. Windows is untested: its test suite has known failures and nobody has tried the package by hand.
- On Windows, Copilot's hook file carries the PowerShell form `& "<trama.exe>" copilot-hook` in `windows` next to `command`, and Cursor's `hooks.json` uses `& "<trama.exe>" cursor-hook`. Update skills replaces Trama's entries in either form instead of adding new ones. The Cursor form has not been tried on Cursor.
- `trama validate` refuses Windows device names (`con`, `prn`, `aux`, `nul`, `com1` to `com9`, `lpt1` to `lpt9`) as Feature, Machine and Actor IDs and as Area and fragment names on every platform, so a project opens on Windows too. Names that only contain one of them stay valid.
- Proposal hashes and comparisons read the Model and Requirement files with LF line endings: a CRLF checkout (`core.autocrlf`) no longer makes a Proposal stale, and its shown changes, touched files and scan scope match a Linux checkout.

## 0.0.1

- First public release, under the GNU AGPL v3 (`AGPL-3.0-only`); the `.vsix` now ships the license text. Earlier tags and releases are gone, and versions restart from 0.0.1.
- The automatic Run no longer carries a fixed list of Task identities from its launch: before each group it reads the authorized Tasks from `trama drift autopilot --json`, so an origin Task whose fix Tasks became Done during the Run is picked up, and nothing outside the authorization is started.
- When the Drift autopilot leaves `disabled`, the window that coordinates the project imports the jobs the other editor windows still run, before it judges the barrier: a Run, scan or Resolve Drifts started in another window during `disabled` is no longer unknown to the coordinator that already held the role.
- The Drift autopilot grants no new automatic step while a live editor window does not answer the project coordinator's jobs request in time: one answering window is no longer enough. The status shows that reason, and the coordinator keeps its role meanwhile.
- With the Drift autopilot `disabled`, a window no longer shares its jobs or send reservations with the other editor windows of the project: another window's Run, scan or Resolve Drifts no longer makes Resolve Drifts or the Run buttons unavailable here, and a send no longer waits behind another window's send. Sharing starts when the autopilot is enabled.
- The Scan button's count restarts when the System scan's instruction is delivered (written to the terminal, sent to the chat, left ready in the chat or copied to the clipboard), not when its check finishes: a scan that fails, is interrupted or has its check withdrawn no longer leaves the count up, and the editor no longer tracks scan launches in memory.
- An agent terminal that went idle or whose command ended is no longer followed: a later idle signal, command end or close of that terminal no longer releases the Tasks the resumed agent took or withdraws its announcements.
- An agent terminal's instruction stays one line: the job ID is no longer written into it. The commands that take `--job` (`announce check`, `proposal new --automatic --resolution`, `drift autopilot`, `agent-event failed`) read the terminal's job from `TRAMA_JOB` when `--job` is absent; a chat job still gets its ID in the text.
- A Drift whose question was skipped in one editor window stays out of automatic resolution in every window: the skip, the later answer and a developer scan are forwarded to the project coordinator.
- An automatic resolution whose approval is refused now fails only the Drifts the refusal names (or whose decision no longer applies); the other Drifts stay open in the Proposal for the developer.
- Rejecting or discarding an automatic resolution no longer marks its undecided Drifts as failed; they stay open, unmarked, for the developer's own decision.
- Add coordinated Drift autopilot modes (`disabled`, `enabled`, `yolo`) with cross-window scan/Run barriers, host-only approval, job-scoped authorization and implementation Runs.
- Resolve Drifts pressed in a window that does not coordinate the project now asks the coordinator, over the local channel, to resume automatic resolution; until a coordinator resumes, that window says why the automatic part waits.
- Autopilot leaves out of automatic resolution a Drift whose Model elements no longer exist, so it stays for the developer instead of failing in the resolution agent.
- Resolve Drifts no longer clears failed automatic cases: a Drift whose automatic fix failed or was excluded gets manual questions on a click, even with full delegation.
- A refused automatic start (mode, barrier or Drift changed at the last moment) releases its reservation and records no failure; its Drifts or Tasks stay eligible for the next cycle.
- Track critical Drifts and failed check outcomes; expose automatic resolution status and critical markers in the CLI and Board.
- Autopilot: a failed or interrupted scan no longer suspends the delegation; it counts as finished.
- Autopilot status reports the last failed or interrupted scan as information; it changes no phase.
- A finished check's outcome reaches the editor over the local channel instead of a marker file, so the System scan memory and the autopilot no longer race for it.
- Add `trama.submitWhileRunning` (`disabled` by default): while a Trama run is in progress, the Run buttons are disabled and launches are refused with "A run is in progress"; `enabled` allows Runs during a run.
- Make the Board's Done column collapsible; it starts collapsed each time the panel opens.
