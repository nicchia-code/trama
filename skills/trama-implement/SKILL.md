# Trama: implement

You implement one **Task** so that the code behaves as the **Model** says and is built as the **Requirements** say. The Model wins. If following it or a Requirement is impossible, or you discover it is wrong or incomplete in an important way, you **stop working on that Task** and file a **Drift**: you never silently deviate and you never edit the Model or the Requirements. The Drift blocks the Task and the other Tasks that concern the same thing. Asked for one named Task, you stop there and take no other. Asked for several Tasks (every Task in "todo"), you hand them out as sub-agent places free up and go on: the Drift leaves its Task in `doing`, and `trama task next --batch` skips the Tasks it blocks.

## Hand-over

A new Proposal starts as a **Draft**, not approvable. Finish every file, then run `trama proposal submit <id>` without `validate --proposal` or `proposal show` before it: read the changes in the submission's output. If they do not match what you meant, reopen the Proposal with `trama proposal edit <id>`, fix the files, and submit again. If submission is refused, fix the reported problems and submit again. Only after it succeeds tell the developer to review it. A Proposal meant for a Drift is attached to that Drift when the Drift is filed, before it is handed over, so it never shows up alone. Before every later file change, call `trama proposal edit` again: it returns an open Proposal to Draft, so submit again when finished.

## Announcing cards

When you know you must file a Drift (see "When you must file a Drift"), announce it before you write it up: `trama announce drift "<title>"` prints an announcement ID. Pass it when you file the Drift: `trama drift new … --announcement <id>`; if the Drift carries a Proposal, announce only the Drift and pass the same ID to `trama proposal new … --announcement <id>` too. The end-of-run scan (step 7) announces its cards as `trama-scan` says. A sub-agent announces the cards it files exactly as you do. The Board shows a ghost of each card meanwhile. Never wait for a ghost to show and never skip or delay a card because of it; an unknown ID is only noted in the output.

## Announcing the check

Once the run has moved at least one Task to Done, announce its **check** right after the last Task, before step 6: `trama announce check "<title>" --phase verifying` prints its ID. The title says the work, in English: `Final check after Task <short number>` for a Task asked by name, `Final check after all Tasks` for every Task in "todo". If step 7 finds a non-empty scope to scan, run `trama announce phase <id> scanning` when that scan starts and use this check; that end-of-Run scan covers only the completed Tasks' scope, never the whole System, as step 7 says. Otherwise keep the check open for step 8. Close the check after step 8 and before the report in every case: `trama announce done <id>` when it succeeded, and `trama announce done <id> --failed` when the check of step 6 fails and you cannot fix it, when the scan of step 7 fails or stops, or when the Run stops before its check is over. A sub-agent never announces a check. Never wait for the ghost to show; an unknown ID is only noted in the output.

## Hard rules

- NEVER edit `.trama/model/`, `.trama/requirements/` or the generated `trama-req-*` skills.
- Agents may approve or reject a Proposal, discard a Draft or resolve a Drift only when the developer explicitly asks for that decision in the conversation. Without that request, do not decide and do not ask the developer about it: stop and tell them the decision is theirs, on the Board. A request to design, implement Tasks or prepare a Drift resolution does not by itself authorize deciding it.
- Every question to the developer goes through `trama ask`, as the "Asking" section of `trama-design` says: never with your own question tool, and never as a round written in the conversation.
- NEVER implement behaviour that contradicts the Model, or code that contradicts a Requirement, to get something working.
- Do not touch code unrelated to the Task.

## Naming cards

Every live Proposal, Task and Drift has a temporary **short number** (`P3`, `T3`, `D3`) besides its **permanent identity** of eight characters.

- Name cards to the developer by short number and title, for example "Task T3 – title" or "Drift D2 – title", also in the final report. A closed card (for example a Task in Done) has no number: use its permanent identity.
- In every command you run and every file you write (`trama task move`, `--task`, `--proposal`, the body of a Proposal) use **only the permanent identity**, taken from `--json` (field `id`; the number is the field `number`) or from the file name. **Never write a short number in a file**: it changes from one working copy to another.
- Give every card you create, and its announcement, a **short title**: at most five words, about 40 characters, a name for the card rather than a sentence describing the work (for example "Testo fantasma" instead of "Descrivere Start from Scratch e guidare le richieste scritte con un testo fantasma"). Put the detail in the body, even when the title loses information. No command checks the length of a title. Titles that Trama or a skill composes from another title stay as they are: `Fix code to match the …`, `Import: <Feature>`, the titles of checks.

## Language

When the instruction asks you to write in a language, everything you generate for Trama that the developer reads goes in that language: the bodies, descriptions and introductions of Proposals, Model files, Requirements, Tasks and Drifts; the titles of Proposals, Tasks, Drifts, Areas and Requirement fragments, and of announcements; the names of the System, Features, Machines, Actors and States; new identifiers (IDs of Features, Machines and Actors, Event names), transliterated into the allowed ASCII letters (`città` → `citta`, an Event `PAGAMENTO_RIUSCITO`); the text of questions and their options, and your replies in the conversation. Without a language in the instruction, nothing here changes.

- **Always in English**, whatever the language: technical terms are never translated: commands and tools (`git pull`, `npm install`), names of products, services, libraries and languages, and Trama's own terms (Proposal, Task, Drift, Board, Run, Scan). Also always English: code and its comments, commit messages, the project's own documentation; the headers Trama reads in files ("States", "Events", "General", "What happens", "What should happen", "Where in the code", "Fix options", "Already present"), the `(initial)` and `(final)` markers, the keys of Specs and the front matter fields. Trama's interface (panel, editor, command line) stays in English.
- **A language changes nothing already written.** When you edit a file written in another language, keep its existing text and write only the new or rewritten text in the chosen language; never translate the whole file.

## Steps

**Pre-flight, before the first Task.** Every Run starts with a pre-flight, before it asks for the first Tasks and before any code is read. Announce its check with `trama announce check "<title>" --phase scanning` and keep its ID. The title says the work, in English: `Pre-flight before Task <short number>` for a Task asked by name, `Pre-flight before all Tasks` for every Task in "todo", and `Pre-flight before automatic fixes` for the automatic Run.

Then run `trama task scope --pre-flight` with the filters of the Run: `--proposal <id>` or `--not-proposal <id>`, repeated, as the instruction gives them; or repeated `--task <id>` for a named Task or for the authorized Tasks of an automatic Run; or no filter for every Task in "todo". It prints the exact references of the runnable Tasks (the ones `trama task next` would choose, blocked Tasks excluded), each once: a Requirement section counts as the element it is about, and no Transition, General section or Area is added. A reference is already compared when a recorded comparison covers it with the same code and the same text: such references are left out of the list and printed under `## Already compared`, and they are not compared again. With `--json` it gives the list of `{ ref }` and the Tasks' identities, plus `alreadyCompared` with the references already compared. If no reference remains to compare (the list is empty, or every reference is already compared), the pre-flight is done. Otherwise compare the Machines among the remaining references (never those under `## Already compared`) following `trama-compare`, once: with a single Machine among them, do it yourself, running `trama compare brief <machine> --ref <ref>…` on its references; with more than one Machine, give each Machine to its own sub-agent, all at once, up to the maximum number of sub-agents the instruction allows (20 when it gives no limit), in whatever way your agent starts sub-agents, and wait for all of them, the slowest included. References that belong to no Machine (an Actor, a Feature, a Requirement section with no element) stay with the Run's agent. Tell each sub-agent that this is the pre-flight of a Run and to compare only its Machine's references: file only Drifts with no origin (no `--task`), and never to file a Task, announce a check or run `trama task next`.

**Proposal filters.** When the instruction names Proposals with `--proposal <id>` (only the Tasks of those Proposals) or `--not-proposal <id>` (every Task but theirs, the ones with no Proposal included), pass those filters exactly as the instruction gives them, repeated, to this pre-flight command and to every `trama task next --batch` call of the Run, and add no other Proposal filter.

A difference that is the work of a Task about to start is not a Drift: do not file it. A Drift the pre-flight finds blocks the Tasks that concern the same element, and the Run goes on with the others. Close the check when the pre-flight is over: `trama announce done <id>` when it succeeded, and `trama announce done <id> --failed` when it failed or stopped. A failed or stopped pre-flight does not stop the Run: write the line `Pre-flight scan failed: the Run continues without it.`, repeat it in the report, and go on with the first Tasks. The pre-flight announces no card by hand and no second check: each Machine comparison is announced by its `trama compare brief`, and its cards are filed by one `trama compare file`.

1. **Pick the Task.** Asked for one named Task, use the ID you were given, and do steps 2 to 5 for it. For automatic Runs, use only the identities currently authorized by `trama drift autopilot --json`: pass them as repeated `--task <id>` filters to every `trama task next --batch` call, and recheck that authorization before starting each Task. Include an origin Task only after its required fix Tasks are Done; if no authorized Task is runnable, do not fall back to the general queue. Asked for several ordinary Tasks, ask `trama task next --batch --max <N>` for up to <N> Tasks: <N> is the number of sub-agents the instruction allows, or 1 without sub-agents (with the Run's `--proposal` or `--not-proposal` filters, if the instruction gives any). It prints one Task per line, short number and title (with `--json`, the list `batch`, each with `id` and `number`): up to <N> runnable Tasks that do not concern the same thing, and none that concerns a Task In progress the agent has taken, the first being the next runnable Task. `--max` is the maximum number of sub-agents the instruction allows, an integer of 1 or more; 20 when the instruction gives no limit. It skips the blocked Tasks, moves nothing, and recomputes the answer each time, so a Task that waited for the Task fixing its Drift comes back, after it, once that Task is Done.
   - **With sub-agents**: start one sub-agent for each free place, up to <N> at once, in whatever way your agent starts sub-agents, and give each one a Task from the batch. Tell each one the Task's permanent identity and to do steps 2 to 5 of this skill for that Task only: move it to `doing`, read it once with `trama task show <id>`, check its premise (step 3), implement it and run only its own tests, then move it to `done`, close it without changes as step 3 says, or file a Drift as described below, announcing it, and leave the Task in `doing`. Tell it never to run `trama task next`, never to take another Task, never to run the full suite, the linter or the build, and never to scan; it comes back with the Task done, closed without changes with its note, or the Drift it filed. If two sub-agents change the same file, each changes only the parts of its own Task; the final check finds conflicts. Each time a sub-agent comes back, its place is free: step 5 says what to do next.
   - **Without sub-agents**, or with one place only: do steps 2 to 5 yourself for each Task, one after the other, asking `trama task next --batch --max 1` (with the same `--proposal` or `--not-proposal` filters, if any) before each Task.

   Read a Task once, with `trama task show <id>`. That text is the Model and the Requirements for this Task. A Machine reference includes the State tree and the Events with who receives them. A State reference includes the outgoing Transitions, including those inherited from the States that contain it, marked as inherited. An Event reference includes the Transitions that react to it. A reference to a whole Area includes the text of every section. Under `## Requirements` are the Requirements attached to the referenced elements, and every General section that has text, written in full. A Technical Task references no Model element; implement it as a normal engineering task from the Requirements in that text.
2. **Start it.** `trama task move <id> doing`. If the move is refused because the Task is blocked, nothing changed. Asked for one named Task: stop, take no other Task, and report the Task and the Drift (or fix Task) the refusal names; only the developer can decide on that Drift. In a run over several Tasks `trama task next --batch` never names a blocked Task, so a refusal means something changed since you asked: leave that Task and go on with the other Tasks you were given.
3. **Read the code.** The Model and the Requirements for this Task are the `trama task show` text already read. Read the code that implements them and follow its conventions. For this Task, do not run `trama state`, `trama event`, `trama paths`, `trama machine` or `trama requirements`, and do not open a `trama-req-*` skill. If a Transition the Task must implement does not appear in that text, run one command for that Transition, `trama state` or `trama event`, and do not resume the tour.

   **Check the premise first, for a fix Task.** A Task that fixes a Drift says so on its Column line (`from Drift <id>`), and its text carries the Drift's two sides and its Where in the code. Before writing any code, re-read the code at Where in the code and at the Task's references, and compare what it does with What happens. If it already does what What should happen says (the Model or the Requirement), change nothing: run `trama task move <id> done --unchanged "<note>"`, the note saying what you checked (the code and the behaviour); this also dismisses the Drift. Then skip step 4 and step 7 for that Task, and list it in the report's closed-without-changes list. Otherwise continue with step 4. A Task with no Drift skips this check.
4. **Implement.** Write the code, including every Transition's condition and consequence exactly as the prose in the Task text says, and the States around it that the Task depends on. Follow every Requirement in that text, including the General sections written there. Add or update tests for the behaviour. While writing, run the tests added or changed for this Task and the existing tests of the behaviour this Task changes. Do not run the project's full suite, the linter or the build after the Task. After the code, do not read the Model again.
5. **Finish the Task.** `trama task move <id> done`. Record the permanent ID of each Task this run moves to Done without `--unchanged`; the scan of step 7 takes its scope only from those. In a run over several Tasks, each time a sub-agent (or you, without sub-agents) finishes its Task (Done, closed without changes, or stopped by a Drift), ask `trama task next --batch --max <free places>` (with the same `--proposal` or `--not-proposal` filters, if any), where the free places are <N> minus the sub-agents still working, and start the Tasks it prints at once, from step 1. When no sub-agent works and none has been received, ask `trama task next --batch --max <N>` once more: if it says no Task is runnable, the Tasks are finished and the run goes on to step 6.
6. **Check the run.** A Task asked by name is its own run, so this step follows it at once. In a run over several Tasks, this step runs once, after the last Task, when no sub-agent works, none is received and `trama task next --batch --max <N>` (with the same `--proposal` or `--not-proposal` filters, if any) says no Task is runnable; never in a sub-agent. Run the project's tests, linter and build once. If that check fails, fix the code and run it again, without reading the Model again; leave every Task in the column it is in. If you can tell which Task broke the check in an automatic Run, complete the check as failed (`trama announce done <check-id> --failed`, when one was announced), then report that Task with `trama agent-event failed --job <id> --task <task-id> --reason "<text>"`: the other authorized Tasks still go on. If you cannot tell which Task broke the check, say so in the report and stop, without another reading tour and without step 7.
7. **Scan the completed Tasks' scope.** Only when the check of step 6 passed, the run moved at least one Task to Done without `--unchanged`, and no Task of its scope is blocked at the end (`blockedBy` in `trama task list --json`; the scope is every Task in "todo" for a run over several Tasks, that Task for a Task asked by name). Run `trama task scope <id> [<id>…]` with the permanent IDs of the Tasks this run moved to Done without `--unchanged`. If the scope is empty, do not scan; go on to step 8 with the check open. Otherwise, follow the steps of `trama-scan` on exactly the references in this `## Scan scope`, in this same run, comparing each Machine with `trama-compare` on its references (`--ref`); do not expand it to the whole System or a whole Feature. Link the Tasks the scan files to a design with `--proposal <id>` only when this run is a single Task asked by name that belongs to a design (`proposal` in `trama task show <id> --json`); otherwise link none. Do not implement the Tasks this scan files.
8. **Write History.** Run this step after step 7, or after step 6 when step 7 does not run, whenever the run moved at least one Task to Done without `--unchanged`, also when the check of step 6 failed. Pass control to History with `trama announce phase <id> history` (on the check of this run). Read the entries with `trama history list --json`, and `trama history show <id> --json` for those that look related. Group the Tasks of this run by macro-feature, reading their titles, bodies, their Proposals (`trama task show <id> --json`) and the entries already written: when an entry already tells the same feature, update it with `trama history update <id> --task <id>` (it may also change title, `--summary` and `--body`; it only adds Tasks, never removes one) instead of writing another; otherwise write a new one with `trama history add "<title>" --summary "<text>" --body "<text>" --task <id>`, repeating `--task` for every Task it names. Name every Task this run moved to Done without `--unchanged` at least once, by its permanent ID; a Task closed without changes is never named. Write title, summary and body in the language the instruction asks for; the title is one line, the summary one line of at most 280 characters. A refused command changes nothing and names each problem: fix it and run it again. Only this skill writes entries after a run: a sub-agent never writes them, and a run interrupted before this step writes none. Then close the check as the "Announcing the check" section says, and go on to the report.
9. **Report.** Say what you implemented, in domain terms, the Drifts you filed (each with its Task), anything you noticed that was outside the Tasks, the Tasks closed without changes, each with its note in a list of its own, the Tasks still in "todo" left unrun, each with the Drift or the fix Task that blocks it, as the last `trama task next --batch` lists them, the references the pre-flight found already compared (`## Already compared`), the Tasks and Drifts the scan of step 7 filed, and the History entries you wrote or updated, each by its title.

## When you must file a Drift

Stop working on the Task at once and file a Drift when any of these is true:

- The Model cannot be implemented as written (contradiction, impossible condition, an Event nothing can emit).
- The Model is silent on a case that the Task forces you to handle, and the choice changes what the user sees or what data is kept.
- Doing the Task right requires a State or Transition the Model does not have.
- A Requirement cannot be followed (it conflicts with the Model, another Requirement, or the platform), or the Task forces a construction choice the Requirements should decide and do not.

Before running `trama drift new`, re-read the code at the place you name in `--where` and file only if it really does what `--happens` says. A resolved Drift counts as closing a difference when it was fixed in the code, its Proposal was accepted, or the developer dismissed it by decision; a Drift dismissed by its own fix Task (closed without changes) does not, so a difference that comes back is filed again.

Then:

1. Decide which case applies. If the code is right and the Model forgot a case, begin a Proposal with the `trama-design` skill, without its interview (list your choices in the Proposal body): `trama proposal new … --announcement <id of the Drift's announcement>`. Finish its files, but do not submit it yet: attach the Draft to the Drift in step 2, then submit it right after; if the submission is refused, correct it and submit again. Otherwise there is no Proposal, except in the case of step 2 where no fix respects both the Model and the Requirements.
2. File the Drift **once**: `trama drift new "<title>" --ref <nearest Model element or Requirement> --task <id of the Task you are implementing> --happens "<what the code does or what you would do instead, in terms of behaviour>" --should "<what the Model or Requirement says and why it cannot be followed>" --option "<title of the way you recommend>" --option-text "<what it changes and costs>" --option "<title of another way>" --option-text "<…>" [up to five] --where "<where in the code>" [--critical when a developer decision is urgently needed]`, adding `--proposal <id of the Draft>` only in the first case, and `--announcement <id>`. Set `--critical` only when the developer urgently needs to take a position on this case; technical severity or complexity alone does not qualify. Otherwise omit it. The two texts, the options and `--where` are required; `--where` is the only place for code locations. Write them as described in "Writing a Drift". `--task` records the origin: the Drift blocks that Task and Tasks that concern the same thing.
   Give the Drift a short title (see Naming cards).
   - **Resolved Drifts first.** Before filing, run `trama drift list --all --ref <ref>` for the references of the difference. A difference that a resolved Drift closed stays closed while the Model or the Requirement there still says the same thing: do not file it again. If it is back after a fix of the code or an adaptation of the Model, pass `--previous <id>` of that resolved Drift; the command refuses a previous Drift that is open, dismissed or unknown. When `--task` names a fix Task (one whose `drift` field is set), Trama writes `previous` itself, so `--previous` is not needed.
   - **No fix respects both.** When no fix of the code respects the Model and the Requirements together (for example, two Requirements contradict each other), file the Drift with no `--option`, with `--proposal` of the Draft that repairs the Model or the Requirements, as in step 1. A Drift without Fix options is refused without a Proposal.
3. Leave the Task in `doing`; the developer decides whether the code or the Model changes. Asked for one named Task, stop here. In a run over several Tasks, go on with the free places as step 5 says: ask `trama task next --batch` for the next Tasks. The Drift blocks only the Task it was filed for and the Tasks that concern the same thing, and `trama task next --batch` skips those.
4. Report. Say what you implemented and the Drift you filed, with the Task it concerns. In a run over several Tasks this goes into the final report described in step 9 of the steps above, once `trama task next --batch` says no Task is runnable. A sub-agent reports to the main agent instead, which writes the one final report.

Small choices that stay below Diagram level and that no Requirement covers (names, data structures, how an effect is carried out) are yours to make; do not file Drifts for them.

## Writing a Drift

The developer reads a Drift at a glance, as a programmer, but not as a code review. Write the two sides, and the fix options, at the level of behaviour.

- **Say what the System does and what it should do**, in the words of the domain ("the cart total ignores the coupon"), not how the code does it.
- **Name no variable, function, class, field or file** in `--happens`, `--should` or the options, unless the difference cannot be understood without it. Then name only the one or two that matter, as `inline code`.
- **Code locations go only in `--where`**, which is required for every Drift: the files, and the code element when it helps. No line numbers, which go stale, and no long pieces of code.
- **Give two to five fix options**, the one you recommend first: each `--option "<title>"` is followed by its `--option-text "<text>"`. Each is a different way to reach what should happen, not a step of one plan, and says in terms of behaviour what changes and what it costs. About 60 words each, short Markdown, no headings or tables inside an option. Titles differ. A Drift filed with fewer than two, more than five, or an option missing its title or text is refused.
- **Fix options reach what should happen** without changing the Model or any Requirement, and respect every Requirement that applies to the elements of the Drift, not only those it names. An option that asks for an exception to, or a change of, the Model or a Requirement is not a fix option: that way goes to a Drift with a Proposal.
- **Use short Markdown:** short paragraphs, a bulleted list when there are several separate points, **bold** for the one or two terms that carry the difference. No headings inside a section, no tables, about 100 words per side.

## Experimental Drift blocker

This section applies only when the instruction says "The experimental Drift blocker is on". Without that sentence, never name a Task in `--not-blocking`, and skip this section.

When it applies, do this before each `trama drift new`:

1. Ask for the candidates with the references and origin you will file with: `trama drift candidates --ref <ref>… [--task <origin>]`. It lists the Tasks that Drift would block, the origin included, and writes nothing. If it lists none, file the Drift as usual. A Drift that a Machine's comparison files gets its candidates from `trama compare brief <machine> --candidates` instead, as `trama-compare` describes.
2. Judge each candidate: does the difference you found touch that Task, its references or what it changes? Leave free only the Tasks the difference does not touch, with a one-line reason for each, in Italian. Judging only removes blocks: never leave free a Task the difference touches, and never name a Task the command did not list.
3. Pass each Task you leave free as `--not-blocking <permanent ID>` followed by `--not-blocking-reason "<reason>"`, in the same order: they pair the way `--option` and `--option-text` do. Pass none when the difference touches every candidate.

The judgement is made once, at filing: a Drift keeps the Tasks it leaves free and blocks every other one, including the Tasks created later about the same thing.

When you start sub-agents, pass them the sentence "The experimental Drift blocker is on" together with this section, and ask each one to report the permanent IDs of the Drifts it registered and, for each, whether it blocks any Task.

### Final resolution of the Drifts that block nothing

Keep the permanent ID of each Drift you file that blocks no Task: it blocks none when every candidate was left free, or when there was no candidate. Sub-agents report the same, as above.

When the work is over (after the final check and the end-of-Run scan, if there is one), gather those Drifts into one resolution, unless none is left:

1. Leave out a Drift that is critical or recurring (it follows an earlier Drift). Read the delegation with `trama drift autopilot --json`: if its `status` is `unavailable`, its `mode` is `disabled`, or it cannot be read, the delegation is off; otherwise leave out each non-critical, non-recurring Drift that has a Fix option, because the delegation resolves it on its own. A Drift left out stays open.
2. For each remaining Drift, record the recommended decision: when it has an attached Proposal, `proposal`, and the resolution carries that Proposal's changes as the trama-resolve-drifts skill describes; otherwise `fix-code` with option 1.
3. Announce it with `trama announce proposal "<title>"`, write it with `trama proposal new "<title>" --resolution --non-blocking --announcement <id> --body "<what is resolved and why>"`, and record each decision with `trama proposal resolve-drift <proposal id> <drift id> --decision <decision> [--option 1]`. Hand it over with `trama proposal submit <id>` and read its output, without `trama validate --proposal` or `trama proposal show` before it.

Never approve or reject this resolution, and never start a Run because of it: the developer decides it, as any manual resolution.

## Automatic Drift-resolution Runs

An automatic Run is limited to its explicitly delegated Task identities. Query `trama drift autopilot --job <id> --json` for the current authorization; use only its authorized Task IDs, including fix Tasks from this resolution and origin Tasks that are still not Done. Pass each as a repeated `--task <id>` to every `trama task next --batch --max <N>` call. Never fall back to the ordinary queue.

Recheck the coordinator before starting the Run and again before starting each Task. Keep only IDs still authorized then; if authorization is unavailable, unknown, disabled, or no IDs remain, do not start new work. Before starting each Task, ensure its origin Drift is still authorized. Tasks that fail remain reported and are excluded from later selection; report failures with `trama agent-event failed --job <id> --task <task-id> --reason "<text>"`. Do not retry them. A fix Task closed without changes (`trama task move <id> done --unchanged "<note>"`, because the code already does what the Model says) is a success, not a failure: do not report it with `trama agent-event failed`; its origin becomes runnable as after any Done fix Task, and the Run goes on. An in-progress Task may finish if the setting changes, but do not start further unauthorized Tasks.

The Run is separate from the resolution agent: do not reuse its terminal or implement during resolution preparation. Keep the normal Run checks and selective end-of-Run scan. That scan belongs to this Run's existing check; do not announce a second check.

`trama.driftAutoPilot` is the application-scoped user setting for Drift delegation, `disabled` by default, with the values `disabled` (manual), `enabled` (non-critical Drifts only) and `yolo` (also critical Drifts). Only the user value counts; re-read it with `trama drift autopilot --json`. The host can stop further automatic steps if it changes. Repeated automatic cycles have no additional time, cost, or cycle limit; the developer can set `trama.driftAutoPilot` back to `disabled` or interrupt the work. External agent scans are not part of Trama's coordination barrier.

## PowerShell

The examples use POSIX syntax. In PowerShell, pass JSON on standard input with a pipe, for example `Get-Content -Raw round.json | trama ask --root <project>`, not `<`. On Windows PowerShell 5.1, set `$OutputEncoding` and `[Console]::OutputEncoding` to UTF-8 first, or non-ASCII characters arrive as `?`. Write `--body` and `--reason` values in single quotes, because PowerShell expands `$` and the backtick inside double quotes.
