# Trama: implement

You implement one **Task** so that the code behaves as the **Model** says and is built as the **Requirements** say. The Model wins. If following it or a Requirement is impossible, or you discover it is wrong or incomplete in an important way, you **stop working on that Task** and file a **Drift**: you never silently deviate and you never edit the Model or the Requirements. The Drift blocks the Task and the other Tasks that concern the same thing. Asked for one named Task, you stop there and take no other. Asked for several Tasks (every Task in "todo", or every Task of a design), you take them in groups and go on: the Drift leaves its Task in `doing`, and `trama task next --batch` skips the Tasks it blocks.

## Hand-over

A new Proposal starts as a **Draft**, not approvable. Finish every file, validate and read the changes before `trama proposal submit <id>`. If submission is refused, fix the reported problems, validate and review again, then retry. Only after it succeeds tell the developer to review it. A Proposal meant for a Drift is attached to that Drift when the Drift is filed, before it is handed over, so it never shows up alone. Before every later file change, call `trama proposal edit` again: it returns an open Proposal to Draft, so submit again when finished.

## Announcing cards

When you know you must file a Drift (see "When you must file a Drift"), announce it before you write it up: `trama announce drift "<title>"` prints an announcement ID. Pass it when you file the Drift: `trama drift new … --announcement <id>`; if the Drift carries a Proposal, announce only the Drift and pass the same ID to `trama proposal new … --announcement <id>` too. In the scan of the whole System at the end of a run (step 7), announce each Task and each Drift the same way, with `trama announce task "<title>"` and `trama task new … --announcement <id>`. A sub-agent announces the cards it files exactly as you do. The Board shows a ghost of each card meanwhile. Never wait for a ghost to show and never skip or delay a card because of it; an unknown ID is only noted in the output.

## Announcing the check

Once the run has moved at least one Task to Done, announce its **check** right after the last Task, before step 6: `trama announce check "<title>" --phase verifying` prints its ID. The title says the work, in English: `Final check of <Proposal title>` for the Tasks of a design, `Final check after Task <short number>` for a Task asked by name, `Final check after all Tasks` for every Task in "todo". If step 7 finds a non-empty scope to scan, run `trama announce phase <id> scanning` when that scan starts and use this check; that end-of-Run scan covers only the completed Tasks' scope, never the whole System, as step 7 says. Otherwise run `trama announce done <id>` after step 6. Close the check before the report in every case: `trama announce done <id>` when it succeeded, and `trama announce done <id> --failed` when the check of step 6 fails and you cannot fix it, when the scan of step 7 fails or stops, or when the Run stops before its check is over. A sub-agent never announces a check. Never wait for the ghost to show; an unknown ID is only noted in the output.

## Hard rules

- NEVER edit `.trama/model/`, `.trama/requirements/` or the generated `trama-req-*` skills.
- Agent can approve or reject a Proposal, discard a Draft or resolve a Drift only when the developer explicitly asks for that decision in the conversation. Without that request, stop and ask the developer to decide. A request to design, implement Tasks or prepare a Drift resolution does not by itself authorize deciding it.
- NEVER implement behaviour that contradicts the Model, or code that contradicts a Requirement, to get something working.
- Do not touch code unrelated to the Task.

## Naming cards

Every live Proposal, Task and Drift has a temporary **short number** (`P3`, `T3`, `D3`) besides its **permanent identity** of eight characters.

- Name cards to the developer by short number and title, for example "Task T3 – title" or "Drift D2 – title", also in the final report. A closed card (for example a Task in Done) has no number: use its permanent identity.
- In every command you run and every file you write (`trama task move`, `--task`, `--proposal`, the body of a Proposal) use **only the permanent identity**, taken from `--json` (field `id`; the number is the field `number`) or from the file name. **Never write a short number in a file**: it changes from one working copy to another.

## Language

When the instruction asks you to write in a language, only the prose you produce for Trama goes in that language: the bodies, descriptions and introductions of Proposals, Model files, Requirements, Tasks and Drifts, the text of questions and their options, and your replies in the conversation. Without a language in the instruction, nothing here changes.

- **Always in English**, whatever the language: code and its comments, commit messages and the project's own documentation; the names and titles of Model elements, Requirements, Proposals, Tasks and Drifts; IDs, Event names, the section titles Trama requires (for example "General", "What happens", "What should happen", "Where in the code") and the `(initial)` and `(final)` markers.
- **A language changes nothing already written.** When you edit a file written in another language, keep its existing text and write only the new or rewritten text in the chosen language; never translate the whole file.

## Steps

1. **Pick the Task.** Asked for one named Task, use the ID you were given, and do steps 2 to 5 for it. For automatic Runs, use only the identities currently authorized by `trama drift autopilot --json`: pass them as repeated `--task <id>` filters to every `trama task next --batch` call, and recheck that authorization before starting each group. Include an origin Task only after its required fix Tasks are Done; if no authorized Task is runnable, do not fall back to the general queue. Asked for several ordinary Tasks, take them from `trama task next --batch --max <N>` (with `--proposal <id>` when asked for a design). It prints one Task per line, short number and title (with `--json`, the list `batch`, each with `id` and `number`): up to <N> runnable Tasks that do not concern the same thing, the first being the next runnable Task. `--max` is the maximum number of sub-agents the instruction allows, an integer of 1 or more; 20 when the instruction gives no limit. It skips the blocked Tasks, moves nothing, and recomputes the answer each time, so a Task that waited for the Task fixing its Drift comes back, after it, once that Task is Done…
   - **With sub-agents**, and a group of two or more: give each Task of the group to its own sub-agent, up to <N> at once, in whatever way your agent starts sub-agents. Tell each one the Task's permanent identity and to do steps 2 to 5 of this skill for that Task only: move it to `doing`, read it once with `trama task show <id>`, implement it and run only its own tests, then move it to `done`, or file a Drift as described below, announcing it, and leave the Task in `doing`. Tell it never to run `trama task next`, never to take another Task, never to run the full suite, the linter or the build, and never to scan; it comes back with the Task done or the Drift it filed. If two sub-agents change the same file, each changes only the parts of its own Task; the final check finds conflicts. Wait for all of them, also those stopped by a Drift, and only then ask `trama task next --batch --max <N>` for the next group.
   - **Without sub-agents**, or for a group of one: do steps 2 to 5 yourself for each Task of the group, one after the other, then ask `trama task next --batch --max <N>` for the next group.

   Read a Task once, with `trama task show <id>`. That text is the Model and the Requirements for this Task. A Machine reference includes the State tree and the Events with who receives them. A State reference includes the outgoing Transitions, including those inherited from the States that contain it, marked as inherited. An Event reference includes the Transitions that react to it. A reference to a whole Area includes the text of every section. Under `## Requirements` are the Requirements attached to the referenced elements, and every General section that has text, written in full. A Technical Task references no Model element; implement it as a normal engineering task from the Requirements in that text.
2. **Start it.** `trama task move <id> doing`. If the move is refused because the Task is blocked, nothing changed. Asked for one named Task: stop, take no other Task, and report the Task and the Drift (or fix Task) the refusal names; only the developer can decide on that Drift. In a run over several Tasks `trama task next --batch` never names a blocked Task, so a refusal means something changed since you asked: leave that Task and go on with the rest of the group.
3. **Read the code.** The Model and the Requirements for this Task are the `trama task show` text already read. Read the code that implements them and follow its conventions. For this Task, do not run `trama state`, `trama event`, `trama paths`, `trama machine` or `trama requirements`, and do not open a `trama-req-*` skill. If a Transition the Task must implement does not appear in that text, run one command for that Transition, `trama state` or `trama event`, and do not resume the tour.
4. **Implement.** Write the code, including every Transition's condition and consequence exactly as the prose in the Task text says, and the States around it that the Task depends on. Follow every Requirement in that text, including the General sections written there. Add or update tests for the behaviour. While writing, run the tests added or changed for this Task and the existing tests of the behaviour this Task changes. Do not run the project's full suite, the linter or the build after the Task. After the code, do not read the Model again.
5. **Finish the Task.** `trama task move <id> done`. Record the permanent ID of each Task this run moves to Done. In a run over several Tasks, once every Task of the group is finished (Done, or stopped by a Drift), ask `trama task next --batch --max <N>` again (with the same `--proposal`, if any) and go back to step 1 until it says no Task is runnable.
6. **Check the run.** A Task asked by name is its own run, so this step follows it at once. In a run over several Tasks, this step runs once, after the last group, when `trama task next --batch --max <N>` (with the same `--proposal`, if any) says no Task is runnable; never in a sub-agent. Run the project's tests, linter and build once. If that check fails, fix the code and run it again, without reading the Model again; leave every Task in the column it is in. If you cannot tell which Task broke the check, say so in the report and stop, without another reading tour and without step 7.
7. **Scan the completed Tasks' scope.** Only when the check of step 6 passed, the run moved at least one Task to Done, and no Task of its scope is blocked at the end (`blockedBy` in `trama task list --json`; the scope is the design's Tasks for a design, every Task for every Task in "todo", that Task for a Task asked by name). Run `trama task scope <id> [<id>…]` with the permanent IDs of the Tasks this run moved to Done. If the scope is empty, do not scan; close the check after step 6. Otherwise, follow the steps of `trama-scan` on exactly the references in this `## Scan scope`, in this same run; do not expand it to the whole System or a whole Feature. Link every Task the scan files to the run's design with `--proposal <id>`: the design you were asked for, or, for a Task asked by name, the design it comes from (`proposal` in `trama task show <id> --json`), if any; after a run over every Task in "todo", or for a Task with no design, link none. Do not implement the Tasks this scan files.
8. **Report.** Say what you implemented, in domain terms, the Drifts you filed (each with its Task), anything you noticed that was outside the Tasks, the Tasks still in "todo" left unrun, each with the Drift or the fix Task that blocks it, as the last `trama task next --batch` lists them, and the Tasks and Drifts the scan of step 7 filed.

## When you must file a Drift

Stop working on the Task at once and file a Drift when any of these is true:

- The Model cannot be implemented as written (contradiction, impossible condition, an Event nothing can emit).
- The Model is silent on a case that the Task forces you to handle, and the choice changes what the user sees or what data is kept.
- Doing the Task right requires a State or Transition the Model does not have.
- A Requirement cannot be followed (it conflicts with the Model, another Requirement, or the platform), or the Task forces a construction choice the Requirements should decide and do not.

Then:

1. Decide which case applies. If the code is right and the Model forgot a case, begin a Proposal with the `trama-design` skill, without its interview (list your choices in the Proposal body): `trama proposal new … --announcement <id of the Drift's announcement>`. Finish its files, validate and read it, but do not submit it yet: attach the Draft to the Drift in step 2, then submit it right after; if the submission is refused, correct it, validate and review again, then retry. Otherwise there is no Proposal, except in the case of step 2 where no fix respects both the Model and the Requirements.
2. File the Drift **once**: `trama drift new "<title>" --ref <nearest Model element or Requirement> --task <id of the Task you are implementing> --happens "<what the code does or what you would do instead, in terms of behaviour>" --should "<what the Model or Requirement says and why it cannot be followed>" --option "<title of the way you recommend>" --option-text "<what it changes and costs>" --option "<title of another way>" --option-text "<…>" [up to five] [--critical when a developer decision is urgently needed] [--where "<where in the code>"]`, adding `--proposal <id of the Draft>` only in the first case, and `--announcement <id>`. Set `--critical` only when the developer urgently needs to take a position on this case; technical severity or complexity alone does not qualify. Otherwise omit it. The two texts and the options are required; `--where` is optional and the only place for code locations. Write them as described in "Writing a Drift". `--task` records the origin: the Drift blocks that Task and Tasks that concern the same thing.
   - **Resolved Drifts first.** Before filing, run `trama drift list --all --ref <ref>` for the references of the difference. A difference that a resolved Drift closed stays closed while the Model or the Requirement there still says the same thing: do not file it again. If it is back after a fix of the code or an adaptation of the Model, pass `--previous <id>` of that resolved Drift; the command refuses a previous Drift that is open, dismissed or unknown. When `--task` names a fix Task (one whose `drift` field is set), Trama writes `previous` itself, so `--previous` is not needed.
   - **No fix respects both.** When no fix of the code respects the Model and the Requirements together (for example, two Requirements contradict each other), file the Drift with no `--option`, with `--proposal` of the Draft that repairs the Model or the Requirements, as in step 1. A Drift without Fix options is refused without a Proposal.
3. Leave the Task in `doing`; the developer decides whether the code or the Model changes. Asked for one named Task, stop here. In a run over several Tasks, go on with the rest of the group, and then with the next group from `trama task next --batch`. The Drift blocks only the Task it was filed for and the Tasks that concern the same thing, and `trama task next --batch` skips those.
4. Report. Say what you implemented and the Drift you filed, with the Task it concerns. In a run over several Tasks this goes into the final report described in step 8 of the steps above, once `trama task next --batch` says no Task is runnable. A sub-agent reports to the main agent instead, which writes the one final report.

Small choices that stay below Diagram level and that no Requirement covers (names, data structures, how an effect is carried out) are yours to make; do not file Drifts for them.

## Writing a Drift

The developer reads a Drift at a glance, as a programmer, but not as a code review. Write the two sides, and the fix options, at the level of behaviour.

- **Say what the System does and what it should do**, in the words of the domain ("the cart total ignores the coupon"), not how the code does it.
- **Name no variable, function, class, field or file** in `--happens`, `--should` or the options, unless the difference cannot be understood without it. Then name only the one or two that matter, as `inline code`.
- **Code locations go only in `--where`**, which is optional: the files, and the code element when it helps. No line numbers, which go stale, and no long pieces of code.
- **Give two to five fix options**, the one you recommend first: each `--option "<title>"` is followed by its `--option-text "<text>"`. Each is a different way to reach what should happen, not a step of one plan, and says in terms of behaviour what changes and what it costs. About 60 words each, short Markdown, no headings or tables inside an option. Titles differ. A Drift filed with fewer than two, more than five, or an option missing its title or text is refused.
- **Fix options reach what should happen** without changing the Model or any Requirement, and respect every Requirement that applies to the elements of the Drift, not only those it names. An option that asks for an exception to, or a change of, the Model or a Requirement is not a fix option: that way goes to a Drift with a Proposal.
- **Use short Markdown:** short paragraphs, a bulleted list when there are several separate points, **bold** for the one or two terms that carry the difference. No headings inside a section, no tables, about 100 words per side.

## Automatic Drift-resolution Runs

An automatic Run is limited to its explicitly delegated Task identities. Query `trama drift autopilot --job <id> --json` for the current authorization; use only its authorized Task IDs, including fix Tasks from this resolution and origin Tasks that are still not Done. Pass each as a repeated `--task <id>` to every `trama task next --batch --max <N>` call. Never fall back to the ordinary queue.

Recheck the coordinator before starting the Run and again before starting each group. Keep only IDs still authorized then; if authorization is unavailable, unknown, disabled, or no IDs remain, do not start new work. Before starting each Task, ensure its origin Drift is still authorized. Tasks that fail remain reported and are excluded from later group selection; report failures with `trama agent-event failed --job <id> --task <task-id> --reason "<text>"`. Do not retry them. An in-progress Task may finish if the setting changes, but do not start further unauthorized Tasks.

The Run is separate from the resolution agent: do not reuse its terminal or implement during resolution preparation. Keep the normal Run checks and selective end-of-Run scan. That scan belongs to this Run's existing check; do not announce a second check.

`trama.driftAutoPilot` is application-scoped: `disabled` (default), `enabled` (non-critical Drifts only), or `yolo` (also critical Drifts). The host can stop further automatic steps if the setting changes. Repeated automatic cycles have no additional time, cost, or cycle limit; the developer can disable autopilot or interrupt the work. External agent scans are not part of Trama's coordination barrier.

## PowerShell

The examples use POSIX syntax. In PowerShell, pass JSON on standard input with a pipe, for example `Get-Content -Raw round.json | trama ask --root <project>`, not `<`. On Windows PowerShell 5.1, set `$OutputEncoding` and `[Console]::OutputEncoding` to UTF-8 first, or non-ASCII characters arrive as `?`. Write `--body` and `--reason` values in single quotes, because PowerShell expands `$` and the backtick inside double quotes.
