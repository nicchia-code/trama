# Requirements: Tecnologia e vincoli, Tecnologia dei Task

Generated by Trama from `.trama/requirements/tech/work.md`. Do not edit this file: change the Requirements through a Trama Proposal (or ask the developer).

These are the developer's Requirements for how the System is built. Follow them when you write code. The Model (`.trama/model/`) says what the System does; when a Requirement and the Model disagree, stop and tell the developer.
A section titled with a Model reference (such as `order/Paid`) applies to that element and to everything inside it.

## task

- The command line that moves a Task to In progress as the agent, and `trama task show`, report the blocking Drifts or fix Task by ID and title. `trama drift new` accepts the origin Task (`--task <id>`). The skill `trama-scan` files Drifts without an origin.
- `trama task next` prints the next runnable Task, with its ID and title, and moves nothing. With `--proposal <id>` it considers only the Tasks linked to that Proposal, and is refused when the Proposal does not exist. When no Task is runnable it says so on its first line and lists each Task still in To do within that scope, with the Drift or the fix Task that blocks it, marked as in `trama task list`. Both outcomes end successfully.
- `trama task next --batch` prints, instead of one Task, the group of a parallel run (see `rules`): from one to `--max` runnable Tasks (an integer of 1 or more; 20 without the option; a value that is not an integer or is below 1 is a usage error), one per line with ID and title, the first being the one `trama task next` would print. It accepts `--proposal <id>` with the same meaning, moves nothing, and when no Task is runnable prints exactly what `trama task next` prints. With `--json` it gives the list of Tasks, each with `id` and `number`. The group is computed in `src/core`, with the same comparison of references that decides which Tasks a Drift blocks.
- `trama task next` accetta il filtro ripetibile `--task <id>` anche con `--batch`: considera soltanto l'insieme nominato, rimuove i doppioni e rifiuta un'identità inesistente prima di produrre un gruppo. Si interseca con `--proposal` quando presente; ordine, blocchi, limiti e uscita senza Task eseguibili restano quelli attuali. Il filtro è calcolato in `src/core` e non cambia colonne né legami del design.
- Nei Run automatici, `trama-implement` usa sempre il filtro delle identità autorizzate e lo ricontrolla fra i gruppi con `trama drift autopilot --json`; non seleziona Task estranei se nessuno del gruppo è eseguibile. Le origini entrano solo quando i fix necessari sono Done. Per la verifica e lo scan finale considera soltanto i Task realmente eseguiti nella corsa, con le regole esistenti.
- The skill `trama-implement`, asked for several Tasks, takes them from `trama task next --batch --max <N>` (with `--proposal <id>` when asked for a design); `--max` è il limite dei sotto-agenti insieme che l'istruzione porta, intero da 1 in su, e senza `--max` vale 20. When the agent can start sub-agents, it gives each Task of the group to its own sub-agent, with the Task's ID and the instruction to move it, read it with `trama task show`, implement it and run only its tests, as for a single Task; it waits for all of them, then asks for the next group. Without sub-agents, or for a group of one, it implements the Tasks of the group itself, one after the other. It files its Drift with the origin Task, leaves that Task In progress and goes on: a Drift does not end the run. Asked for one named Task, it stops at once when the move to In progress is refused because the Task is blocked, names the Task and the Drift (or fix Task) the refusal names, and takes no other Task. Its final report says what it implemented, which Drifts it filed, and which Tasks in To do were left unrun, each with the Drift or fix Task that blocks it, followed by what the end-of-run scan filed.
- Un sotto-agente non lancia `trama task next`, non sceglie altri Task, non esegue la suite intera, il lint o la build, e non scansiona: torna all'agente principale con il Task fatto o con il Drift archiviato. Se due sotto-agenti si trovano a cambiare lo stesso file, ognuno cambia solo le parti del proprio Task; la verifica finale della corsa scopre i conflitti.
- Dopo la verifica finale riuscita, quando le condizioni di `rules#task` sono vere, la skill `trama-implement` chiede a Trama l'ambito della scansione di fine corsa con `trama task scope <id> [<id>…]`, che stampa l'ambito calcolato come `rules#task` dice (le stesse righe `ref` e `reason` di `trama proposal show`), e segue i passi della skill `trama-scan` su quell'ambito, nella stessa corsa, con `--proposal <id>` sui Task quando la corsa ha un design; non realizza i Task che archivia. Con un ambito vuoto il comando lo dice e la skill chiude il controllo senza scansionare.
- `trama task show` scrive nel testo del task tutto ciò che serve a realizzarlo, senza rimandi ad altri comandi o a skill. Un riferimento a una macchina include l'albero degli stati e gli eventi con chi li riceve, gli stessi fatti di `trama machine`. Un riferimento a uno stato include le transizioni in uscita, anche quelle ereditate dagli stati che lo contengono, segnate come ereditate. Un riferimento a un evento include le transizioni che vi reagiscono, gli stessi fatti di `trama event`. Un riferimento a un'area intera include il testo di ogni sua sezione. Nella parte dei Requisiti, ogni sezione General che ha testo è scritta per intero; il comando non nomina le skill `trama-req-*` da caricare.
- La skill `trama-implement` legge Modello e Requisiti di un task solo con `trama task show`. Per quel task non lancia `trama state`, `trama event`, `trama paths`, `trama machine`, `trama requirements` e non apre le skill `trama-req-*`. La lettura del codice resta. Se una transizione che il task deve realizzare non compare in quel testo, può lanciare un solo comando per quella transizione, `trama state` oppure `trama event`, e non riprende il giro. Dopo il codice non rifà il giro; la scansione mirata di fine corsa è un passo a sé e legge il Modello come la skill `trama-scan`.
- Mentre scrive un task, può eseguire i test aggiunti o modificati per quel task e i test già esistenti del comportamento che il task cambia. Non esegue la suite intera del progetto, il lint né la build dopo ogni task.
- Test, lint e build del progetto girano una volta, alla fine della corsa. Un task chiesto per nome è da solo la sua corsa. In una corsa di più task la suite è dopo l'ultimo, quando `trama task next` dice che non ne resta uno eseguibile.
- Se quella verifica fallisce, l'agente corregge il codice e la rilancia, senza rileggere il Modello, prima del resoconto. I task restano nella colonna in cui sono. Se non sa quale task ha rotto la verifica, lo dice nel resoconto e si ferma, senza un altro giro di lettura.
- Nei Run automatici, un Task o una verifica finale non riusciti vengono riferiti al coordinatore e non provocano un nuovo tentativo automatico sul caso fallito. Il lavoro indipendente può proseguire solo quando il fallimento è attribuito a un caso e non compromette quel lavoro; una verifica finale fallita di origine incerta sospende la prosecuzione automatica e non produce uno scan dichiarato riuscito. La regola di correzione e rilancio sopra resta per i Run manuali.
- `trama task scope <id> [<id>…]` calcola in `src/core` l'ambito della scansione di fine corsa dai riferimenti dei Task nominati, con la stessa funzione che calcola lo scope di una Proposal, e lo stampa come `## Scan scope` (`ref` e `reason`, con `reason` sempre `changed` o `leads into a change`); una General nominata entra come `requirements/<area>#General` con motivo `changed`; con `--json` è una lista di `{ ref, reason }`; un Task che non esiste è un errore d'uso; con l'ambito vuoto stampa una riga che lo dice ed esce con 0.
- `trama task scope --pre-flight [--proposal <id>] [--task <id>…]` sceglie i Task eseguibili in To do come `trama task next` (stessi filtri, bloccati esclusi) e stampa i loro riferimenti esatti deduplicati: una sezione di Requisiti vale il suo elemento; niente Transition, niente General né Aree. Con `--json` dà la lista di `{ ref }` e le identità dei Task. È calcolato in `src/core`; un riferimento che non si risolve più è saltato.
- La skill `trama-implement` fa come primo passo il pre-flight (`rules#task`), prima di `trama task next --batch`: annuncia il check, lancia `trama task scope --pre-flight` con i filtri della corsa e, con più Machine, un sotto-agente per Machine che archivia solo Drift senza origine; chiude il check, poi realizza i gruppi come sotto. A fine corsa lo scan mirato include le General nominate dai Task portati in Done.
- Il numero di Task finiti dall'ultimo scan globale è un campo della Snapshot (`tasksSinceScan`), calcolato in `src/core` dai `finished` dei Task e dall'istante in `.trama/last-scan/system` (vedi `data`); la riga di comando non lo mostra. Il pannello osserva `.trama/last-scan/` come il resto di `.trama/`, così un cambio da un'altra finestra aggiorna i pulsanti. L'estensione scrive il file, con l'istante del lancio, appena consegna l'istruzione di uno scan di tutto il Sistema lanciato da un pulsante Scan (scritta nel terminale, inviata alla chat, lasciata pronta nella chat o copiata negli appunti), passando da un file provvisorio poi rinominato; una scrittura fallita è segnalata al developer e il numero resta. Una consegna che non avviene (richiesta del comando annullata, terminale che non si apre) non scrive nulla. L'estensione non ricorda più in memoria i lanci dello scan globale e non riconosce più il controllo `Scan of the System` per il numero: la consegna o il ritiro di un controllo non toccano il file.
- `trama task move <id> done --unchanged <nota>` chiude un Task di correzione senza modifiche (`rules#task`): scrive `unchanged` nel Task e, nello stesso passo e nella stessa funzione di `src/core` che sposta il Task, porta il suo Drift a `dismissed`. `--unchanged` vale solo con `done`; con un'altra colonna, senza testo o con un Task che non si può chiudere così è rifiutato con un'uscita di errore che dice perché. Qualunque spostamento fuori da Done toglie `unchanged`. `docs/cli.md` descrive l'opzione.
- La skill distribuita `trama-implement`, per un Task con un Drift, dopo averlo preso e letto con `trama task show` e prima di scrivere codice, rilegge il codice di Where in the code e dei riferimenti e confronta con What happens; se il codice fa già ciò che dice il Model o il Requisito lo chiude con `--unchanged`, in un sotto-agente come nell'agente principale. Il resoconto ha una voce per i Task chiusi senza modifiche, con la nota. Per lo scan di fine corsa passa a `trama task scope` solo i Task portati in Done senza `--unchanged`; la condizione «almeno un Task in Done» conta solo quelli.
- `tasksSinceScan` non conta i Task con `unchanged`.
