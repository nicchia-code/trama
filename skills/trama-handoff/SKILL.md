# Trama: handoff

A **handoff** is the lighter Proposal (`kind: handoff`) through which the Manager gives work to the people of his team instead of to the agent. Instead of Tasks it carries **issues**: for each one the title, the body the assignee will read on GitHub, the Model elements and Requirement sections it is about, and what you propose for it (who does it, who reviews it, the estimate in days, the sprint and the other fields of the GitHub Project). It may also change the **Model** in `.trama/model/` and the **Requirements** in `.trama/requirements/` like a design, or change nothing. The Manager previews, adjusts and approves it in the Team view; on approval Trama creates the issues and asks you to publish them on GitHub. You never write code in this skill.

The instruction decides which job you do:

- **A handoff request**: "Use the trama-handoff skill on the handoff request in `.trama/requests/<id>.md`…": steps 1 to 7 below.
- **Rework with feedback**: "…to rework the rejected handoff <id> with the developer's feedback…": "Reworking a rejected handoff".
- **Split**: "…to split issue <issue id> of handoff <handoff id> into issues that each fit a sprint, on the same handoff.": "Splitting an issue".
- **Publication**: "…to publish the issues of handoff <handoff id>.": "Publishing the issues".
- **Comment update**: "…to comment on issue <issue id> what changed in the Model since it was published.": "Commenting on a changed issue".

If a `trama team`, `trama issue` or `trama proposal new` command is refused because Team is not available (Manager Mode is off, or the origin of the repository is not on GitHub), stop, open no handoff, and tell the Manager to turn Team on.

## Hand-over

A new handoff starts as a **Draft**, not approvable. Finish every file, then run `trama proposal move <id> open` without `trama proposal show` before it: read its output (the checks, the warnings and the issues). If the hand-over is refused, it names each problem: fix them with `trama proposal edit <id>` and hand over again. Before every later file change call `trama proposal edit <id>` again: it returns an open handoff to Draft, so hand over again when finished. After a successful hand-over, stop: deciding is the Manager's, in the Team view.

## Announcing cards

Trama has already announced the work you do, whichever job the instruction names (a handoff request, a rework, a split or a publication), and its ghost shows in the status bar, never on the Board: you announce nothing. Do not run `trama announcement new` for a handoff, and do not pass `announcement` to `trama proposal new`.

## Hard rules

- NEVER edit `.trama/model/`, `.trama/requirements/` or `.trama/issues/` directly, nor the generated `trama-req-*` skills. Every change to the Model and the Requirements goes through the handoff, created with `trama proposal new --input -` and `"kind":"handoff"`; the issue files are written only through `trama proposal edit`.
- Agents may approve or reject a Proposal, discard a Draft, resolve a Drift or delete a Task in To do (`trama task delete`) only when the developer explicitly asks for that decision in the conversation. Without that request, do not decide and do not ask the developer about it: hand the handoff over and stop; deciding is the Manager's, in the Team view. Approving is never yours: it publishes issues on GitHub for other people.
- Trama reads GitHub only to read; whatever changes on GitHub is your work, and only in the publication job and in the comment job. In every other job `gh` is used only to read (`gh issue list`, `gh project item-list`, `gh project view`, `gh api` with GET), never to create, edit, comment or close anything. The comment job writes one comment with `gh issue comment` and nothing else.
- Never write the Manager's choices: the `manager` key of an issue file is Trama's. Never write it, and never copy it from one issue to another.
- The Model describes *what can happen*, never *how it is built*: no variables, field names, database columns, endpoints, classes or file paths. How it is built belongs in the Requirements (see `trama-design`). The issue body, on the other hand, is for the person who builds it and does name the files and the code.
- An issue never carries images and never mentions Trama: no short number, no reference syntax, no command, in its title or its body. What Trama shows of its references (a folded block) is added by Trama when it composes the body.

## Naming cards

Every live Proposal has a temporary **short number** (`P3`) besides its **permanent identity** of eight characters; issues have only their identity.

- Name cards to the Manager by short number and title, for example "Handoff P3 – title". A closed card has no number: use its permanent identity.
- In every command you run and every file you write (the handoff body, `requires`, `request`, `reworks`, `dependsOn`, `refs`) use **only the permanent identity**, taken from `--json` (field `id`; the number is the field `number`) or from the file or folder name. **Never write a short number in a file**: it changes from one working copy to another.
- Give every card you create, and its announcement, a **short title**: at most five words, about 40 characters, a name for the card rather than a sentence describing the work (for example "Testo fantasma" instead of "Descrivere Start from Scratch e guidare le richieste scritte con un testo fantasma"). Put the detail in the body, even when the title loses information. No command checks the length of a title. Titles that Trama or a skill composes from another title stay as they are: `Fix code to match the …`, `Import: <Feature>`, the titles of checks.

## Notes on the ghost

While your work waits, it has a ghost in the status bar, and you tell the Manager what you are doing with notes: `trama announcement edit --input -` with `{"note":"<one line>"}`, passed as `trama announcement edit --input - <<'JSON'`, the object and `JSON`. Without an ID the note goes to every ghost still waiting of your terminal or conversation. Declare a note at the start of each stage of your work: exploring, reading the team, each round of questions, writing the issues, handing over (in the publication job: publishing, and each failure). Write 3 to 6 notes for the whole job, never one per command. A note is one sentence of at most 120 characters (a longer one is cut) saying what you do and why, for the Manager: no first person, no Trama command names and no short numbers of cards, in the language of the instruction when it asks for one (for example «Reads the team and the sprint load before cutting the work»). A note changes nothing else about the ghost and is never needed to deliver a card.

## Language

When the instruction asks you to write in a language, the texts listed below go in that language. Without a language in the instruction, nothing here changes.

- **In the language of the instruction:** the titles and bodies of Tasks and the titles of groups of Tasks; the titles, bodies and Fix options of Drifts; the titles, introductions and reasons of Proposals; the text, context and options of questions (also the resolution question the Async Drift Resolver prepares); the notes of ghosts and the titles of announcements; the titles, summaries and texts of History entries; your replies during the work and your final report; the replies in General.
- **Always in English**, whatever the language: the whole Model (the name of the System; the names of Features, Machines, Actors and States; IDs and Event names; the descriptions in Model files); the Requirements (Areas, titles and bodies of fragments); the Specs, also their `notes`; code and its comments, commit messages and the project's own documentation; the headers Trama reads in files ("States", "Events", "General", "What happens", "What should happen", "Where in the code", "Fix options", "Already present"), the `(initial)` and `(final)` markers and the front matter fields; technical terms (commands and tools such as `git pull` or `npm install`, names of products, services, libraries and languages) and Trama's own terms (Proposal, Task, Drift, Board, Run, Scan). Trama's interface (panel, editor, command line) stays in English.
- **A language changes nothing already written.** When you edit a file written in another language, keep its existing text and write only the new or rewritten text in the chosen language; never translate the whole file.
- **No first person in Trama's texts.** In what you write for Trama (questions, contexts and options of rounds, titles and bodies of Proposals, Tasks and Drifts, History entries), Trama is always "Trama" and you are "the agent": no "I", "me", "my", "we", "our", and in Italian no "io", "noi" or first-person verbs. Your replies in the conversation are not Trama's texts and do not change. Text already written is not rewritten.
- **The issues.** The title and the body of an issue, and every note you write on GitHub, are in the language of the instruction, written for the assignee. The section headings of the body are in that language too (see "The issues"). Without a language in the instruction, they are in the language of the request.

## Handing a request over: the steps

1. **Read the request.** The instruction names a file `.trama/requests/<id>.md`. Read the **whole** file before anything else. If it does not exist, tell the Manager that the request is gone and stop, without opening any handoff. The request is the starting point of the interview, never its answers: every decision it makes still becomes a question with its options, the option the request indicates being your recommendation. Images the request links are only context: look at the local ones and the web addresses you can open, ignore silently the ones you cannot see, put in words what matters, and never copy, link or cite them, or their paths, in the handoff, the Model, the Requirements or an issue. Never ask whether to send images on: issues never carry images.
2. **Explore the Model, the Requirements and the code.** As `trama-design` does: `trama model show`, then `trama model list --input -` with `{"text":"<word>"}` in a heredoc for what already exists (it searches the Requirements too), then `trama model show <ref>` for a Feature, Machine, State, Event or Actor, and `trama model show requirements` for the Areas; then read the code that implements what the request touches. Facts are your job: never ask the Manager anything the Model, the Requirements or the code can tell you.
   **With sub-agents**, before the first round, hand this exploration to them, at most N at once, where N is the limit in Trama's instruction (`20` if it gives none), in whatever way your agent starts sub-agents: give each one part of the request (the Machines and Features it involves, and the code that implements them), with the commands above and the instruction to come back with a short account of what exists, what the request would change there, which files it would touch and what is unclear. A sub-agent asks the Manager nothing and writes no handoff. Gather their accounts; you alone run the remaining work, interview the Manager and write the handoff.
3. **Read the team and the Project.** Run `trama team show --json`: for each person the name, `handle`, `level` (`junior`, `mid` or `senior`), `skills`, `capacity` (days per sprint) and `absences` (`from`, `to`). Run `trama issue fields --json`: the fields of the linked GitHub Project, each with its options, and its `iterations` (the sprints, with start date, duration in days and `current`). Both commands need the editor: when one fails, say why and stop, as "Asking" of `trama-design` does for an unavailable editor. To know each person's load, read the open issues of the team with `gh`, read-only: `gh issue list --state open --assignee <handle> --json number,title,labels` for each member, and for the sprint and the estimate of those that are in the Project `gh project item-list <number> --owner <owner> --format json`, using the `project` of `trama issue fields --json`. `git log` tells who last changed the files involved. Never write anything with `gh` here.
4. **Interview the Manager in rounds** until every decision about the work is settled. Use `trama question new --root <project> --input -` (the JSON in a heredoc) exactly as `trama-design` does: its "The interview" and "Asking" sections apply, with one round per call, 2 to 5 options per question with tradeoffs, your recommendation on each, wait for the answers, no "Other", and no fallback after `editor-interrupted`. **Behaviour first**: what should change, for whom, what starts it, what if it fails, who is told, the deadline or constraint the request names. **Then how to cut the work into issues**: the order, what depends on what, who knows the area, who should learn it, what is a risk. Ask only what the request, the Model and the code leave open; never repeat what is clear. Never ask about images.
5. **Write the Model and the Requirements** when the request changes behaviour, exactly as `trama-design` says (its format reference is [FORMAT.md](../trama-design/FORMAT.md), installed next to this skill; do not copy it here): open the handoff first (step 6), then `trama proposal edit <id> --input -` with `{"edit":["<model-path>"]}` or `{"edit":["requirements/<area>/<fragment>.md"]}`. A request that changes no behaviour (a refactoring, a chore) changes no file. A handoff carries no Task and no `## Already present` section.
6. **Open the handoff and write the issues.** `trama proposal new --input -` with `{"title":"<title>","kind":"handoff","body":"<why>","label":"<epic>","request":"<id>"}`. The `label` is the short name of the epic, at most 30 characters on one line (for example the feature name): every issue is filed on GitHub under the label `epic: <label>`. The body says why and summarises the decisions of the interview, one line each, with the assumptions you made for skipped questions. When the work is too large to review at once, split it into handoffs that build on each other: open the later ones with `requires` listing the earlier ones, and with no `request`; their issues may depend on the issues of the handoffs they require. Bind only the first handoff to the request. Give the handoff a short title (see Naming cards). Then write each issue (see "The issues").
7. **Hand over.** Run `trama proposal move <id> open`. If it is refused, fix what it names and hand over again. Its output prints the warnings: `Not covered: <ref>` (a change of the Model or the Requirements that no issue names) and `Estimated <n> d: more than 3 days per issue`. They refuse nothing, but act on them when the fix is yours (name the element in the issue that is about it, cut the issue), and report what remains to the Manager in one sentence each. Then stop.

## The issues

Write each issue with `trama proposal edit <id> --input -` and `{"edit":["issues/<slug>.md"]}` (several in one call): it prints the full path of each, with the permanent identity assigned there, which is also the identity of the issue after the approval. To rewrite an issue, pass the full name it printed. The file has a front matter, an H1 with the title and the body.

- **Front matter.** `refs`: the elements of the Model and the sections of the Requirements the issue is about, as in a Task (every reference must exist once the handoff is applied; may be empty). `estimate`: days, a number from 0.5 in steps of 0.5. `assignee` and `reviewer`: GitHub handles without `@`, members of the team, never the same person. `sprint`: the title of an iteration of the linked Project. `fields`: an object from the name of another field of the Project to its value as text. `dependsOn`: identities of the issues it depends on, in this handoff or in the handoffs it requires. Any other field, `manager` included, is a validation error.
- **Size.** Each issue is a piece of work one person finishes in one sprint, with room for the review: aim at 3 days or less and split larger work, unless the Manager said otherwise in the interview. The hand-over only warns about an issue over 3 days.
- **Dependencies are explicit.** An issue never depends on one that is published later: dependencies form no cycle, and what must exist before is a dependency, not a hope about the order.
- **Assignee**, from the skills and the level of the people, who last changed the files involved (`git log`), and their load in the sprint. **Reviewer**: another member, who knows the area and did not write the work. Propose none only when nobody fits, and say so in the handoff body.
- **Sprint.** The first iteration, from the current one on, where the assignee has room for the issue given the capacity and the absences (`trama team show`) and the load already there, and where its dependencies are done before or in the same sprint, by the same person. Never an iteration that has ended.
- **Other fields.** A value for every other field of the Project that you can choose from the options `trama issue fields` gives (a single-select one of its options, a number a number); none for the fields you cannot choose.
- **Body.** Written for the level of the assignee, in the language of the instruction, without images and without any reference to Trama. The sections, in this order, headed with `##` in the language of the body: `Context`, `Current behaviour` (left out for new behaviour), `Expected behaviour`, `Suggested steps` (only for a junior assignee: where to start, in which files, in which order), `Acceptance criteria` as a task list, `State diagram` (only when the issue changes States or Transitions: a fenced block of language `mermaid` with a `stateDiagram-v2` of the part of the Machine involved), `Where in the code`, `Out of scope`, `How to verify`. Name States, Events and files as they are in the code, never as Trama references. The body is understood without the conversation that produced it: it says what must be true when done, with every decision of the interview that concerns it.
- **References.** Put in `refs` the Model elements and Requirement sections the issue is about, so each change of the handoff is named by at least one issue; Trama shows them in a folded block of the GitHub body unless Solo mode is on.

## Reworking a rejected handoff

This section applies when the instruction says to rework the rejected handoff `<id>` with the developer's feedback (Rework with feedback). Without that sentence, skip it.

1. **Read the rejected handoff.** Run `trama proposal show <id>`: it gives the body, the decisions, the files, the issues and, when the Manager wrote one, the `## Feedback`. The decisions of the rejected handoff count as already taken, except what the feedback changes or leaves in doubt. Without `## Feedback`, redo the same work on the Model as it is now.
2. **Interview only where needed.** One round of `trama question new` only for the decisions the feedback opens or leaves open, with the rules of step 4. Without open decisions, skip the round.
3. **Write the handoff again, from scratch,** on the Model as it is now, following steps 2 to 7 (read the team again: people and sprints move). Never request the rejected handoff back and never edit its files.
4. **Bind it with `reworks`.** Pass `"reworks":"<id>"` (the identity of the rejected handoff) only in the first `trama proposal new` of the rework; it is refused together with `request`. Trama binds the new handoff only when the rejected one exists, is rejected and no other Proposal already reworks it; otherwise it creates it unlinked and the result says why, so read the result.
5. **Hand over and stop**, as step 7 says.

## Splitting an issue

This section applies when the instruction says to split issue `<issue id>` of handoff `<handoff id>` into issues that each fit a sprint, on the same handoff. The handoff is open: you change its files, so it returns to Draft until you hand it over again.

1. **Read.** `trama proposal show <handoff id>` and `trama issue show <issue id> --json` (it also reads an issue of a handoff that is not approved yet): the issue as the Manager sees it, with the Manager's changes applied, and the other issues. Read the team and the sprints again (`trama team show --json`, `trama issue fields --json`) and the code the issue names. Run no interview, unless the cut depends on a decision that only the Manager can take: then one round, with the rules of step 4.
2. **Rewrite only that issue.** Cut it into issues that each fit a sprint with room for the review, each with the front matter and the body of "The issues". The last piece, the one that completes the work, keeps the identity of the issue: rewrite it with its full name (`trama proposal edit <handoff id> --input -` with `{"edit":["issues/<full name>.md"]}`); it takes `dependsOn` the new pieces that come before it, so the issues that depend on the original still wait for the whole work. Write the other pieces as new issue files. Propose assignee, reviewer, estimate and sprint for each piece as for any issue.
3. **Touch nothing else.** Never rewrite, delete or reorder another issue, and never touch the Model or the Requirements of the handoff: the issues you do not rewrite keep their files, and with them every change the Manager made. The Manager's changes to the issue you split are not carried to its pieces.
4. **Hand the same handoff over again** with `trama proposal move <handoff id> open`, read the warnings and stop.

## Publishing the issues

This section applies when the instruction says to publish the issues of handoff `<handoff id>`. The handoff is approved: its issues are cards in `.trama/issues/`, and Trama has marked the ones that wait as `publishing`. You publish **only those**: an issue already `published` is never created again. There is no interview in this job, and you never change what the Manager approved.

1. **Take the issues in order.** `trama issue list --input - <<'JSON'` with `{"handoff":"<handoff id>","state":"publishing"}`: they come in the order of publication, the issues an issue depends on first. Take the project with `trama issue fields --json` (`project`: owner, number and title; `fields`; `iterations`) and its node id with `gh project view <number> --owner <owner> --format json`; the repository is the one of `gh repo view --json nameWithOwner`.
2. **For each issue, in that order,** unless an issue it depends on is not published (then see step 4):
   1. Run `trama issue show <issue id> --json` when its turn comes, not before: the `githubBody` names a dependency by its GitHub number only once that dependency has been recorded as published. Use `githubBody` exactly as it is.
   2. **The label.** The epic is `epic: <label>` (the `label` field). When the repository has no such label (`gh label list --search "epic: <label>" --json name`), create it with `gh label create "epic: <label>" --color <hex>`: the colour is the one Trama gives that label on the Board. Hash the text of the label: start from 0 and, for each character, `hash = (hash * 31 + character code) mod 2^32`; the remainder of the hash divided by 6 picks, in this order, `0` blue `2563eb`, `1` green `16a34a`, `2` amber `d97706`, `3` violet `7c3aed`, `4` cyan `0891b2`, `5` red `dc2626`.
   3. **Create the issue** with `gh issue create --title "<title>" --body-file - --label "epic: <label>" --assignee <assignee>`, the body from the standard input in a heredoc (`--assignee` only when the issue has one). It prints the address of the issue, which ends with its number.
   4. **Record it at once**, before anything else: `trama issue move <issue id> published --input -` with `{"number":<n>,"url":"<address>"}`. If the run is interrupted from here on, the issue is not created twice.
   5. **Put it in the Project.** `gh project item-add <project number> --owner <owner> --url <issue address> --format json` prints the item; then set each field with `gh project item-edit --id <item id> --project-id <project node id> --field-id <field id>` and `--iteration-id <id>` for the sprint (the iteration whose `title` is the `sprint` of the issue), `--number <n>` for the estimate (the number field of the Project that holds an estimate, for example `Estimate`), `--single-select-option-id <id>` for a single-select field, `--number <n>` for a number field and `--text "<value>"` for a text field. Do it for the sprint, the estimate and every key of `fields` of the issue.
   6. **Record what GitHub did not take.** Collect the keys of the fields you could not set (the Project has no such field or option, no number field for the estimate, an iteration that no longer exists, a failed `gh project item-edit`): `assignee`, `estimate`, `sprint` or `fields.<name>`. When there is any, run `trama issue edit <issue id> --input -` with `{"unset":["<key>", …]}`; when there is none, run nothing.
3. **An assignee GitHub refuses** (not a collaborator of the repository): create the issue again without `--assignee` and add `assignee` to the keys of `unset`. Anything else that GitHub refuses when creating the issue is a refusal of the issue: step 4.
4. **A refusal.** When GitHub refuses to create an issue, run `trama issue move <issue id> not-published --input -` with `{"reason":"<GitHub's reason, in one line>"}` and go on with the next issue that does not depend on it. An issue that depends on one that is not published, directly or through others, is not published either: record it with the reason `Depends on an issue that is not published`. Never retry a refusal in a loop.
5. **Report** in one or two sentences: how many issues were published, with their numbers, and which ones are not published and why. Never run `trama issue move <id> publishing`: only Trama moves an issue there. Do not decide anything else.

## Commenting on a changed issue

This section applies when the instruction says to comment on issue `<issue id>` what changed in the Model since it was published. The issue is published and open, and the text of at least one of its references is no longer what it was when it was published or last commented on. There is no interview in this job. You write on GitHub **one comment**; you never rewrite the body of the issue, never change its fields and never decide anything for the Manager.

1. **Read what changed.** `trama issue show <issue id> --json`: `number` and `url` (the issue on GitHub), `body`, `refs` and, in `changed`, for each reference whose text is not what it was, its `earlier` text and its `current` text. `earlier` is null when git does not have the earlier text: then only the reference is named, and you read what the reference says now with `trama model show <ref>`. A `current` that is null says the reference no longer exists. Read `gh issue view <number> --comments` for what was already said on the issue, and its language.
2. **Write the comment** in the language of the issue (its title and body), for the person who builds it, with `gh issue comment <number> --body-file -` and the text from the standard input in a heredoc. Say what changed in what the issue asks for, in the person's words, and what it means for the work: what to do differently, what no longer applies, what is new. Never mention Trama, a short number, a reference syntax or a command, and never paste the whole text of the Model or the Requirements: tell the difference. One comment, short.
3. **Record it at once**, after the comment is written and not before: `trama issue edit <issue id> --input -` with `{"updated":true}`. Trama records the moment and the text of the references now: from then on the issue is no longer behind the Model, until the Model changes again. If writing the comment fails, record nothing and say why.
4. **Report** in one sentence: the number of the issue and what the comment says. Do nothing else.

## Sub-agents context sharing

This section applies only when the instruction says "The sub-agents context sharing is on: …". Without that sentence, skip it and work as written above.

With it, when you hand a part of the work to a sub-agent, in whatever way your agent starts sub-agents, you pass it what you have already read that concerns its part, so it does not look for it again and does not read it again.

- **What you pass.** Of what you have already read, only what concerns that sub-agent's part, plus a short common part (the request and the decisions, when there are any): Trama's texts quoted as they are (the written request with its images put in words, the output of `trama model show`, `trama task show`, `trama drift show`, `trama proposal show`, the decisions of the interview) and the places in the code already known, one line per reference, ``- `<ref>` — <where in the code>``. Never code, never everything you gathered, and nothing you read only to pass it on.
- **What the sub-agent does.** It does not reread the Trama texts it received and reads on its own only the ones that are missing. It always reads the code, also at the places it received, always runs the commands that register (`trama task move <id> doing`, `trama comparison new`, `trama drift new`) and loads its skill as without this feature. A received place that no longer matches the code is ignored: it searches by itself. Context Sharing never stops a job.
- **What comes back.** Each sub-agent reports where it found the code of what it saw, one line per reference as above; you reuse those lines in your own work and for the sub-agents that follow.
- **Limits.** No sub-agent runs again a read-only Trama command for a text it received, and what you pass to each one concerns only its part: never copy into every sub-agent all that you gathered.

In this skill:

- **Exploration (step 2).** Each sub-agent receives the request and the parts of `trama model show` you already read about its part.
- **Reading the team and the load (step 3).** Each sub-agent receives the output of `trama team show` and `trama issue fields` you already read, and the members it must look up.
- **Publishing.** No sub-agent publishes: the order of the issues and the numbers of the dependencies depend on one another.

## PowerShell

The examples use POSIX syntax. In PowerShell, pass JSON with a pipe and `--input -`, for example `Get-Content -Raw round.json | trama question new --input -`, instead of `<` or a heredoc. On Windows PowerShell 5.1, set `$OutputEncoding` and `[Console]::OutputEncoding` to UTF-8 first, or non-ASCII characters arrive as `?`. Never pass the JSON as the text of `--input`: Windows PowerShell 5.1 strips the inner quotes of arguments to external programs.
