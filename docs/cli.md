# CLI

`trama` is a single binary. It lets the agent **explore** the Model and manage Proposals, Tasks and Drifts. It never reads the user's code (ADR 0002). File formats are in [model-format.md](./model-format.md).

## Conventions

- `trama [--json] [--root <dir>] <command> …`
- Without `--root`, the CLI walks up from the current directory to the first folder containing `.trama/`.
- Default output is Markdown: compact for agents and readable for people. `--json` prints the same data as one JSON document, for the extension and for scripts. `ask` always prints JSON.
- Every command, including `ask`, `cursor-hook` and `copilot-hook`, accepts `--help` and `-h` in any position after its name: it prints the command's usage line and description on standard output and exits with 0, doing nothing else. It reads no standard input, does not contact the editor and opens no question round. A command that exists never answers `Unknown command`: wrong arguments give that command's usage error.
- Element arguments use the reference syntax from the format spec: `order`, `order/Paid`, `order/Paid/user.CANCEL`, `user.CANCEL`.
- A Proposal, Task or Drift argument may be the whole identity, a prefix that only one card of that kind has, the whole file or folder name, or the card's **short number**. A prefix that matches several cards is refused and the message lists their identities. Digits alone cite only a numbered card (`12` or `0012`), never a random identity made only of digits.
- **Short numbers.** Every live Proposal, Task and Drift has, besides its permanent identity, a temporary number written with the letter of its kind: `P3` for a Proposal, `T3` for a Task, `D3` for a Drift (`t3` works too). It is unique per kind and the lowest free one is given when the working copy first reads the card; a Proposal has one from the start, also as a Draft. A card is live while it is a Proposal not yet approved, rejected or discarded, a Drift not yet resolved, or a Task in To do or In progress. When a card closes (a decided Proposal, a resolved Drift, a Task in Done) it loses its number, which becomes free; a Task that leaves Done takes the lowest free number, not necessarily the one it had. A closed card is cited only by its identity. Exception: a Task of a design (linked to a Proposal, even when it is the only one) keeps its number in Done while a Task of the same design is in To do or In progress, and is cited by it as a live card; all the design's Tasks lose their numbers together on the first read that finds them all Done. A Done Task without a number never takes one, even when its design reopens.
- A command that names a card accepts its short number wherever it accepts an identity, including decision commands (`approve`, `reject`, `discard`, `drift resolve`, `task take-back`). An argument made of `P`, `T` or `D` followed only by digits is always a short number, never the start of an identity. It is refused, changing nothing, with a message that says why, when the letter is not the kind the command expects (`T3` given to a Proposal command: it is a Task) or when no live card has that number. The command turns the number into the permanent identity before it writes anything: file and folder names, front matter (`requires`, `proposal`, `drift`, `task`, `origin`, `refs`), the branch `trama/<id>`, instructions sent to the agent and texts written in files use the identity, never the number.
- Where output names a card (`board`, `list`, `show`, `next`, command messages, the Board's cards and buttons) it shows the short number if the card has one and, only if it has none, the identity. Never both. With `--json`, every command that describes a Proposal, Task or Drift carries both `id` (the permanent identity) and `number` (`"T3"`; no number for a closed card).
- Numbers belong to a working copy, not to the project. They are kept in `.trama/short-numbers/assigned`, one line per live card, `<kind> <identity> <number>` with kind `proposal`, `task` or `drift`. The folder is not versioned: it has its own `.gitignore` containing `*`, written with the first `assigned`. The file is written to a temporary file and renamed, so the panel and a command running together never read half of it. If `assigned` is missing, unreadable, has a line that makes no sense or repeats a number of the same kind, the working copy renumbers the live cards from zero in creation order; no command fails because of it. A card that arrives from another branch or worktree takes its number on the first read.
- Exit codes: `0` success; `1` domain failure (validation errors, unknown element, stale Proposal); `2` usage error.
- Commands that create a file print its ID and path. The agent may edit the file's prose directly afterwards.

## Project

| Command | Effect |
|---|---|
| `init [--skills-dir <dir>] [--force]` | Creates `.trama/` in `--root` (or the current directory) with `model/system.md`, `model/actors/`, `requirements/` with five Areas (`ui`, `tech`, `quality`, `data`, `rules`), each a folder holding only its `area.md` and no fragment, `proposals/`, `tasks/` and `drifts/`, and installs the agent skills (embedded in the binary) into `<dir>`, default `.agents/skills`. It never walks up. Fails, creating nothing, if `.trama/` already exists or if any skill file to install already exists with different content; `--force` overwrites those. Identical files are not a conflict. |
| `skills update [--skills-dir <dir>]` | Writes this version's agent skills into an existing project's `<dir>` (default `.agents/skills`), replacing older or edited copies, and lists the files it changed. Deletes the folder of the retired `trama-fix` skill, whatever it holds, from `.agents/skills`, `.claude/skills`, `.github/skills` and `<dir>`, and lists the folders it deleted. Creates the five starting Areas if the project has no `requirements/` folder. Converts every Area still written as one file, `requirements/<area>.md`, into `requirements/<area>/area.md` (description, title, introduction) and `requirements/<area>/main.md` (the same description and title with every section), deleting the old file; an Area whose folder already exists is left alone. It reports the Areas converted and those left, with why. Then regenerates the `trama-req-*` skills and reports their mode (one skill per fragment, or one index skill per Area), the budget used out of 4,000 characters and any switch. The extension runs it from **Trama: Update Agent Skills**. |

`init` and `skills update` also write the definition of the scan's analysis sub-agent into the project's `.omp/agents/trama-analysis.md` with `model: "@slow"`. It names an omp role, never a concrete model, so it can be versioned; the editor passes the developer's model with `--slow` (see the [extension README](../extension/README.md#terminal-agents-and-model-roles)).

## Identities

| Command | Effect |
|---|---|
| `ids rewrite` | Gives every Proposal, Task and Drift whose name is still `NNNN-<slug>` (at least four digits, and not an eight-digit identity that already has `created`) an identity of its own: the first eight hex characters of the SHA-256, in UTF-8, of `<kind>:<number>`, where the number is padded to four digits (`task:0012`). The same card gets the same identity on every copy that starts from that number. `created` becomes the UTC instant that many milliseconds after the epoch, so number order stays and the clock does not matter. The slug after the first hyphen stays, and so does each card's state. References that cite a rewritten card are updated. Refuses before writing if two cards would have the same identity. The agent may run it when the developer explicitly asks in the conversation; otherwise it asks the developer to decide. |

Un rifiuto di `ids rewrite`, o un'esecuzione senza schede numerate, lascia intatto anche il registro locale dei numeri brevi: non crea `assigned` né il suo `.gitignore`. Il registro si aggiorna soltanto dopo una riscrittura riuscita.

## Exploring

All exploring commands are read-only.

| Command | Output |
|---|---|
| `system` | System description; Actors with their Events; Features with their Machines. |
| `feature <feature>` | Description; Machines, each with the first line of its description; the Events that reach Machines of this Feature, as `owner.EVENT → receiving Machine`. An owner may be an Actor or a Machine of another Feature. Actors are only ever owners: what the System does in response to a Machine's Event toward the outside world is prose in that Event's description, never a graph edge. Then the Requirements attached to the Feature. |
| `machine <machine>` | Description; the State tree with markers; every Transition; owned Events and who receives them; the Requirements attached to the Machine or its Feature. |
| `state <state-ref>` | Description; parent and sub-States; outgoing Transitions, including those inherited from parents; incoming Transitions; the Requirements attached to the State or to what contains it. |
| `event <event-ref>` | Owner and description; every Transition that reacts to it (`machine/State → Target: prose`). |
| `paths <machine> <from> <to> [--max N]` | Simple paths between two States, shortest first, default `N = 20`. A State with sub-States stands for any of its sub-States; parents pass their Transitions down; entering a State with sub-States enters its initial sub-State. |
| `analyze [<machine>]` | Warnings for one Machine or the whole System: unreachable States, non-final dead ends, Events nobody receives. For the whole System, also every Requirement fragment larger than 12 KB, with path and size. |
| `requirements [<area> \| <ref>]` | Without an argument, every Area with its description, sections and the Requirement skills to load. With an Area (`ui` or `requirements/ui`), the Area in full; with `requirements/ui#order/Paid`, one section. With a Model reference, the Requirements attached to that element or to what contains it, each with its skill. The skills named are those the current mode generates: the fragment's skill, or the Area's index skill. |
| `search <text>` | Case-insensitive match over names and prose of the whole Model and its Requirements; each hit with its reference. |
| `validate [--proposal <id>]` | Validation errors for the Model and its Requirements, or for both with that Proposal applied. Exits `1` when there are any. Warnings follow, apart, and never change the exit code: fragments larger than 12 KB and, with `--proposal`, the switch of the Requirement skills between fragment and index mode the Proposal would cause. |

## Proposals

| Command | Effect |
|---|---|
| `proposal new <title> [--body <text>] [--requires <id>…] [--import] [--request <id>]` | Creates `proposals/<id>-<slug>/proposal.md` with `status: draft` and `created`, the UTC creation instant in ISO 8601. The id is eight random lowercase letters and digits, unique among Proposals; a Task or a Drift may use the same string. A card still named `NNNN-<slug>` (at least four digits) stays addressable by that number and has no `created`. An id argument may be the whole identity, a prefix that only one card of that kind has, or the whole file or folder name; digits alone cite only a numbered card. `--requires` writes it on top of those draft, open or approved Proposals (refused for a rejected or discarded one); `--import` marks it `kind: import` (ADR 0008). `--request` binds it to the written design request `.trama/requests/<id>.md` it comes from, recorded as `request`; when that file does not exist the Proposal is created unbound and the output says the request was not found. |
| `proposal edit <id> <path>` | `<path>` is a Model file relative to `.trama/model/`, or a Requirement file `requirements/<area>/area.md` or `requirements/<area>/<fragment>.md`, new or existing. `requirements/<area>.md` and deeper paths are refused, saying why. Copies the current file into the Proposal and records its hash in `base`, or creates an empty file marked `new` if it does not exist. Prints the path to edit. Register before every change: an open Proposal returns to Draft, with a notice after the path. Re-registering keeps the original hash and contents. Use `--json` and its `path` field for scripts. |
| `proposal delete <id> <path>` | Adds the file to `delete` and records its hash in `base`; an open Proposal returns to Draft, with a notice. |
| `proposal submit <id>` | Hands a Draft over, setting `status: open`. Refuses validation errors and unregistered files, leaving it Draft. Staleness or waiting for required approvals do not prevent submission, nor do the warnings of `validate`, which it prints after the result. When the Proposal is bound to a written design request, a successful hand-over deletes `.trama/requests/<id>.md` and says so; a file already gone does not make it fail, and a refused hand-over deletes nothing. |
| `proposal discard <id>` | Discards only a Draft, setting `status: discarded`; no feedback, no changes to dependents. A Draft attached to an open Drift is refused, changing nothing, as `approve` and `reject` refuse it: the message names the Drift, and the Drift is decided with `drift resolve` (fixing its code sets the Draft aside). The agent may run it only when the developer explicitly asks in the conversation; otherwise it asks the developer to decide. |
| `proposal show <id>` | Description; stale or not; for each touched file, what is added, removed or changed, and for a Requirement file its Area and fragment (or `area.md`); for a Proposal that has one, its **`## Scan scope`**: one reference per line in the form `--ref` takes (`order/Paid`, `order/Paid/user.CANCEL`, `requirements/ui#order/Paid`), each with why it is there, `changed`, `removed, its container` or `leads into a change` (with `--json`, `scanScope`, a list of `{ ref, reason }`); validation errors of the Model and Requirements with the Proposal applied. |
| `proposal list [--all]` | Draft and open Proposals (all statuses with `--all`), marking drafts `(draft)`, imports, stale ones and required Proposals not approved yet. |
| `proposal approve <id> [--skills-dir <dir>…]` | Open Proposals only. Refuses Drafts as still being written. Fails if a required Proposal is not approved, or the Proposal is stale or invalid; otherwise applies it in this folder, sets `status: approved` and regenerates the `trama-req-*` skills in `.agents/skills`, `.claude/skills`, `.github/skills` and each `--skills-dir` folder (relative to the project root) that holds `trama-design`. The extension passes its `trama.skillsDir` setting; from a terminal, pass the folder you configured. A Drift's attached Proposal is accepted with `drift resolve --accept-proposal`, which also applies it in this folder. An agent may approve or reject a Proposal only when the developer explicitly asks for that decision in the conversation; otherwise it asks the developer to decide. |
| `proposal reject <id> [--feedback <text>]` | Open Proposals only. Sets `status: rejected`. With non-blank feedback it is appended under `## Feedback`; without it, or with blank text, nothing is appended. Drafts are refused as still being written. An agent may reject a Proposal only when the developer explicitly asks for that decision in the conversation; otherwise it asks the developer to decide. |

These are decisions for the developer: `proposal approve`, `proposal reject`, `proposal discard`, `drift resolve`, `task take-back` and `ids rewrite`. An agent may run any of them only when the developer explicitly asks for that decision in the conversation; otherwise it stops and asks the developer to decide. Requests to design, scan, implement Tasks or prepare a Drift resolution do not authorize the decision. Trama applies the same argument, state, reference, dependency, validity and conflict checks regardless of who runs the command; `TRAMA_AGENT` and `CURSOR_AGENT` do not block it.

## Tasks

| Command | Effect |
|---|---|
| `task new <title> (--ref <ref>… \| --technical [--ref <requirement>…]) [--drift <id>] [--proposal <id>] [--body <text>]` | Creates a Task in `todo`. A Task references at least one Model element and may add Requirements (`requirements/ui#order/Paid`); a Technical Task may reference only Requirements. `--proposal` links the Task to the Proposal (the design) it comes from; the Proposal must exist, in any status; a Technical Task keeps no link, because it is never part of a design. The Scan files its Tasks with it after an approval. Fails if a reference or the Proposal does not resolve. |
| `task list [--column todo\|doing\|done]` | Tasks grouped by column, flat: every Task is listed, with its Proposal ID when it has one, so the agent can always find the Tasks in `todo`. A Task the agent has taken is marked `(agent working)`, here and in `task show` and `board`. A blocked Task is marked `(blocked by Drift <id>)` once for each Drift that blocks it, or `(waiting for Task <id>)` when it waits for the Task that fixes its Drift, in the same places. |
| `task next [--proposal <id>]` | Prints the next runnable Task, `Next Task: <id> <title>`, and moves nothing. A Task is runnable when it is in `todo` and not blocked; the next is the oldest in creation order, worked out again at each call, so a Task that waits for the Task fixing its Drift comes back as soon as that Task is `done`, and the fixing Task goes first. A numbered Task, which has no creation instant, comes before every Task that has one. With `--proposal` only the Tasks linked to that Proposal count; a Proposal that does not exist is refused. When no Task is runnable the first line says `No Task is runnable`, followed by every Task still in `todo` in that scope, marked as in `task list` with the Drift or fix Task that blocks it. Both outcomes exit with success. |
| `task next --batch [--proposal <id>] [--max <N>]` | Prints, instead of one Task, the group of a parallel run, one Task per line, `<id> <title>`, and moves nothing: from the next runnable Task, following the runnable Tasks oldest first, every Task that concerns the same thing as none already chosen (the comparison of references that decides which Tasks a Drift blocks), up to `<N>` (`20` by default). `--max` must be a positive integer. The first line is always the Task `task next` would print. `--proposal` means the same as for `task next`. When no Task is runnable it prints exactly what `task next` prints. With `--json`, `batch` lists the Tasks, each with `id`, `number` and `title`. |
| `task show <id>` | The Task, with the blocked and `(agent working)` marks, a line `Blocked by Drift <id>: <title>` or `Waiting for Task <id>: <title>` for each blocker, and everything needed to carry the Task out, with no pointers to other commands or to skills. A Machine reference includes the State tree and the Events with who receives them, the same facts as `machine`. A State reference includes the outgoing Transitions, including those inherited from the States that contain it, marked as inherited. An Event reference includes the Transitions that react to it, the same facts as `event`. A reference to a whole Area includes the text of every section. Then the Requirements attached to the referenced elements (or to what contains them), and every General section that has text, written in full. |
| `task scope <id> [<id>…]` | Prints the union of the Model references named by the Tasks, plus Transitions that enter named States or react to named Events. A Requirement section counts as the Model element it names; an Area or `General` adds nothing. Text output uses `## Scan scope` with `changed` and `leads into a change`; `--json` prints a list of `{ ref, reason }`. Accepts permanent and short Task IDs, does not change cards, and refuses a Task that does not exist. An empty scope prints `_Nothing to scan._`. |
| `task move <id> <todo\|doing\|done>` | Moves the Task to another column. Run as the agent (`TRAMA_AGENT` set, or `CURSOR_AGENT=1` in Cursor's chat), a move to `doing` takes the Task for the agent and a move to `todo` or `done` clears that; run without it, the move is refused while the agent has the Task, and the refusal points to `trama task take-back`. A move to `doing` by the agent is refused, and changes nothing, when the Task is blocked (also when it is already in `doing`): the refusal names each blocking Drift (ID and title) or the fix Task, and says the developer must decide. Moves of the developer, and of the agent to `todo` or `done`, are never refused for that reason. The Board has no way to move a Task: moving stays here. |
| `task take-back <id>` | Clears the agent's mark on a Task it has taken; the Task stays in `doing` and the developer can move it again. Refused when the Task is not taken. The Board has no button for it. When the agent command ends the Tasks it took are released to `todo`. The agent may run it only when the developer explicitly asks in the conversation; otherwise it asks the developer to decide. |

### Runs over several Tasks

Run all To do, and Run this design for the Tasks of one design, send the agent to the skill `trama-implement` over several Tasks. The agent asks `trama task next --batch --max <N>` (with `--proposal <id>` for a design), where `<N>` is the concurrent sub-agent limit in the instruction, for the next group, implements it, and asks again until the command says that no Task is runnable. The limit is 20 when the instruction gives none. Run all To do considers every Task; Run this design only the Tasks linked to that Proposal, so a fix Task, which belongs to no design, is never run by it. The editor checks the same eligibility again just before delivery; if a Task in scope was taken while the request waited, it sends nothing. A Task in another design does not block Run this design.

When the agent has sub-agents, it gives each Task of a group to its own sub-agent, in the same folder, and waits for all of them, also those stopped by a Drift, before asking for the next group; without sub-agents, or for a group of one, it implements the group's Tasks itself, one after the other. A sub-agent never asks for Tasks, never runs the full suite, the linter or the build, and never scans. The same holds for the other skills: `trama-scan` gives each Machine to a sub-agent, and `trama-design` explores with sub-agents before its first round of questions; at most the limit in the instruction (20 by default) at once in every case.

A run skips the Tasks that are blocked and goes on past a Drift: the Drift the agent files leaves its Task in `doing`, blocks only the Tasks that concern the same thing, and does not end the run. A Task that waits for the Task fixing its Drift becomes runnable once that Task is `done`, so the fixing Task runs first and the waiting one right after it. The agent reads each Task once, from `task show`. While writing a Task it may run the tests it added or changed for that Task and the existing tests of the behaviour that Task changes. The project's tests, linter and build run once, at the end of the run; a Task asked by name is its own run. If that check fails, the agent fixes the code and runs the check again, without reading the Model again, before the report, and the Tasks stay in the column they are in. The run's report says what the agent implemented, the Drifts it filed, and the Tasks left in `todo`, each with the Drift or the fix Task it waits for. Asked for one named Task, the agent still stops at once when the move to `doing` is refused because the Task is blocked, and takes no other Task.

After the final check passes, when the run moved at least one Task to `done` and no Task of its scope is blocked, the agent runs `trama task scope <id> [<id>…]` for the Tasks it moved to `done`. If the scope is empty, there is no scan. Otherwise, the agent follows `trama-scan` on exactly those references, not the whole System or Feature, in the same run. Tasks the scan files link to the run's design (or the design of the single Task asked for), if any; the agent reports them and does not implement them.

Durante la verifica finale e lo scan mirato l'agente tiene un controllo sulla Board (`announce check`, vedi gli annunci): `trama-implement` lo annuncia in Verifying dopo l'ultimo Task, lo passa a Scanning se `trama task scope` restituisce un ambito non vuoto e lo chiude prima del resoconto; con ambito vuoto lo chiude dopo la verifica. `trama-scan`, fuori da una corsa, lo annuncia in Scanning e lo chiude prima del resoconto.

After an ordinary Proposal is approved, the automatic scan (`trama.autoScan`) compares only its scan scope (`proposal show`). La scansione automatica si ferma dopo aver archiviato i Task: non li realizza. Il developer li avvia dalla Board, per esempio con Run this design.


On the Board, Run all To do is unavailable while the agent has taken a Task, when no Task is in `todo`, and when every Task in `todo` is blocked; Run this design is unavailable under the same conditions for the Tasks of that design. The tooltip says why, naming the Task the agent is working on, or the Drift or fix Task of the first blocked Task; when both reasons hold it gives the agent working. The host refuses the launch in the same cases.

## Drifts

| Command | Effect |
|---|---|
| `drift new <title> --ref <ref>… --happens <text> --should <text> (--option <title> --option-text <text>)×2..5 [--where <text>] [--proposal <id>] [--task <id>]` | Records an open Drift. `--happens` is what the code does and `--should` is what the Model or Requirement says; both are required and become the Drift's two sections. The Drift also needs from two to five **fix options**, the one the agent recommends first: each `--option <title>` is followed by its `--option-text <text>`, in order, and they become the **Fix options** section. Each is a different way to reach what should happen (not a step of one plan), in terms of behaviour and with what it costs, about 60 words, no headings or tables. Filing is refused, naming the problem, with fewer than two options, more than five, an option missing its title or its text, or two options with the same title. Write them as short Markdown, at the level of behaviour and in domain words: no variable, function, class, field or file names unless the difference cannot be understood without them, no headings or tables, about 100 words per side. `--where` is optional and becomes a third section, **Where in the code**: the only place for files and code elements (no line numbers); a blank `--where` is refused. The refs point to the Model elements or Requirements closest to where the code differs. `--task` is the Task the agent was implementing when it found the difference, the Drift's origin; it must exist. The Drift blocks its origin and every Task that is not Done and concerns the same thing (a reference of one is the other's or inside it). Drifts filed by a Scan or a Fix have no origin. |
| `drift list [--all]` | Open Drifts (all of them with `--all`). |
| `drift show <id>` | The Drift's two sides (**What happens**, **What should happen**; a Drift written before them shows one **Description**), then **Fix options** as a numbered list, each with its title and text and the first marked `(recommended)` (a Drift written before options existed has none), then **Where in the code** when it has one, printed as the Markdown it was written in, its references inlined, the Requirements that apply, and its attached Proposal with its state and, when it cannot be approved, why. An open Drift listed by a resolution Proposal still being written or open shows `In resolution Proposal <id> <title>` (computed from the Proposals, never stored in the Drift); a Drift resolved by a resolution shows `Resolved by Proposal <id>`. `--json` carries the same as `inResolutionProposal` (`id`, `number`, `title`, or null) and `resolvedBy`. A Drift resolved by fixing the code also shows a **Chosen option** block (the option's number and title, when there was one) and a **Note** block when the developer gave one. |
| `drift resolve <id> --fix-code [--option <n>] [--note <text>] \| --accept-proposal \| --dismiss [--skills-dir <dir>…]` | `--fix-code` (keep what should happen) needs `--option <n>`, the number from 1 of one of the Drift's fix options, when the Drift has options; without it, in an interactive terminal, the options are listed as a numbered menu with the recommended one as the default (Enter) and then an optional note is asked (Enter for none), and in a non-interactive run it is refused, saying that an option must be chosen, and the Drift stays open. A Drift without options is fixed without choosing and accepts no `--option`. `--note` is free text kept with the choice. `--accept-proposal` and `--dismiss` take neither option nor note. Accepting requires an attached Proposal that can be approved (see `proposal approve`); dismissal accepts none. The agent may resolve a Drift only when the developer explicitly asks for that decision in the conversation; otherwise it asks the developer to decide. |

## Announcements

Announcing a card before the agent creates it makes the Board show a ghost of it meanwhile.

| Command | Effect |
|---|---|
| `announce <proposal\|task\|drift> <title>` | Announces a card the agent is about to create, as soon as it knows it will. Prints the announcement ID, six letters and digits. Not developer-only: the agent runs it. Writes a temporary file under `.trama/announcements/` (see the file format). When `TRAMA_TERMINAL` holds a terminal ID (the extension sets it in every agent terminal it starts), the announcement belongs to that terminal; without it, or with a value that is not six lowercase letters and digits, it belongs to none, and with `CURSOR_AGENT=1` it carries `chat: cursor` (made by Cursor's chat agent). |
| `announce check <title> --phase <verifying\|scanning>` | Annuncia un controllo: non una scheda, ma il lavoro che l'agente fa ancora quando nessuna scheda lo mostra (la verifica finale di una corsa, o una scansione). Stampa l'ID come gli altri annunci e copia `terminal` o `chat` allo stesso modo. `--phase` è obbligatorio per `check` e rifiutato per gli altri tipi. Il ghost sta in In progress. |
| `announce phase <id> scanning` | Passa un controllo da Verifying a Scanning, quando parte lo scan. Su un controllo già in Scanning non cambia nulla e lo dice. L'unica fase accettata è `scanning`. |
| `announce done <id>` | Dice che il controllo è finito: il file sparisce e il ghost con lui, senza avviso. |

Un ID sconosciuto, già consegnato o ritirato, o che non è un controllo, non è un errore per `announce phase` e `announce done`: l'uscita dice che il controllo non è stato trovato e il comando finisce con successo. Annunciare un controllo e cambiarne la fase contano come attività nei quindici minuti di quiete. Nessuno dei tre comandi è riservato al developer.

`proposal new`, `task new` and `drift new` take `--announcement <id>`: when the card is created, the announcement it names is delivered and the ghost gives way to the real card. A `proposal new` with no `--announcement` takes over the oldest announcement that Trama made for a design request and that no Draft has taken yet, whatever its terminal; with none waiting it makes an announcement of its own, so the Board shows its Draft, and that one belongs to the terminal in `TRAMA_TERMINAL`, if any. An ID that is unknown, already delivered or withdrawn, of another kind, or already bound to a Draft never prevents the card from being created; the output adds a note saying so. `proposal submit` delivers the announcement bound to the Draft only when it succeeds; `proposal discard` withdraws it with no notice.

Una Proposal creata con `--announcement` non utilizzabile resta senza ghost: non prende un'altra richiesta in attesa e non crea un annuncio automatico. Questi percorsi automatici si applicano solo quando `--announcement` è assente.

L’estensione sincronizza ogni trenta secondi soltanto l’H1 degli annunci Writing già associati a una Draft leggibile, anche dopo modifiche dirette al titolo e durante un round di domande. Conserva tutti i metadati, incluso `touched`, non riscrive un titolo già coincidente e non ricrea annunci ritirati o consegnati. La sincronizzazione non riavvia i quindici minuti di quiete; le modifiche della Draft continuano invece a contare come attività.

Only the extension withdraws announcements the agent never delivered, and each terminal only its own: the command Trama typed into an agent terminal ending (recognised by the command line the editor reports for it, compared after trimming; any other command, or an end reported without that line, withdraws nothing) or that terminal closing withdraws the announcements that belong to it. Every announcement, whatever terminal it belongs to, is also withdrawn after fifteen minutes in which the agent announced nothing, changed no announced Draft and filed no card (the count stops while a question round is open), and at startup; announcements that belong to no terminal (from the editor's chat, or from an agent Trama did not start) go only that way. The command line alone never withdraws any.

## Question rounds

`trama ask [--root <dir>] < round.json` reads one complete question round from JSON stdin and waits for its editor window. It always prints one JSON result or error on stdout; command diagnostics go to stderr. `--root` selects the project independently of the caller's current directory.

Example `round.json`:

```json
{
  "questions": [{
    "id": "route",
    "question": "Choose the route",
    "context": "Orders above **€500** go through the slow route today.",
    "options": [
      { "label": "Fast", "description": "Fewer checks", "details": "Skips the address check; about 1% of parcels come back." },
      { "label": "Safe", "description": "More checks" }
    ],
    "recommended": 1,
    "multi": false
  }]
}
```

Every question needs a unique non-empty ID, non-empty question text, at least two options with non-empty labels and descriptions, an in-range integer recommendation and an explicit `multi` boolean. Two fields are optional: `context` on a question, the background of the decision shown under it, and `details` on an option, a longer explanation the developer can open; when present they must be non-empty once spaces are trimmed. The question, its context and the option descriptions and details are Markdown; labels are plain text. Unknown fields are refused. The whole round is validated before any question is shown. Do not add an "Other" option: the editor always offers a free-text answer.

- **Completed:** `status: "answered"` and `answers` keyed by question ID. Each entry is `{status: "answered", selected: [...]}` with original option labels and optional `text`, or `{status: "skipped"}`. A multiple-choice answer may combine selected options and free text. Recommendation markers never appear in returned labels.
- **Initially unavailable:** `status: "unavailable"` and a `reason`. No answers are supplied; only this outcome permits the agent's own question interface.
- **Invalid request:** `error.code: "invalid-input"` with the offending field identified in `error.message`; correct the request rather than using fallback answers.
- **Editor lost after submission:** `error.code: "editor-interrupted"` with no answers. Stop the current workflow: no partial answers, recommendations, fallback, retry, rerouting or resumption. This is not initial unavailability.
- **Caller cancellation:** abandons only that caller's round. SIGINT/SIGTERM and observable output disconnection cancel CLI waiting.

Completed and initially unavailable results exit `0`; question failures and cancellation exit `1`; malformed requests exit `2`.

Questions open immediately in an overlay inside the editor's Trama panel, one question at a time with an index of the round. Back and the index keep what was entered; free text goes in `Your answer (optional)`; Skip skips one question, and Skip all (also behind Close) asks for confirmation and delivers at once. Otherwise the round is delivered from its summary with Send to agent, once every question is answered or skipped. Esc does nothing. Skips contain no invented answer: the agent applies its recommendation and lists the skipped decisions for review. The exception is `trama-resolve-drifts`: for a skipped question it applies no recommendation, leaves that Drift out of the resolution (it stays open) and says so in its report. There is no response deadline.

Each window owns one FIFO shared by every `trama ask` caller. Cancelling one caller does not cancel another; losing the editor interrupts both its active and queued rounds. Other windows remain independent. The endpoint in `TRAMA_QUESTION_ENDPOINT`, set by Trama in launched agent terminals, is authoritative; otherwise discovery selects the most recently focused live window for the selected project. Requests are sent to only that window; any other project is refused.

Eseguito dalla shell dell'agente chat di Cursor (`CURSOR_AGENT=1`), `trama ask` raggiunge la finestra del progetto attiva più di recente e presenta il round nel normale overlay locale, senza dipendere dagli hook della conversazione.

Routing uses private user-local sockets on Unix and user-only local named pipes on Windows. Discovery records live outside the repository and contain only project/window identities, endpoint and focus recency. Questions and incomplete answers remain in memory, never in `.trama/` or discovery files. The Windows bridge uses OS Windows PowerShell 5.1 and .NET Framework `Add-Type`; it fails closed if those facilities are unavailable, rather than falling back to a permissive Node pipe.

## Cursor hooks

`trama cursor-hook` is run by Cursor's `beforeSubmitPrompt`, `stop` and `sessionEnd` hooks, not by people or agents. It reads the JSON Cursor passes on stdin, takes the project from the first folder of `workspace_roots` that holds `.trama/model/system.md`, and hands the editor of that project, found through the same discovery records as `trama ask`, the hook name, the conversation ID, the project folder and, for `stop` and `sessionEnd`, Cursor's `status` or `reason`. Of the prompt it passes only whether it starts with `Use the trama-` or `/trama-`, never its text. It waits at most one second for an editor, writes nothing to disk, prints only `{"continue": true}` for `beforeSubmitPrompt` and `{}` otherwise, and exits with `0` in every case, also without an editor, without a Trama project or with invalid input.

The editor follows a conversation from its first prompt naming a Trama skill, whoever wrote it, and turns its hooks into the `cursor-chat` Events: every later prompt is `PROMPT_SUBMITTED`; `stop` with `completed` is `AGENT_STOPPED`, with `aborted` or `error` `AGENT_INTERRUPTED`; `sessionEnd` with `window_close` or `user_close` is `CONVERSATION_CLOSED` and ends the following, other reasons produce nothing. Other conversations are ignored. The list lives only in the editor's memory and is lost when it restarts.

## Copilot hooks

`trama copilot-hook` is run by VS Code's `UserPromptSubmit` and `Stop` hooks. It reads the hook JSON from stdin, uses `cwd` when it contains `.trama/model/system.md`, and hands the editor found through `trama ask`'s local discovery the hook name, session ID, project folder and only whether a prompt starts with `Use the trama-` or `/trama-`. It does not pass prompt text, waits at most one second, prints `{}` and exits `0` even without an editor, project or valid input.

The editor identifies a conversation on its first Trama prompt and treats every subsequent prompt as `PROMPT_SUBMITTED`; `Stop` emits `AGENT_STOPPED` only for an identified conversation in that same project. The editor keeps this recognition in memory. Copilot chat commands do not identify themselves as agent commands, so this hook releases originless Tasks at turn end but does not mark Tasks taken.

## Agent hooks

`trama agent-event idle [--root <dir>]` is run by the hook Trama makes omp load (`--hook`, see `extension/src/omp/trama-hook.ts`) when omp's main session settles (`session_stop`) or ends (`session_shutdown`), not by people. It takes the terminal's identity from `TRAMA_TERMINAL`, finds the editor of the project as `trama ask` does and tells it that the agent of that terminal is idle: the editor then ends the run, releases the Tasks that terminal had taken and withdraws its announcements. It waits at most one second, writes nothing to disk and exits with `0` also without an editor, a project or `TRAMA_TERMINAL`; only a wrong use exits with `2`.
