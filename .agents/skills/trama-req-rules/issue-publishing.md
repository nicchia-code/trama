# Requirements: Regole di business, Issue publishing

Use when implementing how the agent publishes the issues of an approved handoff and Trama's reads of GitHub through gh.

## issue

- The body published on GitHub is composed by Trama, the same in the preview and on GitHub, from: a first line `**Reviewer:** @<handle>` when there is a reviewer; a line `**Depends on:** #<n>, #<m>` when it depends on published issues (an issue that is not published yet is named by its title); an empty line; the body the agent wrote; and, except with Solo mode on, a folded block `<details><summary>Trama references</summary>` listing each reference of `refs` as inline code, then `</details>`. Nothing else is added.
- The agent's body has two parts. The part for the person comes first, with the sections `Context`, `Current behaviour` (left out for new behaviour), `Expected behaviour`, `Acceptance criteria` as a task list, `Out of scope` and `How to verify`, in this order, with `##` headings. Then a line with only `---`, the heading `## For the agent` written in the language of the body (for example `## Per l'agente`), and the part for the agent, with `###` headings, in this order: `Where in the code` (files, symbols, short code excerpts and the technical context or constraints only an agent needs), `State diagram` with a `mermaid` `stateDiagram-v2` of the part of the Machine involved when the issue changes States or Transitions, and, for a junior assignee only, `Suggested steps`. The part for the agent never repeats the acceptance criteria: it says to meet those of the part above. All headings are in the language of the body. The level of the assignee sets the detail of both parts. The body names States, Events and files as they are in the code, never as Trama references.
- Publication: the agent takes the issues of the approved handoff that wait to be published with `trama issue list`, in the order of their dependencies, and for each one: creates the label `epic: <label>` in the repository when it is missing, with the colour of the tag colour function of `tech#panel`; creates the issue with `gh issue create` with title, the composed body (`trama issue show <id> --json`, field `githubBody`), the label and the assignee; runs `trama issue move <id> published` with number and address right away; adds it to the Project with `gh project item-add` and sets the sprint, the estimate when the Project has a number field for it, and every other field; then records with `trama issue edit <id>` the keys of the fields GitHub did not take in `unset`. An assignee GitHub refuses (not a collaborator) leaves the issue without assignee and `assignee` in `unset`. When GitHub refuses to create the issue, the agent runs `trama issue move <id> not-published` with the reason and goes on with the next issue that does not depend on it; those that depend on it are not published either, with the reason `Depends on an issue that is not published`.
- The instruction of the publication is one line: "Use the trama-handoff skill to publish the issues of handoff <handoff id>." The terminal is named `Publish <short number>`, with the execution role (`rules#agent-launching`), and its ghost shows in the status bar.
- `Publish again` sends the same instruction; the skill publishes only the issues that are not published.
- When `trama issue move <id> published` runs, Trama records `published` and `texts`, the fingerprint of the text of each reference at that moment.
- The execution check (`rules#time`) moves to `not-published`, with the reason `The agent stopped before publishing it.`, every issue in `publishing` whose publishing agent no longer lives.

## github-project

- Trama looks for the GitHub command line `gh` in the editor's `PATH`, then in `/opt/homebrew/bin`, `/usr/local/bin` and, on Windows, `%ProgramFiles%\GitHub CLI`. There is no setting for its path.
- Trama runs `gh` itself only to read, with fixed arguments, without a shell and with a timeout of 20 seconds: `gh --version`; `gh auth status --hostname github.com`; and `gh api graphql` with fixed queries for the Projects of the repository's owner (user or organisation), the fields of the linked Project with their options and its iterations. It never runs a `gh` command that writes.
- States, in this order: `gh` not found → not installed; `gh auth status` fails → not logged in; a Projects query refused for missing scope (the error names `read:project` or `project`) → cannot read Projects; any other failure → read error, with `gh`'s message. Each read keeps the data of the last read that worked and the time it was read.
- `Log in to GitHub` opens a terminal named `Log in to GitHub` that runs `gh auth login --hostname github.com --web --scopes project`; `Give access` runs `gh auth refresh --hostname github.com --scopes project`. Both in the terminal area, visible, with the cursor inside, without a ghost; at the end of the command the Team view reads again.
- Linking keeps only Projects with at least one iteration field; the sprint field is the first iteration field, in the Project's order. Iterations are sprints: the current one contains today; past ones are not offered for new issues.
