# Requirements: Regole di business, Handoffs and issues

Use when implementing the checks of a handoff, how the agent writes and publishes issues, the Manager's changes to issue fields, Split, and Trama's reads of GitHub.

## team

- The handoff skill (`trama-handoff`) reads the whole request, explores the Model, the Requirements and the code as `trama-design` does, reads the team with `trama team show`, the linked Project's fields and iterations with `trama issue fields`, and the open issues of the team with `gh` to know each person's load. It interviews the Manager in rounds of `trama question new` like the design, on behaviour first, then on how the work is cut into issues. It never asks about images.
- It writes the Model and the Requirements like a design when the request changes behaviour, then the issues. Each issue is a piece of work one person finishes in one sprint with room for the review: the agent aims at 3 days or less and splits larger work, unless the Manager said otherwise. Dependencies between issues are explicit; an issue never depends on one published later.
- For each issue it proposes: the assignee among the members of the team, from their skills, their level, who last changed the files involved (`git log`) and their load in the sprint; a reviewer who is another member, who knows the area and did not write the work; an estimate in days in steps of 0.5; the first sprint, from the current one on, where the assignee has room for it given capacity and absences and where its dependencies are done before or in the same sprint by the same person; a value for every other field of the Project that it can choose, and none for the fields it cannot.
- It writes the body for the assignee's level (`rules#issue`) in the language of Trama's instruction, without images and without any reference to Trama, and puts the Model elements and Requirement sections the issue is about in `refs`.
- It opens the handoff with `trama proposal new` and `kind: handoff`, a short label that names the epic, and a body that says why and lists the decisions of the interview; the first one bound to the request with `request`. It hands it over with `trama proposal move <id> open`, reads the warnings in the output and tells the Manager about them, then stops: deciding is the Manager's, in the Team view.
- Rework with feedback and Split use the same skill: Split rewrites only the named issue into issues that each fit a sprint, keeps the other issues and the Manager's changes to them, and hands the same handoff over again.

## proposal/Draft

- `trama proposal new` with `kind: handoff` is refused, creating nothing, when Team is not available, with the reason of `rules#manager-mode`.
- The hand-over of a handoff is refused, naming each problem, when: Team is not available; it has no issue; an issue has no title or an empty body; an issue's assignee or reviewer is not a member of the project's team, or both are the same person; an estimate is not a number from 0.5 in steps of 0.5; a `dependsOn` names an issue that is neither in the handoff nor in a handoff it requires, or the dependencies make a cycle; a reference in `refs` does not exist with the handoff applied; the label is missing, empty, on more lines or longer than 30 characters; the handoff has `tasks/`. The members of the team come from the editor (`cli#team`): when the editor cannot answer, the hand-over is refused with the reason of `cli#team`.
- Warnings, which never refuse the hand-over and show in its output, in `trama proposal show` and in the issue preview: each scope entry (`rules#proposal/Approved`) that no issue names or contains in `refs` (`Not covered: <ref>`), and each issue estimated more than 3 days (`Estimated <n> d: more than 3 days per issue`). A handoff has no `## Already present` check.
- A handoff is blocked like any Proposal (stale, requiring unapproved Proposals, invalid with it applied) and also, only for approving, while no GitHub Project is linked (`Link a GitHub Project first`) or Team is not available.

## developer.CHANGE_ISSUE_FIELD

- Only on an open handoff, never on a Draft, and not while an agent is writing it. Values accepted: `assignee` and `reviewer` a member of the team or none, never the same person; `estimate` a number from 0.5 in steps of 0.5 (`Enter 0.5 days or more, in steps of 0.5.`); `sprint` an iteration of the linked Project that has not ended, or none (`Choose a sprint that has not ended.`); a single-select field one of its options; a number field a number; a text field at most 1,000 characters. A value equal to the agent's removes the key from `manager`: that is the undo.
- The change never sends the handoff back to Draft and is not seen by the agent as a change of its own: an agent that reworks or splits the handoff keeps the Manager's values of the issues it does not rewrite.

## developer.SPLIT_ISSUE

- Available on an issue estimated more than 3 days of an open handoff, when the agent that handed it over has finished its turn, no agent is writing the handoff and no Run launched from this window is in progress; otherwise `Split` is disabled with the reason, in this order: `The agent is still finishing`, `The agent is writing this handoff`, `A run is in progress`.
- The instruction is one line: "Use the trama-handoff skill to split issue <issue id> of handoff <handoff id> into issues that each fit a sprint, on the same handoff." The terminal is named `Split <short number>` and uses the model role of the design (`rules#agent-launching`).

## issue

- The body published on GitHub is composed by Trama, the same in the preview and on GitHub, from: a first line `**Reviewer:** @<handle>` when there is a reviewer; a line `**Depends on:** #<n>, #<m>` when it depends on published issues (an issue that is not published yet is named by its title); an empty line; the body the agent wrote; and, except with Solo mode on, a folded block `<details><summary>Trama references</summary>` listing each reference of `refs` as inline code, then `</details>`. Nothing else is added.
- The agent's body has, in this order, the sections `Context`, `Current behaviour` (left out for new behaviour), `Expected behaviour`, `Acceptance criteria` as a task list, `State diagram` with a `mermaid` `stateDiagram-v2` of the part of the Machine involved when the issue changes States or Transitions, `Where in the code`, `Out of scope`, `How to verify`; for a junior assignee also `Suggested steps` after `Expected behaviour`. Its headings are `##`, in the language of the body. It names States, Events and files as they are in the code, never as Trama references.
- Publication: the agent takes the issues of the approved handoff that wait to be published with `trama issue list`, in the order of their dependencies, and for each one: creates the label `epic: <label>` in the repository when it is missing, with the colour of the tag colour function of `tech#panel`; creates the issue with `gh issue create` with title, the composed body (`trama issue show <id> --json`, field `githubBody`), the label and the assignee; runs `trama issue move <id> published` with number and address right away; adds it to the Project with `gh project item-add` and sets the sprint, the estimate when the Project has a number field for it, and every other field; then records with `trama issue edit <id>` the keys of the fields GitHub did not take in `unset`. An assignee GitHub refuses (not a collaborator) leaves the issue without assignee and `assignee` in `unset`. When GitHub refuses to create the issue, the agent runs `trama issue move <id> not-published` with the reason and goes on with the next issue that does not depend on it; those that depend on it are not published either, with the reason `Depends on an issue that is not published`.
- The instruction of the publication is one line: "Use the trama-handoff skill to publish the issues of handoff <handoff id>." The terminal is named `Publish <short number>`, with the execution role (`rules#agent-launching`), and its ghost shows in the status bar.
- `Publish again` sends the same instruction; the skill publishes only the issues that are not published.
- When `trama issue move <id> published` runs, Trama records `published` and `texts`, the fingerprint of the text of each reference at that moment.
- The execution check (`rules#time`) moves to `not-published`, with the reason `The agent stopped before publishing it.`, every issue in `publishing` whose publishing agent no longer lives.

## github-project

- Trama looks for the GitHub command line `gh` in the editor's `PATH`, then in `/opt/homebrew/bin`, `/usr/local/bin` and, on Windows, `%ProgramFiles%\GitHub CLI`. There is no setting for its path.
- Trama runs `gh` itself only to read, with fixed arguments, without a shell and with a timeout of 20 seconds: `gh --version`; `gh auth status --hostname github.com`; and `gh api graphql` with fixed queries for the Projects of the repository's owner (user or organisation), the fields of the linked Project with their options and its iterations. It never runs a `gh` command that writes.
- States, in this order: `gh` not found → not installed; `gh auth status` fails → not logged in; a Projects query refused for missing scope (the error names `read:project` or `project`) → cannot read Projects; any other failure → read error, with `gh`'s message. Each read keeps the data of the last read that worked and the time it was read.
- `Log in to GitHub` opens a terminal named `Log in to GitHub` that runs `gh auth login --hostname github.com --web --scopes project`; `Give access` runs `gh auth refresh --hostname github.com --scopes project`. Both in the terminal area, visible, with the cursor inside, without a ghost; at the end of the command the Team view reads again.
- Linking keeps only Projects with at least one iteration field; the sprint field is the first iteration field, in the Project's order. Iterations are sprints: the current one contains today; past ones are not offered for new issues.
