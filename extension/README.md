# Trama

Trama keeps a map of your app next to your code and raises a Drift when the two stop agreeing. See the project README for how it works.

## Settings

Trama's settings are changed from the VS Code settings, or from the **Settings** tab of the Trama panel. The tab has four groups: **omp**, **Models**, **Project** and **Advanced**, which is split into the subgroups **Appearance**, **Drifts**, **Agents**, **omp Chat** and **Notifications**. It always writes to the user settings, never to the workspace.

The **omp** group (and the `omp` step of the setup wizard) has a **Providers** section, shown while omp answers, with one row per model provider omp logs in to with a subscription: ChatGPT, Anthropic, GitHub Copilot, Google Gemini CLI, Google Antigravity, Cursor and xAI Grok. A provider is **Connected** when `omp models --json` lists at least one usable model of it, whatever the way omp reaches it (login, API key, environment variable); **Not connected** otherwise, and no state when the list of models fails. **Log in** (**Log in again** for a connected one) opens a new terminal in the terminals area named `Log in to <provider>` that runs `<omp> login <provider>`, with the omp of `trama.ompPath` (in the wizard, of the step's path, even if not saved yet). When the command ends, or the terminal is closed, Trama checks omp again and refreshes the states; it shows no notice, does not read the exit code or the terminal, and runs no `omp token`, `omp auth export` or `omp usage accounts`.

**Cursor API key.** The Cursor row of **Providers** also takes an API key, saved by Trama, not by omp: **Set API key** (**Change API key** with one saved, plus **Remove API key**) asks for it in a masked input box titled `Cursor API key` and keeps it only in the editor's secret storage (`ExtensionContext.secrets`, key `trama.cursorApiKey`), one per user, shared by all windows and projects; the panel only learns whether a key is saved (`cursorApiKey { saved }`), never the key, and nothing else (settings, project files, `.trama/`, extension state, logs, instructions to the agent) holds it. Each omp process Trama starts afterwards gets it as `CURSOR_ACCESS_TOKEN` in its environment, over the editor's own value (job and Ask more terminals, the login terminal, `omp models --json`, `omp --version`, the check and update of omp, `omp usage --json`, and the processes of omp Chat and General); terminals and conversations already open do not get it, and an omp started by hand gets nothing. Saving or removing it makes Trama check omp again; a change from another window does the same here. If the secret storage fails, the editor shows `Trama: could not save|remove|read the Cursor API key: <reason>.` and nothing changes. Known risk: it is not verified that a Cursor dashboard user key works as `CURSOR_ACCESS_TOKEN` (Cursor's documentation says such keys are exchanged for an access token, which omp does not do), omp lists Cursor's models even with a wrong key, so the row can say **Connected** with an invalid key, and, like any environment variable, the key is visible to the commands omp runs.

**Log out.** A **Connected** row of **Providers** also has a ghost **Log out** button (accessible name `Log out of <provider>`, after **Log in again**). It asks first, with a modal editor dialog (`Log out of <provider>?`; closing it does nothing), and then runs `execFile(<omp>, ["auth-broker", "logout", <id>])` with a 30-second limit, without a terminal and without a shell, with the omp of `trama.ompPath` (in the wizard, of the step's path, even if not saved yet) and the environment of every omp process Trama starts (the PATH of omp and bun, and `CURSOR_ACCESS_TOKEN` when a Cursor API key is saved, never in the arguments). Only the exit code and the error output are read. omp forgets every account it stored for that provider; environment variables, `.env` files, keys in `models.yml` and the Cursor API key saved in Trama stay. While it runs, the row's **Log out** shows a spinner and every button of that row is disabled; when it has ended and the omp checks of the Settings tab and of the wizard's `omp` step have run again, the focus returns to **Log in** or **Log in again** of the row. A failure (non-zero exit, omp not starting, or no answer within 30 seconds) is an editor error `Trama: could not log out of <provider>: <reason>.`; after a success, a provider that omp still lists as Connected gets the editor message that it is still connected through another credential (for Cursor with a saved key, through the key saved in Trama or another one).

**System Certificates.** `trama.systemCertificates` (boolean, off by default, `scope: application`, last key of the `omp` group of `SETTING_GROUPS`; only the user value counts, `inspect(key).globalValue === true`, through `configuredSystemCertificates` in `agent.ts`) makes `extension/src/host/system-certificates.ts` export the machine's certificate authorities into one bundle and give every process Trama starts its path. The export never uses a shell and has a 30 s limit: macOS `/usr/bin/security find-certificate -a -p /Library/Keychains/System.keychain /System/Library/Keychains/SystemRootCertificates.keychain` (never the `login` keychain), Windows PowerShell on `Cert:\LocalMachine\Root` (never the user's store) and, on Linux, the first readable of `/etc/ssl/certs/ca-certificates.crt`, `/etc/pki/tls/certs/ca-bundle.crt`, `/etc/ssl/ca-bundle.pem`, `/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem` and `/etc/ssl/cert.pem`. `buildBundle` keeps the blocks that `crypto.X509Certificate` reads and that have `ca` true, adds `tls.rootCertificates` and drops duplicates by `fingerprint256`; no authority in the store is the failure `no certificate authority found`. The bundle is written to `<path>.<pid>.tmp` and renamed over the per-user path (macOS `~/Library/Caches/Trama`, Windows `%LOCALAPPDATA%\Trama`, Linux `$XDG_CACHE_HOME/trama`, else `~/.cache/trama`), so a failed export leaves the earlier bundle and no process reads half a file. The export runs when the mode is turned on, at activation when the bundle is missing or older than 24 h (a failure there shows once the editor warning with `Open Settings`), with the command `trama.refreshSystemCertificates` (`Trama: Refresh System Certificates`, in the palette only with `config.trama.systemCertificates`) and with the webview messages `refreshSystemCertificates` (only while the saved setting is on) and `systemCertificatesExport` (the wizard's step, which has no saved value to ask); a request during an export of the same window does nothing. The state (`exporting`, `count`, `exportedAt`, `error`) goes to the webview as `systemCertificates` at `ready`, when the Settings view shows and at every change. With the mode on and a bundle on disk, `systemCertificatesEnv(on)` gives `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `GIT_SSL_CAINFO`, `PIP_CERT`, `CARGO_HTTP_CAINFO`, `AWS_CA_BUNDLE` and `DENO_CERT`, merged after the inherited environment and `cursorKeyEnv()` in the terminals of the jobs and Ask more, the omp Chat processes, `installOmp`, `loginOmp`, `logoutOmp`, `ompModels`, `ompStatus`, `omp update --check`, `omp update` and `omp usage --json`; `agentCheckWanted`, `installOmp` and `ompLogin` carry the wizard step's `systemCertificates?: boolean`, which counts for that check, installer and login only. After every export that ends and every change of the mode the host forgets the outcome of the last update check and checks omp again in silence. In the wizard's `omp` step the same `SettingField` shows the box with the state line and `Refresh` (`WizardController` keeps the host's `systemCertificates` in its snapshot): the step's value counts at once for its own `agentCheckWanted`, `installOmp` and `ompLogin` (`systemCertificates` field), checking the box sends `systemCertificatesExport` when the bundle is missing or older than 24 h and the step sends a new `agentCheckWanted` when the export ends (also after `Refresh`, which sends `systemCertificatesExport` too), unchecking it sends `agentCheckWanted` at once, and the value is written only at the confirmation. Java's truststore is not covered, and certificate checking is never turned off. A reason that comes from a certificate error (`isCertificateError` in `extension/src/certificate-errors.ts`, shared by host and webview) is shown as «omp could not verify a server's certificate; a corporate proxy that inspects HTTPS traffic is the usual cause» (with the mode on, «…, even with System Certificates on; …») in the omp state, the models list, a failed update, the usage line, a failed logout, a conversation that does not start, exits or has its prompt refused (Board notices), and General; omp's own lines stay behind `Show details`; what omp writes in a terminal is never read.

**Auto-update stale Proposals** (`trama.autoUpdateStaleProposals`, on by default, turned off by setting it to `false`, in the **Agents** subgroup of **Advanced**): when on, approving a stale Proposal does not write it at once. The Proposal joins a queue, in Backlog order, and the agent refines it onto the current Model first; the Proposal is approved when the agent delivers it unblocked. A Proposal still stale after one refinement, or blocked for another reason, stays Open and Trama says why. The queue lives in the editor window: turning the setting off clears it, and refinements already working finish.

Refinements work in parallel. The Proposals in the queue and at work are split into chains: two Proposals are in the same chain when they touch a file in common or one requires the other (directly or through others), and each chain refines one Proposal at a time, the required ones first and then in Backlog order, while different chains work together. Each refinement is a job of its own, with its own terminal (`Refine P3`) or omp Chat conversation, and holds a share of `trama.maxParallelAgents` from its start to its end: the free places are divided equally among the refinements that start together, at least one each, and the places held never add up to more than the limit. A chain that is ready when no place is free waits for a refinement to end. A Proposal that requires another one still queued, at work or waiting for a Run waits for its approval, and when that Proposal leaves without being approved it leaves the queue and goes back to being stale. Each card in the queue says why it waits. A refinement does not stop and is not stopped by Run all, a Run, Resolve, Unify Drifts, a scan, a design or an import.

**Refine All** is the second entry of the arrow beside `+ Add Work Item`, under `Unify Drifts`. It queues in one click every stale Proposal the Board shows as to refine, Drafts left half-refined included, as if Approve had been pressed on each, and counts them (`Refine All (3)`); a Proposal that waits only for required Proposals is taken too when each of them is taken, already queued or at work. Nothing is approved and no file changes at the click; each refined Proposal is approved when its refinement ends, like with Approve. The entry is disabled, and says why, when the setting is off or there is nothing to refine. While Refine All is in progress, which lasts while the queue holds a Proposal that has not started, the entry reads `Cancel Refine All`: two seconds after the click it empties the whole queue, the Proposals queued with Approve too, and the refinements at work finish as usual. `Cancel` on a queued card takes out that Proposal only.

A Draft an agent is still writing (any agent: this window's refinement, another window, a refinement launched by hand) has the card of a Proposal in refining, whether Auto-update Stale Proposals is on or off, and its `Approve`, `Reject` and Rework arrow stay disabled with `The agent is refining this Proposal`. With the setting off, a Draft left half-way that nobody writes shows `to refine` and the same buttons disabled with `Still being written. Turn on Auto-update Stale Proposals to resume refining`; it does not count among the cards that await a decision.

While a Run launched from the window is in progress, Approve waits for it: the button says `A run is in progress`. Refine All does not wait: the refinements start, and a Proposal refined during that Run is marked `waiting for the run` and is approved when the Run ends (or goes back to the queue, without approval, if it is stale again then).

**Parallel execution** (`trama.parallelExecution`, on by default, turned off by setting it to `false`, in the **Agents** subgroup of **Advanced**): when on, Run all starts the Runs of the Tasks cut by model together, instead of one after the other. `trama.maxParallelAgents` (default 20, in the **Models** group) is the number of sub-agents the Runs share: each Run gets a share in proportion to its executable Tasks, at least one, and the shares never add up to more than the limit. Runs that do not fit the limit wait for a place, one place each. A Run that ends abnormally stops the Runs that have not started; the Runs already working go on. The project stays held until the last Run ends.

**Notifications** (`trama.ntfyServer`, default `https://ntfy.sh`, and `trama.ntfyTopic`, default empty, `"type": "string"` and `scope: application` both, the last subgroup of **Advanced** in `SETTING_GROUPS`, with the explicit titles `ntfy Server` and `ntfy Topic`; only the user value counts, `inspect(key).globalValue`, through `configuredNtfyTarget` in `agent.ts`, so a cloned repository can neither turn them on nor send them to its own server; the wizard leaves them out). With a topic set, each window sends a notification through ntfy for the jobs it launched in omp Chat conversations with Trama's hook (design, scan, Run, Resolve Drifts, Unify Drifts, import, refinement), and only for them: Ask more, General, a job in a terminal (the fallback of a conversation that does not start included) and the prepared question of the Async Drift Resolver never notify. Four kinds, each born in Waiting only if the topic is not empty at that moment: *finished* (the window stopped working because the work of a conversation ended with `end_turn`; not for Stop, for an abnormal end or when the last job ran in a terminal or was closed by the developer; at most one per window; 30 s of quiet restarted by each `session/update` of a job conversation still open or message of the developer in one, at once when none is left open; cancelled by any conversation of omp Chat that opens; not sent if the window works again when the wait ends), *question* (`question-round.ROUND_OPENED` of a round asked by a job conversation of the window, found through `context.terminal`; one per round, 30 s from then, cancelled by `question-round.ROUND_CLOSED`), *permission* (one per `session/request_permission` of a job conversation with `trama.ompChatApproval` on `ask`, 30 s, cancelled by the answer or the cancellation of the request, both taken from the session's port, `onPermissionRequest`, `onPermissionAnswered` and `onPermissionCancelled`, never from the view-model) and *stopped* (no wait: an abnormal end of a job's work from Agent running, or `omp-acp.EXITED` from Agent running, also while other jobs work; never for `EXITED` from Agent idle, for `SESSION_NOT_RESUMED` or a failed start). Nothing is born at `SESSION_RESUMED`; closing or reloading the window cancels every waiting notice and nothing is saved. The text is composed when the notice goes and is English whatever `trama.language` says: `<project> - <name> finished` (`<project> - <n> jobs finished` for several jobs), `asks a question`, `asks permission` and `stopped`, each with a fixed message, an emoji tag (`white_check_mark`, `question`, `closed_lock_with_key`, `warning`) and a priority (3 or 4); never what the agent wrote, asked or did, and no click action. The logic is pure, in `src/core/away-notices.ts` (the validity of the two settings, shared with the Settings tab, is in `src/core/ntfy.ts`); the notifier of each window, with one timer that exists only while a notice waits, is in `extension/src/host/away-notices.ts`. The host sends with the global `fetch`: `POST` to the server with a JSON body `{ topic, title, message, tags, priority }`, `Authorization: Bearer <token>` only with a saved token (`trama.ntfyToken` in `ExtensionContext.secrets`, read by `extension/src/host/ntfy-token.ts`, one per user), `redirect: "manual"` and a limit of 10 s; only a 2xx answer is a success. A failure waits 10 s and tries once more with the same text if the topic and the server are still valid; a second failure is silent, and the server, the topic and the token never appear in a message, a log or a diagnostic. The same function sends the **Send test notification** of the Settings tab, with a single attempt. On the public ntfy.sh the topic works as a password: anyone who knows it can read the notifications.

**Solo mode** is not a setting of the editor: there is no key for it in `contributes.configuration`, it is not in `SETTING_GROUPS` or `EXPLICIT_TITLES`, and `setSetting` does not accept it. It belongs to the working copy and lives in `.trama/solo/mode.json` and in a block of `.git/info/exclude` (`src/core/solo-mode.ts`, described in the project README). The check that runs at every ordinary opening of Trama (`refreshProjectSkills(project, configuredSkillsDir(), false)` in `extension/src/host/project.ts`) also calls `repairSoloBlock`: with Solo mode on it writes the block again, in silence, when it is missing or differs from the one the kind and `trama.skillsDir` need, and it adds nothing to the message `Trama: updated the agent skills to this version.`; a write that fails shows `Trama: could not update the agent skills: <reason>.` like any other failure of the check and is tried again at the next opening.

The `Solo Mode` row is the component `webview/settings/solo-mode.tsx` (`SoloModeRow`, shared by the Settings tab and the wizard's `Project` step, right after `trama.skillsDir`). The webview sends `setSoloMode { solo: "off" | "folders" | "files" }`, which `parseToHost` validates; the host (`host/solo-mode.ts`, the same in-process code as `trama project edit`, with the configured `trama.skillsDir`) writes it and answers `soloMode { available, solo, tracked }` at `ready`, every time the Settings view becomes visible (with `ompStatusWanted`), after each write and when `trama.skillsDir` changes; it is never sent without a project. A failed write is the editor error `Trama: could not save Solo Mode: <reason>.` and the row goes back to the project's value. In the wizard the choice lives in `WizardState.solo` (`null` follows the project's value, which is how the Empty Model mode opens; the first setup opens with `off`), travels in `confirmSetup` as `solo`, and the host writes it only on the confirmation: the first setup passes it to `initializeProject` (`trama project new` with `solo`, so a failure creates nothing), the Empty Model mode calls `writeSoloMode(project, solo, true)` after the settings and before the path, only when it differs from the project's value. `WorkspaceFolderView.inGit` tells the first setup whether a folder can have Solo mode.

**Manager mode** is not a setting of the editor either: no key in `contributes.configuration`, not in `SETTING_GROUPS` or `EXPLICIT_TITLES`, and `setSetting` does not accept it. It belongs to the working copy and lives in `.trama/manager/mode.json` (`{}`, in a folder with its own `.gitignore` containing `*`; present only while it is on; `src/core/manager-mode.ts`, which also parses `git remote get-url origin` through the `git()` helper of `src/core/git.ts` into `<owner>/<repo>` in lower case for `https://`, `http://`, `git@github.com:` and `ssh://git@github.com/`, with or without `.git` and a final `/`, and reads any other host as not on GitHub). Team is available when it is recorded and origin is on GitHub; the repository is read again at every opening of the panel, at every picture and whenever Settings or Team becomes visible.

The `Manager Mode` row is the component `webview/settings/manager-mode.tsx` (`ManagerModeRow`, shared by the Settings tab, right after the `Solo Mode` row, and the wizard's `Project` step, last in the step inside a bordered box below the `Repository` box, `OriginBox`). The webview sends `setManagerMode { on }`, which `parseToHost` validates; the host (`host/manager-mode.ts`, the same in-process code as `trama project edit`) writes it and answers `managerMode { available, recorded, repository, reason }` with every picture, at `ready`, every time the Settings view becomes visible (with `ompStatusWanted`) and after each write; it is never sent without a project. A failed write is the editor error `Trama: could not save Manager Mode: <reason>.` and the row goes back to the recorded value. Turning it on without origin on GitHub is refused with `Manager Mode needs a repository on GitHub (the origin remote).` and turning it off deletes only the file. The wizard keeps the choice in its state in every mode (`WizardState.manager`, `null` following the project, `false` in the first setup) and sends it in `confirmSetup` as `manager`: the first setup passes it to `initializeProject`, which gives it to `trama project new` (written after the project's files, a failure is shown and the project stays), the other modes write it with the same code as `project edit` after the settings and before going on with the path, only when it differs from the project's value, and only while origin is on GitHub, so a Manager mode left on whose origin moved away is never turned off by the wizard. The `workspaceFolders` message carries the `origin` of each folder for the first setup. The texts are in English and do not follow `trama.language`.

**The Team view and the people** (`ui#panel/Team`, `ui#person`, `tech#team`, `data#person`). `Team` is a seventh view of the panel (`ViewName` `"team"`, in `PANEL_VIEWS` and `VIEW_LABELS`; the command `trama.showTeam` after `trama.showHistory` in `SHOW_COMMANDS` and in `contributes.commands`; the side menu's `MenuState.manager` carries `managerStatus(project).available`, `projectEntries` adds the `Team` entry after History with the `Users` icon). `Controller.show("team")` does the ordinary `open()` while Team is not available; `postManager` sends `navigate` to `board` when the panel shows `team` and Team is no longer available, and the shell mounts `team` only while `ShellState.teamAvailable` (set from every `managerMode` message) is true, after History and before Settings. The people are `extension/src/host/team/people.ts` (`People(store, today, draw)`: `view`, `members`, `save`, `addToTeam`, `removeFromTeam`, `delete`, `find`; the only module that touches the key `trama.team`, with the injected `PeopleStore { get, update }`, `ExtensionContext.globalState` in `main.ts` and `memoryPeopleStore` in the tests; `setKeysForSync` is never called for it; every person is read again with `personSchema` and a write keeps the people it cannot read as they are) over `src/core/people.ts` (schemas, `checkPerson` with the messages of `rules#person`, absences, initials, the teams); the Controller takes `People` as its sixth constructor parameter and `EditorQuestions` as its fourth, which answers `trama team show` with `teamAnswer`. The webview sends `savePerson { person }`, `addToTeam`, `removeFromTeam`, `undoRemoveFromTeam` and `deletePerson { id }` (`parseToHost` checks only their shape and sizes; the host checks the values again); the host answers `team { members, others, unreadable, error }` (`error` is `Trama could not save the team: <reason>.` after a write that failed, or the notice for a value of another version), with `ready`, when the view becomes visible and after every write, followed by `managerMode`; a person that breaks `rules#person` is answered with `personRejected { errors }`, writes nothing and leaves the dialog open. `Delete person` is confirmed by the controller with `showWarningMessage("Delete <name>?", { modal: true, detail }, "Delete")`. The view is `webview/team/`: `index.tsx` (`TeamPage { team, rejection, post, github? }` and `mountTeam`), `github.tsx` (the GitHub Project's button and popover, the boxes of the state of `gh`, the skeleton and the page `Link a GitHub Project`), `people-tab.tsx`, `person-dialog.tsx` (the dialog has no trigger of its own, so `onCloseAutoFocus` gives the focus back to the button that opened it) and `logic.ts`, with `ui/tabs.tsx` from shadcn/ui over `@radix-ui/react-tabs`. All its texts are in English whatever `trama.language` says.

**The GitHub Project and the reads with `gh`** (`ui#github-project`, `rules#github-project`, `data#github-project`). `src/core/github.ts` is the only module that builds `gh` commands, all read-only, with fixed arguments, without a shell and with a timeout of 20 seconds (`GH_TIMEOUT_MS`): `gh --version`, `gh auth status --hostname github.com` and `gh api graphql` with the constant queries `PROJECTS_QUERY` (the Projects of the owner of the repository, user or organisation, and which belong to the repository) and `PROJECT_QUERY` (the fields with their options and the iterations of one Project); `findGh` looks in the `PATH` of the process, then `/opt/homebrew/bin`, `/usr/local/bin` and, on Windows, `%ProgramFiles%\GitHub CLI`, and there is no setting for it. `readGitHub` stops at the first problem, in the order `not-installed`, `not-logged-in`, `no-project-access` (the message names `read:project`, or `project` in a message about scopes) and `read-error` (`gh exited with code <n>: <first line of stderr>`); `ghProblemKind` tells the state from the stored reason. The linked Project is `.trama/manager/project.json` (`linkedGithubProject`, `linkGithubProject`, `unlinkGithubProject`; a file that does not match is not linked and the next link replaces it); only a Project with an iteration field is linked and the sprint field is the first one (`sprintField`, `currentIteration`, `offeredIterations`). The host side is `extension/src/host/team/github.ts`: `TeamGitHub` (one read at a time, the cache in the workspace state key `trama.team.github` `{ readAt, project, error }` that keeps the last good data through a failed read, `message` for the view, `details` for the output channel, `problem` for the terminal), `githubTarget` and `linkChosenProject` (only a Project of the last list is linked, with the title and the iteration flag the host read). The Controller takes the workspace state as its fifth constructor parameter, which builds the `TeamGitHub`; it reads when the Team view becomes visible and on `refreshTeam`, never on a timer, and after `linkGitHubProject` and `unlinkGitHubProject` (a failed link or unlink is a `notice` and changes nothing); `logInGitHub` runs `loginGitHub` of `host/agent.ts` (the visible terminal `Log in to GitHub` with `gh auth login --hostname github.com --web --scopes project`, or `Give access to Projects` with `gh auth refresh --hostname github.com --scopes project` when the last read said `no-project-access`) and reads again when the command ends; `showGitHubDetails` opens the output channel `Trama`. `parseToHost` validates `linkGitHubProject { owner, number }` (a non-empty owner, a positive whole number) and the four messages without fields; the host sends `teamGitHub { state, reading, repository, linked, readAt, project, projects, error }` at `ready`, when the Team view becomes visible and whenever a read starts or ends. `Create a Project on GitHub` opens `https://github.com/<owner>?tab=projects`. `trama issue fields` (`src/cli/commands/issue.ts`) prints the fields and iterations of the linked Project through the same code. Tested in `test/github.test.ts`, `test/host-team.test.ts` (with a fake `gh` first in the `PATH`), `test/host-messages.test.ts` and `test/webview-team-github.test.tsx`.

**The Decisions and Issues tabs** (`ui#proposal/Open`, `ui#issue`, `rules#issue`, `tech#issue`). `buildSnapshot` carries `handoffs` (`HandoffView` of `src/core/team-views.ts`: the open handoffs in creation order, never a Draft, with their issues, warnings and `block`) and `issues` (`IssueRowView`: the cards of `.trama/issues/` grouped by handoff and kept in publication order); a file that cannot be read leaves its list empty and goes to `diagnostics`. The Board's columns and its number never include `kind: handoff`, and `menuState` carries `handoffs` (the open ones, only with Team available), which the `Team` entry shows as a `Badge` and in its name (`entryName(view, decisions, handoffs)`). The tabs live in `webview/team/` (`decisions-tab.tsx`, `issue-preview.tsx`, `issues-tab.tsx`; pure logic in `logic.ts`, tested without DOM in `test/webview-team-decisions.test.tsx`). **Merge** (Solo mode on only; `ui#solo-merge`, `tech#solo-merge`). The core is `src/core/solo-merge.ts` (availability, branches, up-to-date check, merge, abort, the remembered merge `.trama/solo/merge.json`); the flow is `extension/src/host/solo-merge.ts` (`SoloMerge`, built in `main.ts` with `Controller.launch`): `merge()` shows the progress notification `Fetching…` while `git fetch --all --prune` runs (a failure is `Trama: could not fetch: <reason>.`), then the `QuickPick` `Merge into <current branch>` (placeholder `Choose the branch to merge`; the upstream first with the description `upstream`, then the other remote branches, then the local ones), the modal confirmation `Merge <branch> into <current branch>?` for a branch that is neither the upstream nor `<remote>/<current branch>`, and `startMerge`; `openMergeEditor()` runs `git.openMergeEditor` on the first file with conflicts, or opens the file when the command is missing; `reconcile()` launches `{ kind: "reconcileMerge", branch }`; `abort()` asks `Abort the merge of <branch>?` and runs `git merge --abort`. `state()` is the `merge` of `menuState` and `onDidChange` says when to send it again. `SoloMerge` watches `HEAD`, `MERGE_HEAD` and `index` of the git directory (`git rev-parse --git-dir`) and `refs/**` and `packed-refs` of the common one (`--git-common-dir`) with a `FileSystemWatcher`, and the files of the working copy and the saves with a 500 ms debounce, and calls `settleMerge` at every change of git, at activation and at every execution check (`startExecutionCheck`'s `onCheck`). The scan after a merge is `AgentAction` `{ kind: "mergeScan", base, incoming }`: it goes through the same `send` as `Scan System` in `Controller.launchAction`, with no confirmation, the announcement `Scanning System`, the job `scan`, the terminal name `Scan` and `rememberDeliveredScan`. The reconciliation is `{ kind: "reconcileMerge", branch }`: terminal or omp Chat conversation `Merge`, no job and no cards, `LaunchJobOptions.subAgents: false` (no limit sentence, no sub-agent sentence, no `--slow`). `parseToHost` refuses both actions from the panel (`launch` is typed `Exclude<AgentAction, { kind: "scan" | "mergeScan" | "reconcileMerge" }>`). The skill `trama-merge` ships with the others.
