# Requirements: Qualità, Panel performance

Use for the performance and reliability of the panel's views, of the picture of the project and of the side menu.

## panel

- Performance: changing the panel's view (from the side menu, a palette command, a focus or an internal link) builds no picture, reads no file of `.trama/` and starts no process in the editor host. The view changes at once, whatever the size of the project and whatever antivirus inspects files and processes. The only exceptions are the read of GitHub that the Team view starts in the background when it appears (`rules#github-project`) and the check of omp at the first show of the Settings tab in the window (`tech#panel/Settings`); neither holds the view back. What the Settings and Team views show of git (Solo mode, Manager mode, the GitHub repository) comes from what the window already knows (`quality#General`). The skills check runs only as `rules#project` says.
- Performance: one change of the files gives one picture, shared by the panel and the side menu. A picture reads and parses again only the files of `.trama/` that the editor's file watcher reported since the previous picture, Model and Requirements included; it never checks every file. Every file is checked (modification time, size and identity) only when the window opens the project and when the editor window comes back to the foreground, without holding the panel back. Its time grows linearly with the number of changed files and of cards, never with their product (for example unified Drifts by all Drifts).
- Performance: one action of the panel gives one picture: the refresh the action asks and the watcher events of the files it wrote do not build a second one. The other readers of the project in the window (the ghost item of the status bar, the execution check, the Run all estimate) take Tasks, announcements and issues from the picture, never by reading their folders again at each event.
- Reliability: a file the watcher reports, or that the full check finds changed, is read again. A file that cannot be read is an error as today, and the panel keeps its last picture. A refresh asked by an action of the panel always sees what the action wrote. A change the watcher did not report (for example made while the editor was suspended, or on a shared folder) shows at the next change of that file or at the next return of the window to the foreground.
- Acceptance exercises, on a project with some hundreds of Drifts (some unified), Proposals and History entries: switching among every view with the panel open, with no file read and no process started; a card file changed by hand that shows at the next picture; a card file changed outside the editor while the window was in the background, which shows when the window comes back; a deleted card that leaves the Board; Approve and Clear that show their result at once, with one picture each.

## menu-laterale

- Performance: when the panel changes view, and when the menu becomes visible again, the menu shows its last state at once, reading no file and starting no process; only the highlight of the view moves.
- Performance: the state of Merge (`rules#solo-merge`) is worked out in the background, never blocking the editor, and only while the menu is visible: when it becomes visible and when git's `HEAD`, `MERGE_HEAD`, `index` or refs change. Saving a file or changing any other file of the project does not work it out. While it is being worked out the menu shows the last state.
