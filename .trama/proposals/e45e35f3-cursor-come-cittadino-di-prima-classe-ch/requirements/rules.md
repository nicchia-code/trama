# Business rules

## General

## task
- A Task that is not technical must reference at least one Model element, and may add Requirements. A Technical Task must reference no Model element, only Requirements if any. Every reference must resolve to an existing Model element or Requirement section when the Task is created.
- Any move between the three columns is allowed, in either direction, from the command line (and always for the agent). The Board offers no move at all: it sends none and the editor accepts none, whether by drag, by buttons or by message.
- A Task may be linked to a Proposal when it is created; the Proposal must exist, in any status. Tasks that carry no link are never grouped.
- Design grouping: the Tasks linked to the same Proposal form one design, listed in the order they were created. A design with fewer than two Tasks is not shown as a group. The column of a design is derived: To do when every Task is in To do, Done when every Task is in Done, In progress in every other case (including a mix of To do and Done).
- A Task is runnable when it is in To do and not blocked. The next runnable Task is the runnable Task with the lowest number, worked out again each time it is asked: a Task that waits for the Task that fixes its Drift becomes runnable once that Task is Done, so the fixing Task runs first and the waiting one right after it. No other order is imposed between Tasks.
- A run (Run all To do, or implementing a design) asks for the next runnable Task, implements it, and asks again, until there is none. Run all To do considers every Task; implementing a design considers only that design's Tasks, so a fix Task, which belongs to no design, is never run by it. A run skips the Tasks that are blocked and goes on past a Drift: the Drift the agent files during the run leaves its Task In progress, blocks only the Tasks it concerns, and does not end the run. A run ends when no Task is runnable. Its report says what the agent implemented, the Drifts it filed, and the Tasks in To do left unrun, each with the Drift or the fix Task it waits for.
- Asked to implement one named Task, the agent still stops at once if that Task is blocked (see below): the order and the skipping apply only to runs over several Tasks.
- The agent takes a Task when it moves it to In progress with the command line run in the terminal Trama started for the agent (the one marked with `TRAMA_AGENT`). A move by the developer never takes a Task, and neither does a move made by an agent outside that terminal, which cannot be told from the developer's. Moving a taken Task to To do or Done, by the agent, clears the mark; moving it to In progress again keeps it.
- A Task taken by the agent cannot be moved by the developer: not with the command line run without `TRAMA_AGENT`. The Board has no way to move a Task. The refusal says the agent is working on it and points to `task take-back`. Moves by the agent are always allowed.
- Taking a Task back is a decision of the developer: it clears the mark, leaves the Task In progress and is refused to an agent. It has a command, `task take-back <id>`, refused when `TRAMA_AGENT` is set. The Board has no button for it.
- When the command running in the agent terminal ends, every Task that carries the mark is released and goes back to To do, so it can be run again. A Task is not released if the terminal cannot report that a command ended; then only `task take-back` frees it.
- Run all To do is unavailable while any Task is taken by the agent, and when no Task in To do is runnable. Run this design is unavailable while any Task of that design is taken, and when none of the design's Tasks in To do is runnable.
- A Task is blocked when an open Drift blocks it or when it is the origin of a Drift fixed in the code and the Task created for that fix is not Done. A Done Task is never blocked. Blocking is derived from the Drifts, the Tasks and their references each time it is asked; it is never stored on the Task.
- An open Drift blocks its origin Task, if it has one, and every Task that is not Done and concerns the same thing as the Drift. A Drift filed by a Scan has no origin. A Task concerns the same thing as a Drift when one of their references is the same as one of the other's or inside it: an element contains its States and Transitions, and a Machine or Feature contains its Machines and States. A Requirement section of an element also counts as that element, and the element and everything inside it as that section. The General section of an Area is equal only to itself, so it concerns only the Tasks that name it. This holds for Technical Tasks, which have only Requirement references.
- Moving a blocked Task to In progress is refused to the agent, whatever its column, and so is keeping a blocked In progress Task with another move to In progress. The refusal names the Drift that blocks it (ID and title), or the fix Task it waits for. Moves of the developer, and moves of the agent to To do or Done, are not affected. A blocked Task already In progress is not moved.

## drift
- A Drift must reference at least one Model element or Requirement, and every reference must resolve when it is created. It may only be resolved once: resolving an already resolved Drift is refused.
- A new Drift must have the sections What happens, What should happen and Fix options, each with text; creating it without one of them is refused, naming the missing one. An open Drift filed after options existed is never without them. The Where in the code section is optional; when given it must have text.
- The Fix options of a new Drift are from two to five, each with a title and a text, both non-empty, and with titles that differ from each other; otherwise creating the Drift is refused, naming the problem. The first option is the one the agent recommends.
- Fixing the code of a Drift that has options requires the number of one of them, counted from 1 in the order they are written; it is refused, saying that an option must be chosen, when none is given or the number is not that of an option, and the Drift stays Open. The developer may add a note, free text kept with the choice. A Drift without options accepts no option, and its code is fixed without choosing; a note is accepted in both cases. Accepting the attached Proposal and dismissing take neither an option nor a note: given one, they are refused.
- Fixing the code creates a Task titled "Fix code to match the Model: <Drift title>" (or "…the Requirements: …" when the Drift points only to Requirements), pointing to the Drift's references, linked to the Drift, with these as its body, in this order: What happens and What should happen, then the chosen option with its title and text and the developer's note when given, then Where in the code when the Drift has it. The chosen option's number and the note are kept in the Drift. It is a Technical Task exactly when the Drift points only to Requirements.
- The agent writes What happens and What should happen for a programmer who reads the Drift at a glance, not as a code review: what the System does and what it should do, in terms of behaviour and the words of the domain ("the cart total ignores the coupon"), not how the code does it. These are guidelines for the agent and the skills; nothing refuses a Drift for its style or length.
- The two sides and the options name no variable, function, class, field or file, unless the difference cannot be understood without it; then they name only the one or two that matter, as inline code. Where the code was seen goes only in Where in the code: files, and the code element when it helps, with no line numbers (they go stale) and no long pieces of code.
- The texts are Markdown, written to be read quickly: short paragraphs, a bulleted list when there are several separate points, bold for the one or two terms that carry the difference, no headings inside a section and no tables, about 100 words per side. Each fix option is a different way to reach what should happen, not a step of one plan, and says in terms of behaviour what changes and what it costs; about 60 words each, no headings or tables inside an option. These are guidelines for the agent and the skills, like the rest of this style.
- Accepting the attached Proposal is refused when the Drift has none, and when the Proposal cannot be approved; the refusal names the reason: still being written, rejected, discarded, already approved, stale, invalid or waiting for others.
- Dismissing a Drift is refused when it has an attached Proposal, whatever its state; the refusal says to accept that Proposal or to fix the code.
- Replacing the attached Proposal is refused unless the Drift is open, the attached Proposal is open and stale, and the new one exists, is not the attached one and was neither rejected nor discarded. It attaches the new Proposal and rejects the old one with the feedback "Replaced by Proposal <id>"; Proposals that require the old one stay blocked.
- A Drift remembers the Task the agent was implementing when it filed it (its origin); a Drift filed by a Scan has none. The origin must be an existing Task.
- Fixing the code of a Drift with an origin that is not Done moves that Task to To do and clears its mark of being taken, then the origin waits for the fix Task as described for blocked Tasks. Accepting the attached Proposal or dismissing a Drift leaves its origin where it is. Once a Drift is resolved it no longer blocks anything.

## proposal
- Every new Proposal starts as a Draft, whether it is an ordinary change, an import or one attached to a Drift. Only the agent hands it over, and only a Draft can be handed over.
- A Proposal may only require Proposals that exist and were neither rejected nor discarded when it is created. Required Proposals are applied under it in dependency order (each after the ones it requires) before it is drawn, diffed, checked for staleness or validated; approving a required Proposal therefore does not make it stale.
- A touched file is stale when its current content (on top of the required Proposals) differs from the hash recorded in `base`, or when it was recorded as new and now exists. A deleted file counts as touched.
- Editing a file of a Proposal again does not change what was recorded for it; marking for deletion a file the Proposal already holds a copy of is refused; only Drafts and open Proposals can be edited, only open Proposals can be approved or rejected, and only Drafts can be discarded or handed over.
- Registering, rewriting or marking for deletion a file of an open Proposal sends it back to Draft, even when nothing in the file ends up different; the agent must call the registering step before every change to a file so that the Proposal cannot be approved while it is being changed.
- Handing over is refused, leaving the Proposal a Draft and naming each problem, when the Model and Requirements with the Proposal applied (on top of the Proposals it requires) would have errors, or when a file it holds was never registered with it. It is not refused because the Proposal is stale or requires Proposals that are not approved yet.
- Approving, rejecting or accepting through a Drift a Draft is refused with the message that the Proposal is still being written; discarding or handing over a Proposal that is not a Draft is refused.
- Rejecting needs no feedback text: when the text is empty or only blank, the Proposal is still rejected and no Feedback section is added. Discarding needs none and appends nothing to the Proposal.
- A Proposal that requires a Draft or a discarded Proposal is blocked, with the reason "still being written" or "was discarded". Discarding never changes the Proposals that require it or the Drift it is attached to.
- The agent skills that write Proposals (design, import and scan, when they attach a Proposal to a Drift) finish by handing the Proposal over, after validating it; they tell the developer to review it only after the hand-over succeeded.

## proposal/Approved
- After an ordinary (not import) Proposal is approved, the Features to scan are those whose code it can affect: a changed Machine file or Feature description affects its own Feature; a changed Actor file affects every Feature with a Machine that reacts to that Actor's Events, before or after; the System description affects none. For Requirements, a change to an Area's description, its introductory text or its General section affects every Feature; a change to another section affects the Features of the element it names, before or after. Only Features that still exist after the approval are scanned, all in one agent run.

## agent-terminal
- The instruction sent to the agent is one line naming a skill: design → "Use the trama-design skill. <the developer's request>" (the request is asked for in an input box when the button did not carry one; an empty request sends nothing); scan of the whole System → "Use the trama-scan skill on the whole System."; scan of Features → "Use the trama-scan skill on the Feature `a`." or "…on the Features `a`, `b`."; implement → "Use the trama-implement skill on Task <id>."; implement all → "Use the trama-implement skill on every Task in the \"todo\" column. Take each one from `trama task next`, one after the other, until it says there is none."; implement a design → "Use the trama-implement skill on every Task of Proposal <id> that is in the \"todo\" column. Take each one from `trama task next --proposal <id>`, one after the other, until it says there is none."; import → "Use the trama-import skill on this repository." There is no instruction naming a Fix skill, and no button or command to ask for one.
- Reworking the stale Proposal of a Drift sends one line naming the design skill: "Use the trama-design skill, without asking questions. Proposal <p>, attached to Drift <d>, is stale: write a new Proposal that makes the same change on the current Model and Requirements, hand it over, and attach it to the Drift in place of the stale one." It is refused unless the Drift is open and its attached Proposal is open and stale.
- A scan of a Feature that does not exist in the Model is refused; an implement request is refused unless the Task exists, and an implement-a-design request unless the Proposal exists.
- Automatic scanning after an approval uses the same scan instruction, with every affected Feature in one run, followed by a sentence naming the approved Proposal and asking that every Task the scan files is linked to it. It needs the setting on, a configured agent command (or the chat launcher) and at least one affected Feature. A scan the developer starts by hand names no Proposal, so its Tasks belong to no design.
- When a language is set, every instruction above ends, on the same line, with the sentence "Write everything you generate in <language>, except code, which always stays in English." where <language> is the setting's text, trimmed, as typed. It applies to every instruction sent to the agent: design, scan, import, implement, implement all, the rework of a stale Proposal and the automatic scan. Without a language (empty or only spaces) the instruction is exactly as before.
- In the chosen language go the prose the agent produces for Trama: the bodies, descriptions and introductions of Proposals, Model files, Requirements, Tasks and Drifts, the text of questions and their options, and the agent's replies in the conversation. Always English, whatever the language: code and its comments, commit messages and the project's own documentation; the names and titles of Model elements, Requirements, Proposals, Tasks and Drifts; IDs, Event names, the section titles Trama requires (for example "General", "What happens", "What should happen", "Where in the code") and the `(initial)` and `(final)` markers.
- Changing the language changes nothing already written. When the agent edits a file written in another language it keeps the existing text and writes only the new or rewritten text in the chosen language; it does not translate the whole file.
- Nella chat di Cursor l'istruzione ha una seconda riga, dopo la frase della lingua se c'è: `The trama command may not be on your PATH. Before anything else run: export PATH="<cartella del programma trama incluso nell'estensione>:$PATH"`. Serve perché Cursor avvia i comandi dell'agente senza il PATH dell'estensione. Senza un programma incluso per questa piattaforma la riga non c'è. Con il terminale e con la chat di altri editor l'istruzione resta di una riga.
- La scansione automatica dopo l'approvazione, in Cursor, parte da sola solo se la consegna ha usato `composer.createNew`. Se ha dovuto ripiegare sul deeplink o sugli appunti, non invia nulla: mostra l'avviso «Trama: Proposal <id> was approved. Scan the Features it affects?» con il pulsante «Scan now»; il pulsante invia la stessa istruzione di scansione con la stessa catena di consegna, e chiudere l'avviso non fa nulla.
- Ogni passo della consegna alla chat di Cursor che fallisce o non esiste passa al successivo senza avvisare il developer; solo il passaggio agli appunti lo avvisa. Non si prova mai due volte lo stesso passo per lo stesso prompt, per non creare due chat con lo stesso testo.
- Una conversazione è di Trama se un prompt inviato comincia con «Use the trama-» o «/trama-», che il prompt l'abbia scritto Trama con un pulsante o il developer a mano. Un prompt che nomina una skill di Trama ma in una conversazione già di Trama è un normale `PROMPT_SUBMITTED`. Le conversazioni del progetto che non lo sono non producono mai avvisi, né rilasci di Task, né ritiro di annunci.

## announcement
- An announcement has a kind (Proposal, Task or Drift) and a title. The kind decides the column of its ghost: To decide for a Proposal or a Drift, To do for a Task.
- The agent announces a card as soon as it knows it will create it, saying the kind and the title, and gets the announcement's ID back. It passes that ID when it creates the card: when it starts the Proposal, files the Task or files the Drift. Creating a card without announcing it is allowed; it simply has no ghost.
- Trama announces a Proposal for every design request sent from the terminal launcher, at the moment the instruction is actually sent; its title is the developer's request, or "Rework of Proposal <p>" when the request is to rework the stale Proposal of a Drift, and it belongs to the terminal the instruction is typed into. The agent is not told this announcement's ID: the first Proposal the agent starts without naming an announcement takes over the oldest of these still Preparing, and the Draft's title replaces the request in the ghost.
- A Proposal the agent starts that names no announcement, with none of these waiting, makes an announcement of its own, titled like the Draft and already Writing. This is how a design sent with the chat launcher gets its ghost.
- The announcement is delivered when the card arrives: a Proposal when it is handed over (never when the hand-over is refused, which leaves the ghost), a Task or a Drift when it is filed with the announcement's ID of the same kind. An ID that is unknown, already delivered or withdrawn, or of another kind never prevents the card from being created; the output says that no such announcement was found.
- An announcement that belongs to an agent terminal is withdrawn, with the notice, when the command Trama typed into that terminal ends or that terminal is closed. The end of any other command, in that terminal or in another one, and the close of another terminal, withdraw nothing. When the terminal cannot tell that the command that ended is the one Trama typed, its end withdraws nothing; the close of the terminal and the quiet period still do.
- Every announcement still waiting, whatever terminal it belongs to, is also withdrawn, with the notice, when fifteen minutes pass without the agent announcing a card, changing a Draft it announced or filing a card. The fifteen minutes stop counting while a question round is open and start again when it closes. This is the only way, besides the editor starting up, that an announcement with no terminal is withdrawn.
- An announcement whose Draft the developer discarded is withdrawn at once, with no notice. A Draft that returns to Draft after being handed over does not bring its ghost back.
- Starting up, the extension withdraws every announcement it finds left on disk, with no notice, since the agent run that made it can no longer be told.
- A delivered or withdrawn announcement ceases to exist at once.
- Un annuncio fatto dall'agente della chat di Cursor (campo `chat`) è ritirato, con l'avviso, quando una conversazione di Trama dello stesso progetto è interrotta (`cursor-chat.AGENT_INTERRUPTED`), e senza avviso quando è chiusa (`cursor-chat.CONVERSATION_CLOSED`). Un turno concluso normalmente (`cursor-chat.AGENT_STOPPED`) non ritira nulla: ci pensano la consegna della carta o i quindici minuti di quiete.

## project
- Initializing creates, under `.trama/`: `model/system.md` (H1 is the folder name with dashes and underscores turned into spaces and the first letter capitalised, followed by a placeholder sentence), `model/actors/`, `requirements/` with five Areas that each have a description and an empty General section — `ui` (Interface), `tech` (Technology and constraints), `quality` (Quality), `data` (Data), `rules` (Business rules) — and `proposals/`, `tasks/` and `drifts/`. It installs the agent skills (trama-design with its format reference, trama-scan, trama-implement, trama-import) into the skills folder, `.agents/skills` by default. It never looks in parent folders.
- It refuses, creating nothing, when `.trama/` already exists, or when a skill file to install exists with different content, unless forced; identical files are not a conflict. The extension forces only after the developer confirms in a modal dialog.
- Updating skills overwrites the shipped skills in the chosen folder, deletes the `trama-fix` skill folder, with whatever it holds, from every skill folder that has it among `.agents/skills`, `.claude/skills`, `.github/skills` and the configured folder, creates the five starting Areas only when there is no `requirements/` folder, and regenerates the Requirement skills. The report lists the folder it deleted.
- A Requirement skill `trama-req-<area>` is generated for every Area that has any text (introduction or a non-empty section); its description is the Area's description and its body lists the introduction and each non-empty section titled by its element reference (`General` for the general one). It is written into every skill folder that already holds `trama-design` among `.agents/skills`, `.claude/skills`, `.github/skills` and the configured folder; files whose content would not change are left alone, and skills of Areas that were deleted or became empty are removed.

## question-round
- Validate the complete request before queueing or presenting anything: at least one question, unique non-empty question IDs, non-empty question text, at least two options per question, non-empty option labels, descriptions, a boolean `multi` and an integer recommendation index within the options. Refuse an invalid round with an error rather than asking a partial round.
- Accept at least one option or a non-empty free answer for an answered question. A single-choice answer cannot include multiple options. Whitespace-only free text is empty. Skipping requires the explicit confirmation action and is distinct from accepting no selection.
- Remember answers across Back navigation. Accepting a revised answer replaces that question's preceding answer; it does not duplicate it. Returning from the free-answer input or skip confirmation does not advance the round.
- `Skip this one` skips only the current question. `Skip all` skips the current and following questions, preserving accepted answers before it. The agent applies its recommendation for each skipped question and explicitly lists those decisions for the developer to verify.
- Present at most one round per editor window. Admit concurrent rounds in FIFO order, present each as a whole and do not interleave their questions. Cancelling a queued round removes only that round; finishing or abandoning the active round opens the oldest remaining one.
- Route an agent launched in a Trama terminal to its launching window. Otherwise use the most recently focused window with that same project open. Never show a project's questions in a window for a different project.
- There is no Trama response timeout. When the caller stops waiting, remove its queued round or close its active controls and discard its answers. A stopped caller must not leave an orphaned menu or block the queue.
- `trama-design` and `trama-import` use `trama ask` for every question round. Only if the editor is unavailable before admission do they fall back to the agent's own question tool, or a numbered round in conversation when no question tool exists. An input error is corrected, not treated as editor unavailability; a deliberate skip is not re-asked through the fallback.
- Losing the editor after admission interrupts every active or queued round assigned to that window and discards all answers of those incomplete rounds. The agent stops the workflow awaiting those decisions; it must not continue using partial answers, apply recommendations, fall back to another question interface, automatically retry, reroute to another window or resume the round when the editor returns. Rounds assigned to other windows are unaffected.

## notice
- Un avviso nasce solo se in quel momento l'impostazione dell'argomento ntfy non è vuota e l'agente è stato avviato da Trama in un proprio terminale o in una conversazione della chat di Cursor che Trama riconosce come propria (la chat di un altro editor non genera avvisi, né quelli sulle domande né quelli sulla fine; neppure un agente avviato dal developer per conto suo, a meno che il suo prompt nomini una skill di Trama in Cursor). Un'impostazione fatta mentre un round è già aperto o un comando è già finito non genera avvisi su di essi. Se è non vuota ma non valida, l'avviso nasce comunque e finisce in Not sent quando scadono i dieci secondi.
- L'avviso su una domanda nasce quando un round chiesto da un agente che gira in un terminale avviato da Trama (quello a cui Trama dà l'indirizzo della finestra) diventa quello presentato nella sua finestra, non quando è in coda. Un round chiesto da qualunque altro agente non genera avvisi, salvo quello dell'agente di Cursor descritto sotto. Ne nasce uno solo per round, qualunque sia il numero di domande. I dieci secondi partono da quel momento e non ripartono con una risposta, un salto o un ritorno indietro. Se il round si chiude prima, perché risposto, saltato o abbandonato, l'avviso è annullato.
- Un round chiesto dall'agente della chat di Cursor (`trama ask` con `CURSOR_AGENT=1`) genera l'avviso sulla domanda allo stesso modo, nella finestra più recentemente attiva con il progetto aperto.
- Quando l'avviso su una domanda parte, mostra la domanda che il developer ha davanti in quel momento, anche se è la domanda a cui sta scrivendo una risposta libera o su cui sta confermando un salto, con la sua posizione nel round. Se il round è già chiuso a quel punto, l'avviso è già stato annullato e non parte.
- L'avviso sulla fine del comando nasce solo per la fine del comando che Trama ha scritto nel terminale dell'agente, con la regola degli annunci: la fine di un altro comando, o una fine senza la riga di comando di Trama, non genera nulla. La chiusura del terminale non ne genera. Due comandi che finiscono in due terminali diversi generano due avvisi.
- Nella chat di Cursor l'avviso sulla fine nasce a ogni `cursor-chat.AGENT_STOPPED` e a ogni `cursor-chat.AGENT_INTERRUPTED` di una conversazione di Trama, e non a `cursor-chat.CONVERSATION_CLOSED`. Due turni che finiscono in due conversazioni diverse generano due avvisi.
- I dieci secondi dell'avviso sulla fine partono dalla fine del comando. Qualunque istruzione che Trama scrive davvero in un terminale per l'agente prima dello scadere, da bottone o da scansione automatica, annulla tutti gli avvisi sulla fine ancora in attesa, di tutti i terminali. Un'istruzione non inviata (richiesta vuota, comando non scelto, richiesta rifiutata) o mandata alla chat non annulla nulla.
- Ogni `cursor-chat.PROMPT_SUBMITTED` di una conversazione di Trama annulla gli avvisi sulla fine del turno ancora in attesa dello stesso progetto.
- Il testo si compone quando l'avviso parte, non quando nasce, e il secondo tentativo manda lo stesso testo del primo senza ricomporlo. Il riepilogo della Board dell'avviso sulla fine conta: da decidere = Proposal aperte (mai quelle in scrittura) più Drift aperti; Task in To do; Task in In progress.
- Priorità e tag: domanda priorità 4, tag `question`; fine con comando finito bene (stato 0) priorità 3, tag `white_check_mark`; fine con errore (stato diverso da 0) priorità 4, tag `warning`; fine con esito non riportato dal terminale priorità 3, tag `white_check_mark`.
- Nella chat di Cursor la fine normale ha priorità 3, tag `white_check_mark`; la fine interrotta o in errore ha priorità 4, tag `warning`.
- Il messaggio è lungo al massimo 4000 byte in UTF-8: se è più lungo, si taglia a un confine di carattere e termina con `…`, rispettando comunque il limite. Il taglio colpisce prima le ultime opzioni; la riga del progetto e la posizione nel round restano.
- Un invio fallito, compreso quello senza richiesta per un valore non valido, mostra nell'editor un avviso con il motivo, una sola volta: non lo mostra di nuovo finché non riesce almeno un invio. Il secondo tentativo dopo un fallimento è uno solo, dopo dieci secondi; se nel frattempo l'argomento è stato tolto o è diventato non valido, non parte.
- Un avviso, riuscito o fallito, non cambia nulla nel round, nei Task, nelle Proposal, nei Drift né nell'agente.
