# Regole dei Drift

## drift
- A Drift must reference at least one Model element or Requirement, and every reference must resolve when it is created. It may only be resolved once: resolving an already resolved Drift is refused.
- A new Drift must have the sections What happens, What should happen and Fix options, each with text; creating it without one of them is refused, naming the missing one. An open Drift filed after options existed is never without them. The Where in the code section is optional; when given it must have text.
- The Fix options of a new Drift are from two to five, each with a title and a text, both non-empty, and with titles that differ from each other; otherwise creating the Drift is refused, naming the problem. The first option is the one the agent recommends.
- La Proposal allegata a un nuovo Drift dev'essere una Draft o aperta e non già allegata a un altro Drift aperto; altrimenti la creazione del Drift è rifiutata, dicendo perché (approvata, rifiutata, scartata, o allegata al Drift `<id>`). Una Proposal è allegata a un Drift aperto quando un Drift aperto la nomina; un Drift risolto non trattiene più la sua Proposal.
- Tenere ciò che dovrebbe succedere su un Drift con una Proposal allegata, nello stesso passo, rifiuta la Proposal aperta con il feedback «Drift <id> resolved by fixing the code» oppure scarta la Draft, senza feedback; una Proposal già approvata, rifiutata o scartata resta com'è. Le Proposal che la richiedono restano bloccate, come per ogni rifiuto o scarto.
- Fixing the code of a Drift that has options requires the number of one of them, counted from 1 in the order they are written; it is refused, saying that an option must be chosen, when none is given or the number is not that of an option, and the Drift stays Open. The developer may add a note, free text kept with the choice. A Drift without options accepts no option, and its code is fixed without choosing; a note is accepted in both cases. Accepting the attached Proposal and dismissing take neither an option nor a note: given one, they are refused.
- Fixing the code creates a Task titled "Fix code to match the Model: <Drift title>" (or "…the Requirements: …" when the Drift points only to Requirements), pointing to the Drift's references, linked to the Drift, with these as its body, in this order: What happens and What should happen, then the chosen option with its title and text and the developer's note when given, then Where in the code when the Drift has it. The chosen option's number and the note are kept in the Drift. It is a Technical Task exactly when the Drift points only to Requirements.
- The agent writes What happens and What should happen for a programmer who reads the Drift at a glance, not as a code review: what the System does and what it should do, in terms of behaviour and the words of the domain ("the cart total ignores the coupon"), not how the code does it. These are guidelines for the agent and the skills; nothing refuses a Drift for its style or length.
- The two sides and the options name no variable, function, class, field or file, unless the difference cannot be understood without it; then they name only the one or two that matter, as inline code. Where the code was seen goes only in Where in the code: files, and the code element when it helps, with no line numbers (they go stale) and no long pieces of code.
- The texts are Markdown, written to be read quickly: short paragraphs, a bulleted list when there are several separate points, bold for the one or two terms that carry the difference, no headings inside a section and no tables, about 100 words per side. Each fix option is a different way to reach what should happen, not a step of one plan, and says in terms of behaviour what changes and what it costs; about 60 words each, no headings or tables inside an option. These are guidelines for the agent and the skills, like the rest of this style.
- Accepting the attached Proposal is refused when the Drift has none, and when the Proposal cannot be approved; the refusal names the reason: still being written, rejected, discarded, already approved, stale, invalid or waiting for others.
- Dismissing a Drift is refused when it has an attached Proposal, whatever its state; the refusal says to accept that Proposal or to fix the code.
- Approvare una risoluzione risolve, nello stesso passo, ogni Drift della sua lista ancora aperto con la decisione registrata, con le regole della riga di comando: `fix-code` crea il Task di correzione con l'opzione e la nota registrate e muove l'origine come scritto sotto; `proposal` e `dismissed` chiudono il Drift con quella `resolution`, e `dismissed` vale anche quando una Proposal è allegata. Ogni Drift risolto così prende `resolvedBy`. La Proposal allegata a ciascuno è rifiutata con il feedback «Drift <id> resolved by Proposal <id>», o scartata senza feedback se è una Draft; una già approvata, rifiutata o scartata resta com'è. Un Drift della lista già risolto in altro modo è saltato senza errore, e l'approvazione dice quali.
- Il rifacimento della Proposal obsoleta di un Drift non esiste più: `trama drift replace-proposal` è tolto, e una Proposal allegata obsoleta resta com'è finché il Drift non è risolto.
- A Drift remembers the Task the agent was implementing when it filed it (its origin); a Drift filed by a Scan has none. The origin must be an existing Task.
- Fixing the code of a Drift with an origin that is not Done moves that Task to To do and clears its mark of being taken, then the origin waits for the fix Task as described for blocked Tasks. Accepting the attached Proposal or dismissing a Drift leaves its origin where it is. Once a Drift is resolved it no longer blocks anything.

## drift-resolution
- Resolve Drifts si può lanciare solo quando c'è almeno un Drift aperto, nessuna Proposal con `kind: resolution` è `draft` o `open` e Drift resolution è in Free. Run all To do, Run this design e il Run di un Task non si lanciano mentre è in Resolving. Il pannello disabilita i pulsanti, e l'host controlla di nuovo quando la richiesta arriva, come per `Run all To do`: una richiesta che non passa non invia nulla e il developer è avvisato del motivo.
- Un lavoro (un Run o Resolve Drifts) è in corso dal momento in cui la sua istruzione è scritta nel terminale o inviata dalla chat da sola. Un'istruzione lasciata pronta nella chat o copiata negli appunti non apre nessun lavoro in corso.
- Un lavoro in un terminale finisce con la fine del comando che Trama vi ha scritto, con le stesse regole che ritirano gli annunci (la fine di un altro comando non conta), o con la chiusura di quel terminale. Un lavoro nella chat di Cursor finisce con la prima fine di turno, interruzione o chiusura di una conversazione di Trama dello stesso progetto che arriva dopo il suo invio.
- La quiete vale solo per un lavoro in una finestra del terminale esterno, in un terminale integrato che non segnala la fine dei comandi o nella chat di un editor che non è Cursor: il lavoro è considerato finito dopo quindici minuti senza un comando di `trama` dell'agente che cambi qualcosa (annuncio, Proposal nuova, file o decisione registrati, consegna, Drift o Task archiviato, Task spostato) dal suo terminale o dalla chat. I quindici minuti si fermano mentre un round di domande è aperto e ripartono quando si chiude.
- Più Run possono essere in corso insieme; Drift resolution torna in Free solo quando sono finiti tutti. Resolve Drifts lancia sempre un solo agente.
- L'istruzione di Resolve Drifts copre i Drift aperti al momento dell'invio; quelli archiviati dopo, per esempio da una scansione che lavora intanto, restano per la volta seguente.
