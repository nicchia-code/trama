# Business rules

## General

## task
- A Task that is not technical must reference at least one Model element, and may add Requirements. A Technical Task must reference no Model element, only Requirements if any. Every reference must resolve to an existing Model element or Requirement section when the Task is created.
- Any move between the three columns is allowed, in either direction. The Board refuses dropping a card on the To decide column or on the column it already is in.
- A Task may be linked to a Proposal when it is created; the Proposal must exist, in any status. Tasks that carry no link are never grouped.
- Design grouping: the Tasks linked to the same Proposal form one design, listed in the order they were created. A design with fewer than two Tasks is not shown as a group. The column of a design is derived: To do when every Task is in To do, Done when every Task is in Done, In progress in every other case (including a mix of To do and Done).
- Implementing a design asks the agent to work only on that design's Tasks still in To do, in order, one after the other, skipping the Tasks that are blocked and going on with the others, also after it files a Drift. The action is not available when the design has no Task in To do.
- The agent takes a Task when it moves it to In progress with its tools, or with the command line run in the terminal Trama started for the agent (the one marked with `TRAMA_AGENT`). A move by the developer never takes a Task, and neither does a move made by an agent outside that terminal, which cannot be told from the developer's. Moving a taken Task to To do or Done, by the agent, clears the mark; moving it to In progress again keeps it.
- A Task taken by the agent cannot be moved by the developer: not with the Board's arrows or drag, not with the move message the Board sends the editor, and not with the command line run without `TRAMA_AGENT`. The refusal says the agent is working on it and points to Take back. Moves by the agent are always allowed.
- Taking a Task back is a decision of the developer: it clears the mark, leaves the Task In progress and is refused to an agent. It has a command, `task take-back <id>`, refused when `TRAMA_AGENT` is set, and a button on the Task's card.
- When the command running in the agent terminal ends, every Task that carries the mark is released; the Task stays where it is. A Task is not released if the terminal cannot report that a command ended.
- Run all To do is unavailable while any Task is taken by the agent. Run this design is unavailable while any Task of that design is taken.
- A Task is blocked when an open Drift blocks it or when it is the origin of a Drift fixed in the code and the Task created for that fix is not Done. A Done Task is never blocked. Blocking is derived from the Drifts, the Tasks and their references each time it is asked; it is never stored on the Task.
- An open Drift blocks its origin Task, if it has one, and every Task that is not Done and concerns the same thing as the Drift. A Drift filed by a Scan or a Fix has no origin. A Task concerns the same thing as a Drift when one of their references is the same as one of the other's or inside it: an element contains its States and Transitions, and a Machine or Feature contains its Machines and States. A Requirement section of an element also counts as that element, and the element and everything inside it as that section. The General section of an Area is equal only to itself, so it concerns only the Tasks that name it. This holds for Technical Tasks, which have only Requirement references.
- Moving a blocked Task to In progress is refused to the agent, whatever its column, and so is keeping a blocked In progress Task with another move to In progress. The refusal names the Drift that blocks it (ID and title), or the fix Task it waits for. Moves of the developer, and moves of the agent to To do or Done, are not affected. A blocked Task already In progress is not moved.

## drift
- A Drift must reference at least one Model element or Requirement, and every reference must resolve when it is created. It may only be resolved once: resolving an already resolved Drift is refused.
- A new Drift must have both sections, What happens and What should happen, each with text; creating it without one of them is refused, naming the missing one. An open Drift is never without both.
- Fixing the code creates a Task titled "Fix code to match the Model: <Drift title>" (or "…the Requirements: …" when the Drift points only to Requirements), pointing to the Drift's references, linked to the Drift, with the Drift's two sections as its body. It is a Technical Task exactly when the Drift points only to Requirements.
- Accepting the attached Proposal is refused when the Drift has none, and when the Proposal cannot be approved; the refusal names the reason: still being written, rejected, discarded, already approved, stale, invalid or waiting for others.
- Dismissing a Drift is refused when it has an attached Proposal, whatever its state; the refusal says to accept that Proposal or to fix the code.
- Replacing the attached Proposal is refused unless the Drift is open, the attached Proposal is open and stale, and the new one exists, is not the attached one and was neither rejected nor discarded. It attaches the new Proposal and rejects the old one with the feedback "Replaced by Proposal <id>"; Proposals that require the old one stay blocked.
- A Drift remembers the Task the agent was implementing when it filed it (its origin); a Drift filed by a Scan or a Fix has none. The origin must be an existing Task.
- Fixing the code of a Drift with an origin that is not Done moves that Task to To do and clears its mark of being taken, then the origin waits for the fix Task as described for blocked Tasks. Accepting the attached Proposal or dismissing a Drift leaves its origin where it is. Once a Drift is resolved it no longer blocks anything.

## proposal
- Every new Proposal starts as a Draft, whether it is an ordinary change, an import or one attached to a Drift. Only the agent hands it over, and only a Draft can be handed over.
- A Proposal may only require Proposals that exist and were neither rejected nor discarded when it is created. Required Proposals are applied under it in dependency order (each after the ones it requires) before it is drawn, diffed, checked for staleness or validated; approving a required Proposal therefore does not make it stale.
- A touched file is stale when its current content (on top of the required Proposals) differs from the hash recorded in `base`, or when it was recorded as new and now exists. A deleted file counts as touched.
- Editing a file of a Proposal again does not change what was recorded for it; marking for deletion a file the Proposal already holds a copy of is refused; only Drafts and open Proposals can be edited, only open Proposals can be approved or rejected, and only Drafts can be discarded or handed over.
- Registering, rewriting or marking for deletion a file of an open Proposal sends it back to Draft, even when nothing in the file ends up different; the agent must call the registering step before every change to a file so that the Proposal cannot be approved while it is being changed.
- Handing over is refused, leaving the Proposal a Draft and naming each problem, when the Model and Requirements with the Proposal applied (on top of the Proposals it requires) would have errors, or when a file it holds was never registered with it. It is not refused because the Proposal is stale or requires Proposals that are not approved yet.
- Approving, rejecting or accepting through a Drift a Draft is refused with the message that the Proposal is still being written; discarding or handing over a Proposal that is not a Draft is refused.
- Rejecting needs no feedback text: when the text is empty or only blank, the Proposal is still rejected and no Feedback section is added. Discarding needs none and appends nothing to the Proposal.
- A Proposal that requires a Draft or a discarded Proposal is blocked, with the reason "still being written" or "was discarded". Discarding never changes the Proposals that require it or the Drift it is attached to.
- The agent skills that write Proposals (design, import, scan and fix, when they attach a Proposal to a Drift) finish by handing the Proposal over, after validating it; they tell the developer to review it only after the hand-over succeeded.

## proposal/Approved
- After an ordinary (not import) Proposal is approved, the Features to scan are those whose code it can affect: a changed Machine file or Feature description affects its own Feature; a changed Actor file affects every Feature with a Machine that reacts to that Actor's Events, before or after; the System description affects none. For Requirements, a change to an Area's description, its introductory text or its General section affects every Feature; a change to another section affects the Features of the element it names, before or after. Only Features that still exist after the approval are scanned, all in one agent run.

## agent-terminal
- The instruction sent to the agent is one line naming a skill: design → "Use the trama-design skill. <the developer's request>" (the request is asked for in an input box when the button did not carry one; an empty request sends nothing); fix → "Use the trama-fix skill. <the developer's description of the problem>" (asked for and refused when empty in the same way); scan of the whole System → "Use the trama-scan skill on the whole System."; scan of Features → "Use the trama-scan skill on the Feature `a`." or "…on the Features `a`, `b`."; implement → "Use the trama-implement skill on Task <id>."; implement all → "Use the trama-implement skill on every Task in the \"todo\" column, in order, one after the other. Stop at the first Drift you file."; implement a design → "Use the trama-implement skill on every Task of Proposal <id> that is in the \"todo\" column, in order, one after the other. Stop at the first Drift you file."; import → "Use the trama-import skill on this repository."
- Reworking the stale Proposal of a Drift sends one line naming the design skill: "Use the trama-design skill, without asking questions. Proposal <p>, attached to Drift <d>, is stale: write a new Proposal that makes the same change on the current Model and Requirements, hand it over, and attach it to the Drift in place of the stale one." It is refused unless the Drift is open and its attached Proposal is open and stale.
- A scan of a Feature that does not exist in the Model is refused; an implement request is refused unless the Task exists, and an implement-a-design request unless the Proposal exists.
- Automatic scanning after an approval uses the same scan instruction, with every affected Feature in one run, followed by a sentence naming the approved Proposal and asking that every Task the scan files is linked to it. It needs the setting on, a configured agent command (or the chat launcher) and at least one affected Feature. A scan the developer starts by hand names no Proposal, so its Tasks belong to no design.

## project
- Initializing creates, under `.trama/`: `model/system.md` (H1 is the folder name with dashes and underscores turned into spaces and the first letter capitalised, followed by a placeholder sentence), `model/actors/`, `requirements/` with five Areas that each have a description and an empty General section — `ui` (Interface), `tech` (Technology and constraints), `quality` (Quality), `data` (Data), `rules` (Business rules) — and `proposals/`, `tasks/` and `drifts/`. It installs the agent skills (trama-design with its format reference, trama-scan, trama-implement, trama-import, trama-fix) into the skills folder, `.agents/skills` by default. It never looks in parent folders.
- It refuses, creating nothing, when `.trama/` already exists, or when a skill file to install exists with different content, unless forced; identical files are not a conflict. The extension forces only after the developer confirms in a modal dialog.
- Updating skills overwrites the shipped skills in the chosen folder, creates the five starting Areas only when there is no `requirements/` folder, and regenerates the Requirement skills.
- A Requirement skill `trama-req-<area>` is generated for every Area that has any text (introduction or a non-empty section); its description is the Area's description and its body lists the introduction and each non-empty section titled by its element reference (`General` for the general one). It is written into every skill folder that already holds `trama-design` among `.agents/skills`, `.claude/skills`, `.github/skills` and the configured folder; files whose content would not change are left alone, and skills of Areas that were deleted or became empty are removed.

## question-round
- Validate the complete request before queueing or presenting anything: at least one question, unique non-empty question IDs, non-empty question text, at least two options per question, non-empty option labels, descriptions, a boolean `multi` and an integer recommendation index within the options. Refuse an invalid round with an error rather than asking a partial round.
- Accept at least one option or a non-empty free answer for an answered question. A single-choice answer cannot include multiple options. Whitespace-only free text is empty. Skipping requires the explicit confirmation action and is distinct from accepting no selection.
- Remember answers across Back navigation. Accepting a revised answer replaces that question's preceding answer; it does not duplicate it. Returning from the free-answer input or skip confirmation does not advance the round.
- `Skip this one` skips only the current question. `Skip all` skips the current and following questions, preserving accepted answers before it. The agent applies its recommendation for each skipped question and explicitly lists those decisions for the developer to verify.
- Present at most one round per editor window. Admit concurrent rounds in FIFO order, present each as a whole and do not interleave their questions. Cancelling a queued round removes only that round; finishing or abandoning the active round opens the oldest remaining one.
- Route an agent launched in a Trama terminal to its launching window. Otherwise use the most recently focused window with that same project open. Never show a project's questions in a window for a different project.
- There is no Trama response timeout. When the caller stops waiting, remove its queued round or close its active controls and discard its answers. A stopped caller must not leave an orphaned menu or block the queue.
- `trama-design`, `trama-fix` and `trama-import` prefer `trama_ask` for every question round. When agent tools are unavailable they use `trama ask`. Only if the editor is unavailable before admission do they fall back to the agent's own question tool, or a numbered round in conversation when no question tool exists. An input error is corrected, not treated as editor unavailability; a deliberate skip is not re-asked through the fallback.
- Losing the editor after admission interrupts every active or queued round assigned to that window and discards all answers of those incomplete rounds. The agent stops the workflow awaiting those decisions; it must not continue using partial answers, apply recommendations, fall back to another question interface, automatically retry, reroute to another window or resume the round when the editor returns. Rounds assigned to other windows are unaffected.
