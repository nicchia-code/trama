# Handoffs and issues

## team
- The handoff skill (`trama-handoff`) reads the whole request, explores the Model, the Requirements and the code as `trama-design` does, reads the team with `trama team show`, the linked Project's fields and iterations with `trama issue fields`, the open issues of the team with `gh`, and the issues of the other open handoffs with `trama proposal list` and `trama proposal show <id>`, to know each person's load. It interviews the Manager in rounds of `trama question new` like the design, on behaviour first, then on how the work is cut into issues. It never asks about images.
- It writes the Model and the Requirements like a design when the request changes behaviour, then the issues. Each issue is a piece of work one person finishes in one sprint with room for the review: the agent aims at 3 days or less and splits larger work, unless the Manager said otherwise. Dependencies between issues are explicit; an issue never depends on one published later.
- For each issue it proposes: the assignee among the members of the team, from their skills, their level, who last changed the files involved (`git log`) and their load in the sprint; a reviewer who is another member, who knows the area and did not write the work; an estimate in days in steps of 0.5; the first sprint, from the current one on, where the assignee has room for it given capacity and absences and where its dependencies are done before or in the same sprint by the same person; a value for every other field of the Project that it can choose, and none for the fields it cannot nor for the Project's estimate field (`rules#issue/Published`), which publication fills with the estimate. A person's load in a sprint is the sum of the estimates of the open items of the linked Project assigned to them in that sprint (`rules#issue/Published`) and of the issues of the other open handoffs assigned to them in that sprint, each with the Manager's values applied.
- It writes the body for the assignee's level (`rules#issue`) in the language of Trama's instruction, without images and without any reference to Trama, and puts the Model elements and Requirement sections the issue is about in `refs`.
- It opens the handoff with `trama proposal new` and `kind: handoff`, a short label that names the epic, and a body that says why and lists the decisions of the interview; the first one bound to the request with `request`. It hands it over with `trama proposal move <id> open`, reads the warnings in the output and tells the Manager about them, then stops: deciding is the Manager's, in the Team view.
- Rework with feedback, Split and Replan use the same skill: Split rewrites only the named issue into issues that each fit a sprint, keeps the other issues and the Manager's changes to them, and hands the same handoff over again; Replan follows `rules#developer.REPLAN_HANDOFFS`.

## proposal/Draft
- `trama proposal new` with `kind: handoff` is refused, creating nothing, when Team is not available, with the reason of `rules#manager-mode`.
- The hand-over of a handoff is refused, naming each problem, when: Team is not available; it has no issue; an issue has no title or an empty body; an issue's assignee or reviewer is not a member of the project's team, or both are the same person; an estimate is not a number from 0.5 in steps of 0.5; a `dependsOn` names an issue that is neither in the handoff nor in a handoff it requires, or the dependencies make a cycle; a reference in `refs` does not exist with the handoff applied; the label is missing, empty, on more lines or longer than 30 characters; the handoff has `tasks/`. The members of the team come from the editor (`cli#team`): when the editor cannot answer, the hand-over is refused with the reason of `cli#team`.
- Warnings, which never refuse the hand-over and show in its output, in `trama proposal show` and in the issue preview: each scope entry (`rules#proposal/Approved`) that no issue names or contains in `refs` (`Not covered: <ref>`), and each issue estimated more than 3 days (`Estimated <n> d: more than 3 days per issue`). A handoff has no `## Already present` check.
- A handoff is blocked like any Proposal (stale, requiring unapproved Proposals, invalid with it applied) and also, only for approving, while no GitHub Project is linked (`Link a GitHub Project first`) or Team is not available.

## developer.CHANGE_ISSUE_FIELD
- Only on an open handoff, never on a Draft, and not while an agent is writing it. Values accepted: `assignee` and `reviewer` a member of the team or none, never the same person; `estimate` a number from 0.5 in steps of 0.5 (`Enter 0.5 days or more, in steps of 0.5.`); `sprint` an iteration of the linked Project that has not ended, or none (`Choose a sprint that has not ended.`); a single-select field one of its options; a number field a number; a text field at most 1,000 characters. A value equal to the agent's removes the key from `manager`: that is the undo.
- The change never sends the handoff back to Draft and is not seen by the agent as a change of its own: an agent that reworks, splits or replans the handoff keeps the Manager's values of the issues it does not rewrite.

## developer.SPLIT_ISSUE
- Available on an issue estimated more than 3 days of an open handoff, when the agent that handed it over has finished its turn, no agent is writing the handoff and no Run launched from this window is in progress; otherwise `Split` is disabled with the reason, in this order: `The agent is still finishing`, `The agent is writing this handoff`, `A run is in progress`.
- The instruction is one line: "Use the trama-handoff skill to split issue <issue id> of handoff <handoff id> into issues that each fit a sprint, on the same handoff." The terminal is named `Split <short number>` and uses the model role of the design (`rules#agent-launching`).

## developer.REPLAN_HANDOFFS
- `Replan` is available when a GitHub Project is linked, at least one handoff is open, every agent that handed over an open handoff has finished its turn, no agent is writing a handoff (a Draft handoff an agent is writing, or a handoff request, Split or Rework with feedback of a handoff whose agent has not finished its turn), no Run launched from this window is in progress and no Replan launched from this window is running; otherwise it is disabled with the first reason, in this order: `Link a GitHub Project first`, `No handoff waits for a decision`, `The agent is still finishing`, `An agent is writing a handoff`, `A run is in progress`, `Replan is already running`. A Replan is running from its launch until its agent ends its turn or its terminal or conversation closes; Trama keeps this in the memory of the window, like the other jobs (`data#drift-resolution`).
- Clicking it asks for confirmation (`ui#proposal/Open`); only the confirmation launches the agent. The instruction is one line, naming every handoff open at the confirmation, stale ones included: "Use the trama-handoff skill to replan together the issues of the open handoffs <handoff id>, <handoff id>, …." The terminal is named `Replan` and uses the model role of the design (`rules#agent-launching`); it may not file Drifts, and its ghost (`Replanning handoffs`) shows in the status bar, never in a Board column. If the instruction does not leave, nothing changes and the Team view says why.
- The skill asks the Manager nothing. It reads the team, the Project's fields and iterations, the open items of the linked Project with `gh` and every handoff named in the instruction with `trama proposal show <id>`, then plans again together the issues of the named handoffs that are not stale, with the rules of `rules#team` for assignee, reviewer, estimate and sprint. The fixed load of each person and sprint is the open items of the linked Project and the issues of the stale handoffs; the issues it replans count with the values it gives them.
- It may change, in an issue, only its own values of `sprint`, `assignee`, `reviewer` and `estimate`, and the estimate only to fit the issue in a sprint. A field that has a Manager's value (`manager`) is a constraint: the agent keeps its value as the Manager set it and leaves its own value of that field as it was. It never writes `manager`, never adds, removes, splits or moves issues between handoffs, never changes `dependsOn`, `refs`, the title or the other fields of the Project, and never touches a stale handoff. Dependencies stay satisfied: an issue's sprint never comes before the sprint of an issue it depends on, unless both have the same assignee and sprint.
- When an issue's assignee changes to a person of another level, the agent rewrites both parts of its body for the new level (`rules#issue`), in the language of the body; otherwise the body does not change.
- In the body of each handoff where it changed at least one issue, the agent writes a section `## Replan` with one line per changed issue saying what moved (from and to) and why, in the language of Trama's instruction; it also names there each sprint and person left over capacity because of the Manager's values. A later Replan rewrites that section. A handoff with no change keeps its files untouched and stays Open.
- It hands over every handoff it changed with `trama proposal move <id> open`, reads the warnings and tells the Manager about them, then stops.
