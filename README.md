# Trama

**T**asks · **R**equirements · **A**nalysis · **M**ap · **A**gents

**Your AI agent writes code fast. Trama makes sure it's the code you meant.**

Trama keeps a map of your app next to your code: every state it can be in, and the events that move it from one to the next, written as plain Markdown in `.trama/` and drawn for you as a diagram. Your agent reads the map before it writes a line. Every change to the design arrives as a **Proposal** you approve before any code exists. When the code and the map stop telling the same story, Trama raises a **Drift**, and you decide which one is right.

Trama is an editor extension. It never calls a model: the work is done by the agent you already use, with your subscription.

## How it works

1. **Describe a change** in plain words, as you'd tell a colleague.
2. **Answer the agent's questions**: only what it can't decide alone, with its recommendation already selected.
3. **Approve the Proposal**: the change drawn on the map, with every decision and assumption beside it.
4. **Run the Tasks**: the agent builds what you approved while you follow along on the Board.
5. **Resolve the Drifts**: fix the code, or keep it and update the map. Until you decide, no Task touches that part of the app.

Your rules (tech stack, design, data, business rules) live next to the map as **Requirements**, and the agent follows them on every Task.

## Requirements

- VS Code 1.106 or later with the Trama extension: it is the only editor Trama supports.
- Linux (x64), macOS (Apple silicon) or Windows (x64, preview).
- omp, the only agent Trama supports. It is required: Trama finds it in `trama.ompPath` or, when that is empty, in your `PATH`, then in `~/.bun/bin` and `~/.local/bin`; when it is missing Trama offers to install it with omp's official installer, and before every launch it checks for a newer omp and updates it by itself.
- The GitHub CLI (`gh`), only for Team (see below): logged in with access to Projects. Team uses it only to read; Trama looks for it in your `PATH`, then in `/opt/homebrew/bin` and `/usr/local/bin` (on Windows also in `%ProgramFiles%\GitHub CLI`). Without Team Trama never needs it.

The `trama` command line comes inside the extension: there's nothing else to install.

## Install

Download the `.vsix` for your platform from [Releases](https://github.com/nicchia-code/trama/releases), then run **Extensions: Install from VSIX…** from the command palette, or:

```sh
code --install-extension trama-<platform>-<version>.vsix
```

> **Windows is in preview**: it is tested on CI but not yet by hand. `trama.exe` is not signed, so SmartScreen or an antivirus may warn the first time it runs.

## Use

1. **Open your project** and click the Trama logo in the Activity Bar: the Trama menu opens in the side bar. Choose **Board**, **Diagram** or any other entry to open the panel on it (the same entries are the `Trama: Show …` commands of the palette).
2. **Set it up.** In a folder without a Trama project the panel opens on **Get Started**, a step-by-step setup (`Set up Trama`): choose **Import from Code** (the agent maps the app you already have) or **Start from Scratch**, check omp, pick the models omp uses, and confirm a summary of your choices. The steps appear at the top, each earlier one is a button that takes you back with your choices kept, and **Back**, **Next** and the confirmation stay in a bar at the bottom. Nothing is written until you confirm the summary.
3. **Ask for a change.** On the Board, click **+ Add Work Item**, write what you want in the tab that opens, and send it with **Send to agent** (closing the tab sends it too).
4. **Decide.** Answer the agent's questions, then **Approve** or **Reject** its Proposal.
5. **Build.** Click **Run all** and the agent implements the Tasks.
6. **Keep the map honest.** **Scan System** in the side menu has the agent compare the code with the map. Each Drift it finds offers ways to fix the code: **Resolve** it or **Dismiss Drift**.

Every setting is in the **Settings** tab of the panel, which saves to your user settings; **Guided setup** there (top right) walks you through the main ones again, step by step, with each setting explained under its title.

To use a model with a subscription (ChatGPT, Anthropic, GitHub Copilot, Google Gemini CLI, Google Antigravity, Cursor or xAI Grok), open the **omp** group of the **Settings** tab, or the `omp` step of the wizard, and press **Log in** on the provider's row of the **Providers** section (**Log in again** when it already shows **Connected**). Trama opens a terminal named `Log in to <provider>` where omp runs `omp login <provider>`: omp opens the browser or shows a code, and you finish the login there. When the command ends, Trama checks omp again and updates the **Connected** marks; it never reads the terminal or your credentials.

For Cursor you can also give Trama a **Cursor API key**: press **Set API key** on the Cursor row of the **Providers** section (**Change API key** and **Remove API key** appear once one is saved), paste a user API key from the Cursor dashboard in the masked box the editor opens, and Trama saves it in the editor's secret storage (`trama.cursorApiKey`), one key per user shared by every window and project; the key never goes into a file, a setting, the panel or an instruction to the agent. Every omp that Trama starts afterwards (jobs, Ask more, the login terminal, `omp models --json`, `omp --version`, the check and update of omp, `omp usage --json`, and the conversations of omp Chat and General) receives it in the environment variable `CURSOR_ACCESS_TOKEN`, which wins over one the editor inherited; without a saved key Trama adds nothing, and an omp you start by hand receives nothing. Terminals and conversations already open keep the access they had. Known risk: Cursor's documentation says the dashboard's user keys are exchanged for an access token, omp does not do that exchange, and it is not verified that a dashboard key works as `CURSOR_ACCESS_TOKEN`; omp lists Cursor's models even with a wrong key, so the row can say **Connected** with an invalid key. Like any environment variable, the key is visible to the commands omp runs in its process.

To make omp forget a provider, press **Log out** on the row of a provider that shows **Connected**, and confirm in the editor's dialog (closing it changes nothing). Trama then runs `omp auth-broker logout <provider>` in the background, with no terminal; the row's **Log out** shows a spinner and its buttons are unavailable until omp has finished and Trama has checked omp again. omp removes every account it stored for that provider (OAuth logins and keys saved by its login). It never touches credentials omp reads from elsewhere (environment variables, `.env` files, keys in `models.yml`) or the **Cursor API key** saved in Trama: if the provider is still **Connected** after a successful logout, Trama says it is still reachable through another credential, and you remove that one where it lives. A failure is shown as an editor error with the last line of omp's error output.
Behind a proxy that inspects HTTPS traffic, omp and the commands its agent runs reject the proxy's certificates, because they do not trust the authority your company installed in the system. **System Certificates** (`trama.systemCertificates`, the last setting of the **omp** group and of the wizard's `omp` step, off by default, user settings only) fixes that: while it is on, Trama exports the certificate authorities your system trusts, together with the public ones the editor's runtime ships, into one bundle in your own cache folder (`~/Library/Caches/Trama/system-certificates.pem` on macOS, `%LOCALAPPDATA%\Trama\system-certificates.pem` on Windows, `$XDG_CACHE_HOME/trama/system-certificates.pem`, or `~/.cache/trama/`, on Linux), and every omp that Trama starts afterwards receives its path in `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `GIT_SSL_CAINFO`, `PIP_CERT`, `CARGO_HTTP_CAINFO`, `AWS_CA_BUNDLE` and `DENO_CERT`, overwriting the same variables of the editor's environment: the terminals of the jobs and of Ask more, the omp Chat conversations (General included), the terminals that install omp and log in, the logout, `omp models --json`, `omp usage --json`, and the check and update of omp. Trama reads only what is trusted for every user: the system keychains of macOS (`/Library/Keychains/System.keychain` and `/System/Library/Keychains/SystemRootCertificates.keychain`, never your `login` keychain), the `Cert:\LocalMachine\Root` store of Windows (never your own store) and, on Linux, the first readable of `/etc/ssl/certs/ca-certificates.crt`, `/etc/pki/tls/certs/ca-bundle.crt`, `/etc/ssl/ca-bundle.pem`, `/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem` and `/etc/ssl/cert.pem`. The export runs without a shell, takes at most 30 seconds, never blocks the editor or a launch, and runs when you turn the mode on, when the extension starts with a missing bundle or one older than 24 hours, and with **Refresh** next to the state line under the setting or the command **Trama: Refresh System Certificates** (shown only while the mode is on). A failed export keeps the earlier bundle and says why. A process receives the variables only when it starts, so open terminals and conversations keep what they had. Trama never turns certificate checking off, and Java's tools, which read a truststore instead of a PEM bundle, are not covered. The setting, with its state line and **Refresh**, is also the last one of the wizard's `omp` step: the value you choose there counts at once for what the step itself starts (its check of omp, the Install omp terminal and the login terminals), checking the box exports the bundle when it is missing or older than 24 hours and the step checks omp again when the export ends, and the value is saved with the other choices only when you confirm. Whatever the mode, when omp fails because it could not verify a server's certificate, Trama says so in plain words instead of omp's raw error.


## Optional features

The **Advanced** group of the Settings tab holds the theme and the optional features, split into the subgroups **Appearance**, **Drifts**, **Agents**, **omp Chat** and **Notifications** (described in [Notifications](#notifications): it is off until you set a topic). Every optional feature is on by default: **omp Chat** with its **omp Chat Intent Tracing**, **Auto Exit**, the **Advisor Scanner** (`trama.advisorScanner`), **Parallel Execution** (`trama.parallelExecution`), the **Async Drift Resolver** (`trama.asyncDriftResolver`), **Sub-agents Context Sharing** (`trama.subagentsContextSharing`) and **Auto-update Stale Proposals** (`trama.autoUpdateStaleProposals`). Turn one off by unticking it in the Settings tab or by setting it to `false` in your user settings; a value in the workspace settings never counts, so a cloned repository cannot change it. A `false` saved earlier stays off; nothing is rewritten or migrated. The details of **omp Chat**:

- It is on by default and stays on until you turn it off in your user settings (`trama.ompChat` set to `false`); a value in the workspace settings does not count, so a cloned repository cannot change it.
- With it on, the jobs Trama starts open as conversations in the **omp Chat** view, one conversation per job, instead of omp terminals. The view sits in its own container of the secondary sidebar of VS Code, on the right like the VS Code chat (VS Code 1.106 or later). Trama never opens, closes or moves a side bar by itself, except to show the view when a conversation opens.
- **General** is always the first tab of the view in a window with a folder open: a free chat with omp in that folder.
- **Usage.** Every conversation of omp Chat (General, a job's conversation, Ask more), even an empty one, shows under the message field, next to the model selector, how much of your subscription limits you have used, as omp reports them with `omp usage --json`: one entry per limit window (`5h`, `7d`, `7d Fable`) of the provider of the model chosen in that conversation, with a ring and the whole percentage (warning colour from 80 %, error colour at 100 %); changing a conversation's model changes its bar at once. Click it to open every provider with its windows and when they reset; each opening asks omp again. The usage is one per window, shared by every conversation. Trama asks omp when a conversation appears and the window has none yet, and after a turn of any omp Chat agent in the window when the last request ended more than 60 seconds ago, never on a timer; a window with no General but with job conversations asks the same way. With only API keys, no subscription, or if omp fails, nothing is shown. Trama reads no credentials and makes no network calls of its own: omp asks the provider with the credentials it already holds.
- **Approval**: the **omp Chat Approval** setting (`trama.ompChatApproval`, user settings only) is `yolo` by default: **omp runs every command without asking**, even those it would ask you to approve in the terminal, which is a risk to accept. To make omp ask permission as in the terminal, set `trama.ompChatApproval` to `ask` in your user settings: each request then shows in the conversation with a button per option. A developer who never chose an approval gets a one-time notice, with a button that opens Settings, when the first conversation starts. The setting applies to omp Chat conversations only: the omp terminal and omp sessions you start by hand are not affected.
- **Intent Tracing**: the **omp Chat Intent Tracing** setting (`trama.ompChatIntentTracing`, on by default, user settings only; a workspace value does not count) makes the agent write, at each tool call in omp Chat, the sentence that says why it makes it. Off saves tokens. It applies to conversations started afterwards.
- The session receives only the MCP servers of omp's own files (`.omp/mcp.json` in the project and `~/.omp/agent/mcp.json`); the files of other tools are not read.
- If omp cannot be reached (not found, exits at start, does not answer), the job starts in the omp terminal as it does with the feature off, and a notice says why.

## Notifications

Trama can tell you, on your phone or another device, that it is your turn. It sends a short notification through [ntfy](https://ntfy.sh), and only once you set a topic: with `trama.ntfyTopic` empty (the default) Trama sends nothing and makes no network call.

- **Which jobs.** Only the jobs Trama starts in omp Chat conversations send notifications: design, scan, Run, Resolve Drifts, Unify Drifts, import and refinement. Ask more, General, a job that runs in a terminal (also the terminal a job falls back to when its conversation does not start) and the prepared questions of the Async Drift Resolver never do. Each window sends only for its own conversations, so two windows never send the same notification.
- **Which events.** *Finished*: the window has stopped working (no job in progress, in a conversation or in a terminal, and no Run of a sequence still to start) because the work of a conversation ended; it goes after 30 seconds without a `session/update` or a message of yours in the conversations still open, at once when none is left open (for example with `trama.autoExit`), never after Stop, and it is cancelled when you open any conversation of omp Chat. *Question*: a question round of a job is presented and you have not answered or skipped it 30 seconds later. *Permission*: with `trama.ompChatApproval` on `ask`, omp asks a permission and you have not chosen an option 30 seconds later. *Stopped*: the agent of a job ends abnormally (the model refused or reached a limit, or omp refused the prompt) or omp exits while it works; it goes at once, also while other jobs keep working.
- **Nothing else.** Nothing is sent when the window closes or reloads, nor when a conversation comes back after a reload; a job continued after the reload counts like any other. A notification says only the project's folder, the conversation's name and what happened, never what the agent wrote, asked or ran, and has no action on click.
- **Settings.** `trama.ntfyServer` (default `https://ntfy.sh`) and `trama.ntfyTopic` (default empty) are in the **Notifications** subgroup, the last of **Advanced**, of the **Settings** tab; they are not in the setup wizard. Both are read only from your user settings, so a cloned repository can neither turn the notifications on nor send them to its own server. The server is an `http` or `https` address without user name, password, query or fragment; the topic has 1 to 64 letters, digits, `-` or `_`.
- **Public topic.** On the public ntfy.sh the topic works as a password: anyone who knows it can read what is sent to it, so choose one that is hard to guess, or use a server of your own.
- **Access token.** For a server that needs sign-in, **Set access token** (**Change access token** and **Remove access token** once one is saved) asks for the token in a masked box and saves it in the editor's secret storage (`trama.ntfyToken`), one per user shared by every window; it is sent as `Authorization: Bearer` and never goes into a setting, a file, the panel or a log.
- **Test.** **Send test notification** sends one notification with the current server, topic and token, with no retry, and says under the button whether it was sent or why not. It does not depend on omp Chat or on a job.
- **Failures.** A notification that cannot be sent is tried once more after 10 seconds and then given up in silence; it never disturbs the agent or the window. Every request is limited to 10 seconds and a redirect counts as a failure. Trama's only network call of its own is this request.

## Solo mode

Solo mode is for using Trama alone in a repository where the others do not: Trama's files stay in your working copy and never enter a commit. It belongs to the working copy, not to you, and it is not a setting of the editor: `trama project new` and `trama project edit` take `solo` (`off`, `folders` or `files`) and the Settings tab and the wizard show the same choice. It needs the project to be inside a git repository; anywhere else Trama says `Solo mode needs a git repository.` and writes nothing.

- **Where it is kept.** The choice is in `.trama/solo/mode.json` (`{ "exclusions": "folders" }` or `"files"`), in a folder with its own `.gitignore` containing `*`, so it stays local even when `.trama/` is tracked. A file that is not valid counts as on with `folders`.
- **The block.** Trama writes a block between `# trama solo mode` and `# end trama solo mode` in the local exclusions of git, `.git/info/exclude` (the file `git rev-parse --git-path info/exclude` names, created when missing), which is never committed and is not shared with a clone. Every other line and the line endings of the file stay as they are, and writing the same block again changes nothing. The paths are anchored to the root of the repository, with the place of the project in it, so a project in a subfolder is covered without touching its neighbours.
- **Two kinds.** `folders` keeps `.trama/`, the folder of the agent skills (`trama.skillsDir`, default `.agents/skills`) and `.omp/` out of git, whatever they hold. `files` keeps out only `.trama/`, the `trama-*` skills (the `trama-req-*` too), `.omp/agents/trama-analysis.md`, `.omp/agents/trama-implementer.md` and `.omp/WATCHDOG.yml`, so other files of those folders stay visible to git.
- **Files already tracked.** An exclusion does not hide a file git already tracks. Turning Solo mode on is not refused for them: Trama lists them (`tracked` in the result of `trama project edit --json`) and their changes still enter commits; remove them from the index yourself (`git rm --cached`) if that is not what you want.
- **Turning it off** removes the block and `.trama/solo/mode.json`, leaving everything else in the exclusion file. Changing the kind rewrites both. A write that fails changes nothing and says why.
- **In the editor.** In a project, the Project group of the Settings tab has the row **Solo Mode** right after the skills folder: a checkbox, the note `Only this workspace.`, and, with it on, the field **Exclude** (`Whole folders` or `Only Trama's files`) and the list of Trama's files git still tracks (at most 10, then `and <N> more`). Outside a git repository the checkbox is off and disabled and says `Solo mode needs a git repository.`. The setup wizard offers the same row in its `Project` step in the first setup and in the Empty Model mode (never in the Guided setup of the Settings tab), without the list of tracked files; nothing is written before the confirmation, and with Solo mode chosen the notice of Get Started says that the files stay out of git in this working copy only.
- **Repair.** With Solo mode on, every ordinary opening of Trama checks, in the same background check as the agent skills, that the block is there and is the one the kind and `trama.skillsDir` need, and writes it again in silence when it is not; a write that fails shows `Trama: could not update the agent skills: <reason>.`.
- **`.trama/` is not versioned elsewhere.** While Solo mode is on, `.trama/` never enters git here, so the Model, the Requirements, the history and the Board are not in the repository, and a clone or another working copy does not have them. Keep your own copy if you need one.
- **Merge.** With Solo mode on, the foot of the side menu has the primary button **Merge**: it brings into the current branch what the others committed, then has the agent scan the whole System, so that every difference their work opened against the Model becomes a Drift on the Board. It is available only when nothing could be lost: no merge, rebase, cherry-pick or revert in progress, HEAD on a branch, no tracked file with uncommitted changes (staged or not, Trama's own files apart; untracked files do not count) and no job of the agent launched from this window running; otherwise it is disabled and a line under it says why. While some of Trama's files are still tracked by git, a warning line reminds you that their changes enter your commits. Pressing it runs `git fetch --all --prune` (a failure says `Trama: could not fetch: <reason>.` and merges nothing), then a list shows the branches (the upstream of the current branch first, then the other remote ones, then the local ones, each in alphabetical order); a branch that is neither the upstream nor `<remote>/<current branch>` asks a confirmation first. Trama then runs `git merge --no-edit <branch>`: a branch already contained says so and scans nothing; a merge without conflicts, a fast-forward included, starts the scan at once, with no confirmation, naming the range the merge brought in (`<base>...<incoming>`); the agent marks `merge` on every Drift whose place in the code lies in one of those files, and the scan counts as the last scan of the System (`Scan System` goes back to `· 0`). With conflicts, Trama remembers the merge in `.trama/solo/merge.json` (`{ branch, base, incoming, started }`, in the local folder of Solo mode, never versioned) and offers **Open Merge Editor** (`git.openMergeEditor` on the first file with conflicts), **Reconcile with Agent** (the `trama-merge` skill resolves the conflicts keeping the intent of both sides, asks you with a round of questions when it cannot tell which one holds, stages only what it resolved, and never commits or aborts) and **Abort** (`git merge --abort`, after a confirmation). Trama never makes the merge commit: you do. When the merge commit arrives, from wherever, the scan starts; when the merge ends without a commit, Trama forgets it and scans nothing. Trama looks at the git directory (`HEAD`, `MERGE_HEAD`, `index` and the refs), when the window opens and at every execution check, so a window closed or reloaded during a merge picks it up again. Since the others do not keep the Model up to date, those Drifts lean towards keeping the code and adapting the Model, except where the work came from an issue of Team (see [Signals and the two actions](#signals-and-the-two-actions-of-an-issue)): there the issue said what had to happen, so the Drift leans towards fixing the code.

## Manager mode

Manager mode turns on Team for one working copy: planning the work of your team and publishing it as GitHub issues. Like Solo mode it belongs to the working copy, not to you, and it is not a setting of the editor.

- **Where it is kept.** In `.trama/manager/mode.json`, a JSON object `{}` with LF line endings and a final newline, in a folder with its own `.gitignore` containing `*`. The file exists only while Manager mode is on, stays local even when `.trama/` is tracked, and never enters a commit, with Solo mode on or off. A file that is not valid JSON counts as on; the next write replaces it.
- **It needs GitHub.** The repository is read again at every opening of the panel and at every picture of it from `git remote get-url origin`: `https://github.com/<owner>/<repo>`, `http://github.com/<owner>/<repo>`, `git@github.com:<owner>/<repo>` or `ssh://git@github.com/<owner>/<repo>`, each with or without a final `.git` and `/`, give `<owner>/<repo>` in lower case. Any other host, GitHub Enterprise included, no `origin` and no git count as not on GitHub. Without it Manager mode cannot be turned on: `Manager Mode needs a repository on GitHub (the origin remote).` Team is available only with Manager mode recorded and origin on GitHub; a Manager mode left on whose origin moved away stays recorded, and Team comes back when origin points to GitHub again.
- **Turning it off** deletes only `.trama/manager/mode.json`: the people in the Manager's editor and the files of Team's work in the project stay, and turning it on again brings everything back.
- **In the editor.** In a project, the Project group of the Settings tab has the row **Manager Mode** right after **Solo Mode**: a checkbox with the description «Plan work for your team and publish it as GitHub issues. Only for this working copy.» and `Repository: <owner>/<repo> · origin on GitHub`. Without origin on GitHub the checkbox is off and disabled, with `Needs a repository on GitHub (the origin remote).` and `No origin remote` or `Origin is not on GitHub`. A write that fails shows `Trama: could not save Manager Mode: <reason>.` and the row goes back to the recorded value.
- **In the setup wizard.** In every mode, the **Project** step ends with a **Repository** box (`<owner>/<repo> · origin on GitHub`, `No origin remote` or `Origin is not on GitHub`; in the first setup, the folder chosen in **Path**) and the row **Manager Mode**. It starts off in the first setup and from the project's value in the other modes; nothing is written before the confirmation, and the summary says `Manager Mode: On` or `Off`, highlighted when it changes the project's value. In the first setup Manager mode is written after the project's files, and a failure is told without undoing the project.
- **Command line.** `trama project new` and `trama project edit` accept `manager` (`true` writes the file, refused without origin on GitHub; `false` deletes it); `project edit` with only `manager` installs no skill. `trama project show` says `Manager mode: on (<owner>/<repo>)`, `Manager mode: on, but origin is not on GitHub` or `Manager mode: off`, and with `--json` has `manager` and `managerRepository`. See [the command line reference](./docs/cli.md).

### Team and people

With Team available (Manager mode on and origin on GitHub) the side menu has **Team** right after **History**, and the command **Trama: Show Team** opens the panel on it; without Team the command only opens the panel as usual. The **Team** view has a tab for each part of the Manager's work; the first is **People**.

- **People stay in your editor.** The list of people is yours, one for all your projects, and each project chooses who is in its team, so the same person can work on several projects. It lives in the editor's global state under `trama.team` and is never synchronised: nothing about people is written in the project, in `.trama/`, in git, in the logs, in notifications, in the History or in a Proposal, a Task or a Drift. The people may or may not use Trama.
- **What Trama knows about a person.** Name, GitHub handle (never their GitHub avatar: the avatar shows their initials), level (Junior, Mid or Senior), skills, capacity per sprint in days (0.5 to 5, in steps of 0.5, 5 by default) and absences. The agent reads the members of the project's team with `trama team show`.
- **Add and edit.** **Add person** and the pencil of a row open a dialog; **Save** checks every field and marks the invalid ones. Two people never share a GitHub handle. A change holds in every project the person is in. Absences that ended more than 90 days ago are dropped when the person is saved.
- **Add from other projects** puts a person you already know in this project's team, from a searchable list. **Remove from team** takes them out of this project only, at once, and says so with an **Undo** that lasts 10 seconds; they stay in your list and in the other teams. **Delete person** asks first in the editor's own dialog and removes them from your list and from every team; issues already assigned to them on GitHub stay assigned.
- **Unreadable values.** A saved person that does not fit what Trama expects is left as it is, not shown, and counted under the header; a list written by another version of Trama is not read and never overwritten.

### GitHub Project

Team publishes issues to one GitHub Project per working copy and reads its sprints from the Project's **Iteration** field. It needs the GitHub CLI (`gh`), installed and logged in with access to Projects, and uses it **only to read**: Trama never creates, changes or deletes anything on GitHub; writing is the agent's work. Besides the away notifications, these `gh` calls are the only network calls Trama makes, and they send nothing of your work.

- **Linking.** The top of the **Team** view has the Project's button (`<owner>/<repo> · <Project>`), which opens **Change GitHub Project**: a search over the Projects of the repository's owner (user or organisation), **Link another Project…** and **Unlink**. Without a Project the view asks for one with **Link a GitHub Project**: only a Project with an Iteration field can be linked (the others are disabled, with the reason), and **Create a Project on GitHub** opens the owner's Projects page. The link is `.trama/manager/project.json`, in the local folder of Manager mode, so it is never committed. Changing the Project leaves the issues already published where they are; **Unlink** changes nothing on GitHub.
- **Reading.** Trama reads when the Team view opens and when you press **Refresh**, never on a timer, one read at a time; the view says `Updated <time ago>` and keeps what it read last when a read fails. The first read shows `Loading from GitHub…`.
- **When `gh` is not ready.** A box at the top of the view says so: `GitHub CLI is not installed` (**Install gh** opens <https://cli.github.com>), `You're not logged in to GitHub` (**Log in to GitHub** runs `gh auth login --hostname github.com --web --scopes project` in a terminal), `GitHub CLI can't read Projects` (**Give access** runs `gh auth refresh --hostname github.com --scopes project`) and `Couldn't read the GitHub Project` (**Retry**, and **Show details** in the Output channel). When the terminal command ends the view reads again.
- **For the agent.** `trama issue fields` prints the fields and iterations of the linked Project.

### Handoffs: the Decisions and Issues tabs

A handoff is the lighter Proposal through which you give work to your team: the agent turns your request into issues for the people of your team and, when the work changes behaviour, into changes of the Model. The **Team** view opens on **Decisions**; its tabs are **Decisions**, **Issues** and **People**, and the tab you choose stays while you visit other views.

- **Decisions.** The handoffs that wait for your decision, each as a card: short number, title, the epic as a chip with a coloured dot, `Creates <n> issues · changes <m> Machines · proposed <time ago>` and, when it has some, `<n> warnings`. The tab's label carries the number of handoffs waiting, and so does the **Team** entry of the side menu (`Team, 2 handoffs wait for a decision`); handoffs never count in the number of **Board** nor in the icon of the activity bar. **New handoff** writes a handoff request for the agent. **Approve** publishes the issues on GitHub and is disabled, with the reason, while the agent is still finishing the handoff, when it is blocked, and without a linked Project (`Link a GitHub Project first`); **Reject** and, in the arrow, **Rework with feedback…** work as on the Board. A handoff is decided only here: from any other view the editor refuses and says so.
- **The preview.** A click on a card opens the first of its issues as it will look on GitHub: the title, the labels, the warnings (`Estimated 4 d: more than 3 days per issue.` with **Split**, which asks the agent to cut that issue in parts, and `Not covered: <ref>.`), the body composed as it will be published, with its `mermaid` diagrams, and the block `Trama references`. **Alt+↑** and **Alt+↓** move between the issues, **Esc** goes back to the cards. The column of fields lets you change the assignee, the reviewer, the estimate, the sprint and every other field of the Project the agent proposed; a change says `Changed by you · Undo`, is kept apart from what the agent wrote, and makes the handoff neither stale nor a Draft.
- **Issues.** The issues of the approved handoffs grouped by epic (`<n> issues · <days> d`), each row with its number, title, assignee, sprint and status: `Publishing` while the agent publishes it, `Not published` with `Publish failed: <reason>` and **Publish again** when it could not be, and, once published, **Open on GitHub**. A field GitHub did not take is listed under the title.
- **For the agent.** `trama issue list`, `show`, `move` and `edit` (see [the command line reference](./docs/cli.md)) and the skill `trama-handoff`.

### Where a published issue is

After publication Trama follows each issue by **reading** GitHub, when the Team view opens and with **Refresh**; it never changes anything there. The Issues tab says where each issue is: `Open`, `In progress` (a draft pull request, a linked branch or a Project status of `In progress` or `Doing` in any case), `In review` (an open pull request, not a draft, that closes it), `Closed`, `Not planned`, or `Not found on GitHub` when the Project no longer has it, and a group says `· <n> closed`. The sprint, the estimate and the assignee are always what GitHub has now; Trama's card keeps the published values only as history. The estimate is read from the first number field of the Project whose name contains `estimate` or `days`; without one, Trama's own estimates count. Before the first read, and for an issue published after it, the status is `Open`. Every comparison of the Model with the code (a scan, a Run, the scan after a Merge) lists the published issues whose references fall in the Machine it compares, and a Drift on those references names the issue and recommends fixing the code to what the Model says.

### The Timeline

The **Timeline** tab, between **Issues** and **People**, is the roadmap in time of the linked Project: its weekly sprints as columns, from the earliest current or past sprint that holds an open issue of Trama (the current sprint when none) to the last iteration, and a last column `No iteration` for the open issues with no sprint. `By person` (the default) gives a lane to each member of the team, with their capacity per sprint, and then `Unassigned` and `Not in this team` when needed; `By epic` gives a lane to each epic. Each issue is a block as wide as its estimate over five days; a click opens it on GitHub. By person, absences are dashed blocks and every cell says `<load> / <capacity> d`, in red with `· over` when the person has more than their capacity in the sprint: the load counts every open item of the Project assigned to them, Trama's or not, and the capacity is their capacity per sprint for the working days (Monday to Friday) they are not away, rounded to half a day. When the Project has no sprint in the next three weeks a warning says so, with a button to add iterations on GitHub. The Timeline is only a view: sprints, estimates and assignees change on GitHub, and the plan is changed by hand. In the preview of a handoff's issue, the `Sprint` field also says what the assignee would have in that sprint.

### Signals and the two actions of an issue

Under the title of an **open** published issue, the Issues tab shows **signals**: small badges with an icon and a short reason, always in this order, recomputed at every read of GitHub and every picture of the panel, and never changing anything on GitHub or in the project. `Stale` (`The Model changed after publishing`): the text of a reference of the issue is not what it was when it was published or last commented on, or a reference no longer exists. `Carry-over` (`From <sprint>`): its sprint ended before today. `Overload` (`<first name> <load> / <capacity> d`): its assignee has more in its sprint than their capacity there (capacity and load as in the Timeline). `Dependency` (`Blocked by #<n>`, or by the title when the dependency has no number): an issue it depends on is open and has no sprint, or a later sprint, or the same sprint and another assignee. A closed or not planned issue shows none. The Timeline gives a block with a signal a left border in its colour.

- **Comment update** (`MessageSquare`) is on a stale open issue. It asks the agent, in a terminal named `Update #<n>`, to tell the people on the issue what changed in the Model: the agent reads `trama issue show <id>`, which prints under `## Changed since publishing` the earlier and the current text of each changed reference (the earlier one from git when it has it, otherwise only the reference is named), writes one comment on GitHub in the language of the issue, without any mention of Trama, and records it with `trama issue edit <id>` and `{ "updated": true }`. The body of the issue is never rewritten.
- **Scan** (`ScanSearch`) is on a closed issue. It asks the agent, in a terminal named `Scan #<n>`, to compare with the code only the references of the issue: the work was done by a person of the team from the issue, so a difference leans towards fixing the code. It files its Drifts like any scan and never changes the number of **Scan System** or the memory of its last scan.

Both are disabled, with the reason as their tooltip, while their own job runs (`Updating…`, `Scanning…`), while a Run of this window is in progress (`A run is in progress`) and when Team is not available; **Open on GitHub** becomes an icon next to them.
