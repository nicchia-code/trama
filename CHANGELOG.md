# Changelog

## Unreleased

- System Certificates, host side: `trama.systemCertificates` (boolean, off by default, `scope: application`, last key of the `omp` group of `SETTING_GROUPS`; `configuredSystemCertificates` reads only the user value and a non-boolean is off) and the host module `extension/src/host/system-certificates.ts`. With the mode on Trama exports the system's certificate authorities, without a shell and in at most 30 s (macOS `security find-certificate -a -p` on `/Library/Keychains/System.keychain` and `/System/Library/Keychains/SystemRootCertificates.keychain`, never `login`; Windows PowerShell on `Cert:\LocalMachine\Root`; Linux the first readable of `/etc/ssl/certs/ca-certificates.crt`, `/etc/pki/tls/certs/ca-bundle.crt`, `/etc/ssl/ca-bundle.pem`, `/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem`, `/etc/ssl/cert.pem`), `buildBundle` keeps the readable certificates with `ca` true, adds `tls.rootCertificates` and drops duplicates by `fingerprint256` (no authority in the store is the failure `no certificate authority found`), and the bundle is written atomically (`<path>.<pid>.tmp`, then rename) to the per-user path (`~/Library/Caches/Trama/system-certificates.pem`, `%LOCALAPPDATA%\Trama\system-certificates.pem`, `$XDG_CACHE_HOME/trama/system-certificates.pem` or `~/.cache/trama/`), so a failed export leaves the earlier bundle. It exports when the mode is turned on, at activation when the bundle is missing or older than 24 h (a failure shows once `Trama: could not export the system certificates: <reason>.`, with ` Using the ones exported <date and time>.` when an earlier bundle stays in use, and `Open Settings`), with the command `Trama: Refresh System Certificates` (`trama.refreshSystemCertificates`, in the palette only while the mode is on; it says `Trama: exported <N> system certificates.` or the same error) and with the webview messages `refreshSystemCertificates` and `systemCertificatesExport`; a request during an export of the same window does nothing, and an export never blocks the activation or a launch. With the mode on and a bundle on disk `systemCertificatesEnv(on)` gives `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `GIT_SSL_CAINFO`, `PIP_CERT`, `CARGO_HTTP_CAINFO`, `AWS_CA_BUNDLE` and `DENO_CERT`, merged after the inherited environment and `cursorKeyEnv()` (so Trama's values win) in the terminals of the jobs and Ask more, the omp Chat processes, the installer terminal (`installOmp` now passes an environment), the login terminals, `logoutOmp`, `omp models --json`, `omp --version`, the update check and the update, and `omp usage --json`; without the mode or a bundle nothing is set, a process receives the variables only when it starts, and Java's truststore is not covered. Trama never turns certificate checking off. The host tells the webview the state with `systemCertificates { exporting, count?, exportedAt?, error? }` (at `ready`, when the Settings view shows and at every change); after every export that ends and every change of the mode it forgets the last update check and checks omp again in silence (Settings tab and wizard). `agentCheckWanted`, `installOmp` and `ompLogin` accept `systemCertificates?: boolean` (the wizard step's value, for that check, installer and login only; `parseToHost` checks it as a boolean).
- Certificate errors are told in plain words: `isCertificateError(text)` and `certificateErrorText(systemCertificates)` (`extension/src/certificate-errors.ts`, shared by host and webview) recognise `UNABLE_TO_GET_ISSUER_CERT_LOCALLY`, `UNABLE_TO_GET_ISSUER_CERT`, `UNABLE_TO_VERIFY_LEAF_SIGNATURE`, `SELF_SIGNED_CERT_IN_CHAIN`, `DEPTH_ZERO_SELF_SIGNED_CERT`, `CERT_HAS_EXPIRED`, `CERT_UNTRUSTED`, `ERR_TLS_CERT_ALTNAME_INVALID` and, whatever the case, `unable to get local issuer certificate`, `self signed certificate in certificate chain`, `self-signed certificate in certificate chain`, `certificate verify failed`, `SSL certificate problem` and `curl: (60)`. Whatever the mode, the reason of a failure becomes «omp could not verify a server's certificate; a corporate proxy that inspects HTTPS traffic is the usual cause» («…, even with System Certificates on; …» with the mode on) in the `error` of `ompModels` (which now reads the error output of a failed run only for this test), a failed check or update of omp, the usage line of omp Chat, a failed logout, the reasons of a conversation that does not start (`START_FAILED`) or is not resumed (`SESSION_NOT_RESUMED`), the Board notices `The agent of <job> stopped: <text>.` (in place of `omp refused the prompt (<message>)`) and `Trama stopped following <job>: <text>.` (in place of `omp exited (<code or signal>)`) and the reason inside General; omp's own lines stay behind `Show details`, a reason that is not a certificate error is unchanged, and what omp writes in a terminal is never read.

Only with the box checked a line of secondary text under the description (`SystemCertificatesLine` in `extension/src/webview/setup-shared.tsx`, next to the omp status box, fed by the host's `systemCertificates` message through `SettingsView.receiveSystemCertificates`; the wizard shares the component) shows the state of the bundle with its icon on the left and `Refresh` at the right end of the same line: the omp spinner and `Exporting system certificates…`, `CircleCheck` and `<N> certificates, exported <date and time>.`, `TriangleAlert` and `Could not export the system certificates (<reason>). Using the ones exported <date and time>.`, or `TriangleAlert` and `Could not export the system certificates (<reason>). omp gets no certificates from Trama.` (`systemCertificatesLine` in `extension/src/webview/settings/logic.ts`; the time is the bundle's, in the editor's locale, short form). `Refresh` is a small outline button with `RefreshCw` and the accessible name `Refresh system certificates`, sends `refreshSystemCertificates`, is disabled with the tooltip `Exporting system certificates…` while an export runs, and wraps under the text, aligned left, when the line does not fit (down to about 300 px); the line reads in words, is a polite live region and describes the checkbox through `aria-describedby`. Trama cannot work without omp.`; other reasons are unchanged.
- System Certificates in the wizard's `omp` step: `trama.systemCertificates` is the last key of the step (after `trama.language`; it follows `SETTING_GROUPS`, so the summary and `confirmSetup` carry it like any other key), shown with the same `SettingField`, the same `SystemCertificatesLine` and `Refresh` as the Settings tab, only with the box checked in the step. - Refinements of stale Proposals (`trama.autoUpdateStaleProposals`) now work in parallel, and a new **Refine All** entry queues them all in one click. The window keeps one queue, in Backlog order, shared by Approve and Refine All; the Proposals queued or at work are split into chains (two Proposals that touch a file in common, or one requires the other, are in the same chain; recomputed at each start), each chain refines one Proposal at a time (the required first) and different chains work together, each refinement as a job of its own with its own terminal (`Refine P3`) or omp Chat conversation. Each refinement holds a share of `trama.maxParallelAgents` from its start to its end (the free places are divided equally among those that start together, at least one each, never more than the limit in all), and its instruction gives that share as the sub-agent limit. A queued Proposal that requires a Proposal still queued, at work or waiting for a Run waits for its approval, and leaves the queue, back to refinable, when that one is gone without being approved. The end of each job is looked at once and touches no other refinement. The Board message carries `refinement: { enabled, running, queued, refineAll }`: `running` lists every Proposal at work, each entry of `queued` says why it waits (`approval`, `chain` or `slot`), and `refineAll` carries `mode` (`refine` or `cancel`), `count`, `blockers` (`Turn on Auto-update Stale Proposals in Settings`, `No Proposal to refine`) and `since`. The folder goes with its request, when the Proposal bound to it is handed over, when an empty request is closed unsent, or when the file is deleted from outside; folders left without a request are removed at start-up. The ghost text mentions images, and `markdown.copyFiles.destination` defaults to the request folder through `configurationDefaults`.
- Each History entry on the Board shows its time alone in the `Today` and `Yesterday` groups and the date and time before them, with the full date and time as its tooltip. Its summary is shown with inline Markdown in full. The «i» beside its title opens a modal dialog with the entry's full text and its Tasks in creation order, each with its status dot, ID, Proposal tag, end date and references; a Task that no longer exists says so. The dialog closes with **Close**, Esc, a click outside, or a link followed to the Diagram or Requirements.
- A History file that does not read is now an error of the Snapshot: the panel's error box names the file and its problem, while the other History entries stay on the Board.
- Opening the editor on a project sends back to To do every Task an agent had taken, since no agent is followed after a start; before, such a Task stayed taken until its terminal or conversation closed or its turn ended, even when the agent had died.
- Every agent launch except a Run is announced on the Board as soon as its instruction is really sent, in the terminal and in the editor's chat alike: a design, Resolve Drifts (also the automatic collection, titled `Resolve Drifts`), a scan's check and an import. An instruction that waits for the developer's Enter or lands on the clipboard announces nothing. The end of an agent's turn releases the Proposals and Drifts it delivered or filed, so their buttons become available again.
- The quick design request is removed, with its «Quick request…» button, its one-line input box, its command and its message to the host. A design request is only the written one: **+ Add Work Item** at the foot of the Work Items column creates the empty file `.trama/requests/<id>.md` and opens it in the editor, and the Board toolbar no longer has an Add Work Item button.
- Non c'è più la corsa per i soli Task di un design: il pulsante **Run this design** e la sua azione sono rimossi, e il pre-flight, la scansione di fine corsa e i titoli non hanno più quell'ambito. **Run Ready Tasks** si chiama **Run all**, sia sul pulsante sia nei messaggi.
- La Board chiama le colonne Work Items, Ready, In progress e Done; il pulsante della barra **Run all To do** diventa **Run Ready Tasks**. In fondo a Work Items c'è solo **+ Work Item**, in fondo a Ready solo **Run all**, anche quando la colonna è vuota. I motivi del pannello dicono «No Task is Ready» e «All the Ready Tasks are blocked: …».
- Un controllo finale fallito di un Run automatico non ferma più i Task indipendenti: il Run può dichiarare, con `trama agent-event failed --task <id>` dopo il controllo fallito, il Task che ha rotto la verifica. Solo quel Task e i Task che riguardano la stessa cosa restano fermi; gli altri proseguono in una raccolta successiva. Senza un Task dichiarato, la prosecuzione automatica resta ferma come prima.
- La scheda Settings suggerisce i modelli nei tre campi dei ruoli (`trama.analysis`, `trama.scan`, `trama.execution`) con una tendina nativa dello stesso campo: per omp i modelli di `omp models --json`, per la chat di Cursor l'elenco che Cursor tiene nel suo database di stato, per la chat di Copilot i modelli messi a disposizione dell'editor. Con Claude Code, o quando l'elenco manca, il campo resta un testo semplice. Scegliere un suggerimento lo salva subito; un nome scritto a mano resta valido come prima.
- A failed final check of an automatic Run stops that Run's automatic continuation: the coordinator authorizes no further Task of that Run, so the independent ones do not start, and the unfinished ones carry the reason as `autopilot failed`. Collections started after the Run are not held.
- A Done Task keeps its short number (`T3`) while its design still has a Task in To do or In progress, and loses it together with the design's other Tasks on the first read that finds them all Done. A Done Task without a number never takes one, even when its design reopens.
- An empty written design request, and the request started by Start from Scratch, shows a grey ghost text at the start of its tab until the first character is typed: «Describe the change to design…» for a design request, «Describe the application to build…» for the setup request. The text is only on screen: the file stays empty, is never saved or sent, and a request already sent shows none.
- Specs (`.trama/specs.yaml`) is written by an approved Proposal and read by the agent from a generated `trama-specs` skill, beside the `trama-req-*` skills: its fields with entries, the reasons of the entries the agent chose itself, and the notes. The skill is regenerated when the approval, `trama skills update` or a change of `specs.yaml` runs, and removed when Specs is deleted; an invalid Specs keeps the skill as it was and says why. Its name and description count in the Requirement skills' budget.
- The Board shows the Tasks of one Proposal, when there are at least two, as one design card named after the Proposal: it stands in the column its Tasks add up to (Ready, In progress or Done), is closed until expanded to show each Task with its status dot, counts its finished Tasks (for example «2/5 done»), and has **Run this design**, which asks the agent to implement the design's Tasks still in To do. The card is dated by its latest finished Task in Done. A Task alone from its Proposal, or with no Proposal, stays a card of its own; a Task linked to a Proposal keeps the tag with that Proposal's title.
- **Trama: Initialize Project** is removed, with its command `trama.init`. A folder without a Trama project opens **Trama: Open** on Get Started, where you choose **Import from Code** or **Start from Scratch**; Start from Scratch in a folder with visible files first warns that it already contains files. The extension starts in every window once the editor has finished starting, so the status bar's «Trama» button is there even without a project, and it writes nothing to the workspace until you set a project up.
- Drift delegation is one menu, `trama.driftAutoPilot`, with `disabled` (the default), `enabled` (non-critical Drifts are delegated) and `yolo` (critical Drifts too). It is read only from your user settings. It replaces the two checkboxes `trama.autoFixDrifts` and `trama.autoFixCriticalDrifts`, which are no longer read and never rewritten.
- The panel's tabs are, in order, Board, Diagram, Requirements and Settings; it still opens on the Diagram. The design buttons «Quick request…» and «Add Work Item…» are only on the Board, and no longer on the Diagram or Requirements toolbars. With an empty Model the Diagram says so, links to the Board, and offers «Import from Code» and «Start from Scratch» beside each other.
- The agent's terminal opens as a tab in the active editor group by default (`trama.terminalLocation` defaults to `editor`); only the user value `panel` opens it in the terminal area.
- `trama.submitWhileRunning` is a checkbox, `false` by default. The former text values are read as `false` and never rewritten; `true` lets a run start while another one is in progress.
- Start from Scratch on the Diagram of an existing project with an empty Model opens the setup request at once, without the warning about the folder's visible files and without initializing anything.
- A `setup` Proposal handed over (`trama proposal submit`) while the Model has no Feature and no Actor is approved at hand-over, with the same effects as the developer's approval. When that approval refuses it (stale, requiring Proposals not approved yet, a Task that cannot be created), it stays open and the output says why. `submit` accepts `--skills-dir` like `approve`.
- **Dismiss Drift** on the panel closes an open Drift without changes and discards its attached Proposal, a Draft or a handed-over one, with no feedback. It is refused, changing nothing, while the Drift sits in an undecided resolution or while Resolve Drifts runs. `trama proposal discard` refuses a Draft attached to an open Drift, and points at the Drift.
- **Approve** and **Reject** on a Proposal wait for the end of the turn of the agent that delivered it: while that agent is still finishing its turn, both buttons on the Board and the Diagram are disabled with «The agent is still finishing», and the panel's commands refuse with a message. ## 0.0.3

- The Trama panel has a fourth tab, Settings, that lists every `trama.*` setting in groups (Agent, Models, Drift autopilot, Runs, Project) with its title and explanation, and the control that fits it. Changes are saved at once in your user settings, never in the workspace's; raising the Drift autopilot asks for confirmation first in a modal question. The tab shows a workspace value when it overrides a setting, and it follows a Trama setting changed from anywhere (the editor's settings, a settings file, the tab) at once. `trama.maxParallelAgents` is now an integer setting, a whole number of at least 1.
- The Settings tab no longer shows the technical key of a setting, neither on the page nor in its explanation; a failed save names the setting by its title, as `Trama: could not save Max Parallel Agents: <reason>.`.
- In the Settings tab each setting's explanation is no longer on the page: an «i» next to its title opens it in a bubble when hovered or focused, closed by leaving it, losing focus or Esc, and an enum's bubble lists every value with the chosen one marked `(current)`.
- A fix Task can be closed without changes when the code already does what its Drift says: `trama task move <id> done --unchanged <note>` moves it to Done with the note and its Drift to Dismissed in one step. Such a Task is marked `(no changes)` and carries a `no changes` badge with its note on the Board, and is not counted by the Scan button or scanned at the end of a run. The `trama-implement` skill checks the Drift's premise against the code before writing any code, and reports the Tasks closed without changes apart.
- Withdrawing the automatic-resolution delegation during a Run no longer marks the Tasks that had not started as failed: they stay in their column without a badge, and a Task already started finishes normally.
- In the automatic Run, a fix Task closed without changes is a success: it is not reported as failed, carries no `autopilot failed` badge, and its origin becomes runnable as after any Done fix Task; the `trama-implement` skill no longer reports it with `trama agent-event failed`.
- A failed final check of an automatic Run stops that Run's further groups: its Tasks not yet Done carry an `autopilot failed` badge with the reason, the Resolve Drifts tooltip names the failure, and `trama drift autopilot` lists it instead of showing nothing.
- A window whose project changes while a question round is still open no longer shows that round over the other project's panel: the round waits out of sight, its answers kept, and comes back when the window is on its project again; the window's other rounds wait behind it, and no answer is lost or left orphaned.
- The editor title bar shows an Open Trama icon at the right of every editor group in a window with a folder open, also without a Trama project and also while the panel is the active tab; on an unsent design request it sits to the right of Send to agent. The `Open` command is now titled `Open Trama` in the palette.
- The `trama-scan`, `trama-implement` and `trama-import` skills follow the Drift rules: Fix options reach what should happen without changing the Model or the Requirements; a Drift without Fix options comes with a Proposal when no fix of the code respects both; they read the resolved Drifts on the same references before filing and name a recurring one with `--previous`. `trama-import` files a Drift for each difference between the documentation and the code, instead of a doubt; its doubts keep only the code that looks buggy where the documentation says nothing, and behaviour it could not determine.
- `drift new --previous <id>` records the resolved Drift a new one follows, making it recurring; a Drift whose origin Task fixes another Drift follows that one by itself. Recurring Drifts are left out of the Drift autopilot in every mode.
- `drift show` of a recurring Drift has a `Follows Drift <id> <title> (<resolution>)` line under its title; `drift list` and the textual `board` mark it `(recurring)`; the Snapshot and the JSON of these commands carry `previous`.
- The Board card, the resolution rows and the Diagram details of a recurring Drift show a `recurring` badge whose tooltip and accessible name say `Recurring: follows Drift <id> – <title>`.
- `drift list --ref <ref>` (repeatable) keeps only the Drifts that concern the same thing as one of the references, with the test that decides Task blocks; combined with `--all` it shows the resolved ones too. A reference that does not resolve is a usage error.
- `drift new` with no `--option` files a Drift without Fix options, which needs `--proposal` (its Draft fixes the Model or the Requirements); without it the filing is refused. One or more than five options are still refused.
- An approval no longer starts a scan of the Features it touched, from the panel, from the command line or through a Drift: the `trama.autoScan` setting and the «Scan now» notice are removed. A leftover `trama.autoScan` value is ignored and not rewritten; manual scans are unchanged.
- A Proposal's scan scope is computed from the Model and Requirements whenever it is needed (validation, hand-over, approval and `proposal show`) and is no longer saved at approval; the `## Scan scope` of an open Proposal is always current. Approved Proposals that saved one keep it as history.
- Registrations on one Proposal (`proposal edit`, `proposal delete`, `proposal resolve-drift`, and the Task files written inside a Proposal) run one after the other under a lock per Proposal, so sub-agents writing at the same time no longer lose each other's files or recorded bases. The lock is a file in `proposals/.locks/`, kept out of Git; a lock older than 30 seconds is taken as left by a dead process.

## 0.0.2

- Windows (win32-x64) is packaged and smoke-tested by the release workflow, and a manual run can release a single platform. Windows is untested: its test suite has known failures and nobody has tried the package by hand.
- On Windows, Copilot's hook file carries the PowerShell form `& "<trama.exe>" copilot-hook` in `windows` next to `command`, and Cursor's `hooks.json` uses `& "<trama.exe>" cursor-hook`. Update skills replaces Trama's entries in either form instead of adding new ones. The Cursor form has not been tried on Cursor.
- `trama validate` refuses Windows device names (`con`, `prn`, `aux`, `nul`, `com1` to `com9`, `lpt1` to `lpt9`) as Feature, Machine and Actor IDs and as Area and fragment names on every platform, so a project opens on Windows too. Names that only contain one of them stay valid.
- Proposal hashes and comparisons read the Model and Requirement files with LF line endings: a CRLF checkout (`core.autocrlf`) no longer makes a Proposal stale, and its shown changes, touched files and scan scope match a Linux checkout.

## 0.0.1

- First public release, under the GNU AGPL v3 (`AGPL-3.0-only`); the `.vsix` now ships the license text. Earlier tags and releases are gone, and versions restart from 0.0.1.
- The automatic Run no longer carries a fixed list of Task identities from its launch: before each group it reads the authorized Tasks from `trama drift autopilot --json`, so an origin Task whose fix Tasks became Done during the Run is picked up, and nothing outside the authorization is started.
- When the Drift autopilot leaves `disabled`, the window that coordinates the project imports the jobs the other editor windows still run, before it judges the barrier: a Run, scan or Resolve Drifts started in another window during `disabled` is no longer unknown to the coordinator that already held the role.
- The Drift autopilot grants no new automatic step while a live editor window does not answer the project coordinator's jobs request in time: one answering window is no longer enough. The status shows that reason, and the coordinator keeps its role meanwhile.
- With the Drift autopilot `disabled`, a window no longer shares its jobs or send reservations with the other editor windows of the project: another window's Run, scan or Resolve Drifts no longer makes Resolve Drifts or the Run buttons unavailable here, and a send no longer waits behind another window's send. Sharing starts when the autopilot is enabled.
- The Scan button's count restarts when the System scan's instruction is delivered (written to the terminal, sent to the chat, left ready in the chat or copied to the clipboard), not when its check finishes: a scan that fails, is interrupted or has its check withdrawn no longer leaves the count up, and the editor no longer tracks scan launches in memory.
- An agent terminal that went idle or whose command ended is no longer followed: a later idle signal, command end or close of that terminal no longer releases the Tasks the resumed agent took or withdraws its announcements.
- An agent terminal's instruction stays one line: the job ID is no longer written into it. The commands that take `--job` (`announce check`, `proposal new --automatic --resolution`, `drift autopilot`, `agent-event failed`) read the terminal's job from `TRAMA_JOB` when `--job` is absent; a chat job still gets its ID in the text.
- A Drift whose question was skipped in one editor window stays out of automatic resolution in every window: the skip, the later answer and a developer scan are forwarded to the project coordinator.
- An automatic resolution whose approval is refused now fails only the Drifts the refusal names (or whose decision no longer applies); the other Drifts stay open in the Proposal for the developer.
- Rejecting or discarding an automatic resolution no longer marks its undecided Drifts as failed; they stay open, unmarked, for the developer's own decision.
- Add coordinated Drift autopilot modes (`disabled`, `enabled`, `yolo`) with cross-window scan/Run barriers, host-only approval, job-scoped authorization and implementation Runs.
- Resolve Drifts pressed in a window that does not coordinate the project now asks the coordinator, over the local channel, to resume automatic resolution; until a coordinator resumes, that window says why the automatic part waits.
- Autopilot leaves out of automatic resolution a Drift whose Model elements no longer exist, so it stays for the developer instead of failing in the resolution agent.
- Resolve Drifts no longer clears failed automatic cases: a Drift whose automatic fix failed or was excluded gets manual questions on a click, even with full delegation.
- A refused automatic start (mode, barrier or Drift changed at the last moment) releases its reservation and records no failure; its Drifts or Tasks stay eligible for the next cycle.
- Track critical Drifts and failed check outcomes; expose automatic resolution status and critical markers in the CLI and Board.
- Autopilot: a failed or interrupted scan no longer suspends the delegation; it counts as finished.
- Autopilot status reports the last failed or interrupted scan as information; it changes no phase.
- A finished check's outcome reaches the editor over the local channel instead of a marker file, so the System scan memory and the autopilot no longer race for it.
- Add `trama.submitWhileRunning` (`disabled` by default): while a Trama run is in progress, the Run buttons are disabled and launches are refused with "A run is in progress"; `enabled` allows Runs during a run.
- Make the Board's Done column collapsible; it starts collapsed each time the panel opens.
