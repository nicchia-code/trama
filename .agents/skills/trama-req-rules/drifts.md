# Requirements: Regole di business, Regole dei Drift

Usa quando implementi le regole dei Drift, della loro risoluzione e del pulsante Resolve Drifts.

## drift

- A Drift must reference at least one Model element or Requirement, and every reference must resolve when it is created. It may only be resolved once: resolving an already resolved Drift is refused.
- Un Drift nuovo deve avere le sezioni What happens, What should happen, Where in the code e Fix options, ognuna con testo; crearlo senza una di esse è rifiutato, nominando quella mancante. Fa eccezione solo il Drift senza correzione del codice possibile (vedi sotto): non ha la sezione Fix options e dev'essere creato con una Proposal allegata; senza Proposal la creazione è rifiutata, dicendo che un Drift senza Fix options richiede una Proposal allegata. Where in the code è obbligatoria per ogni Drift nuovo, anche senza Fix options e anche quando lo registra il developer; i Drift già scritti senza non sono toccati.
- Le Fix options di un Drift nuovo, quando ci sono, sono da due a cinque, ognuna con un titolo e un testo, entrambi non vuoti, con titoli diversi fra loro; altrimenti la creazione è rifiutata, nominando il problema. La prima opzione è quella che l'agente raccomanda.
- Ogni Fix option raggiunge ciò che dovrebbe succedere senza cambiare il Modello né alcun Requisito: rispetta tutti i Requisiti che si applicano agli elementi del Drift, non solo quelli che il Drift nomina. Un'opzione che chiede una deroga, un'eccezione o una modifica a un Requisito o al Modello non è una Fix option: quella strada va in una Proposal allegata. Quando nessuna correzione del codice rispetta insieme Modello e Requisiti, per esempio perché due Requisiti si contraddicono, l'agente crea il Drift senza Fix options e con una Proposal allegata che sistema il Modello o i Requisiti. Sono indicazioni per l'agente e le skill che archiviano Drift (`trama-scan`, `trama-implement`, `trama-import`): la creazione non può verificarle.
- Un Drift nuovo può avere un precedente, un Drift già risolto di cui è il seguito; un Drift con un precedente è ricorrente. Quando l'origine è il Task di correzione di un altro Drift, il precedente è quel Drift e Trama lo scrive da sola; un precedente dichiarato diverso è rifiutato, nominando quello che vale. Senza un'origine così, chi crea il Drift può dichiarare il precedente; dev'essere un Drift esistente risolto correggendo il codice o adeguando il Modello: un Drift aperto, dismesso o inesistente è rifiutato, dicendo perché. Il precedente non cambia più dopo la creazione; solo la riscrittura delle identità lo porta alla nuova identità dello stesso Drift.
- Prima di archiviare un Drift, l'agente legge i Drift risolti che riguardano gli stessi elementi, con la stessa regola dei blocchi (lo stesso elemento o uno dentro l'altro). Non riarchivia una differenza già chiusa senza cambiare nulla finché il Modello o il Requisito in quel punto dicono la stessa cosa; un Drift dismesso dal suo Task di correzione chiuso senza modifiche non conta come chiusura e non frena una differenza nuova sullo stesso punto. Se ritrova una differenza già risolta correggendo il codice o adeguando il Modello, archivia il Drift nominandola come precedente. Sono indicazioni per l'agente e le skill che archiviano Drift; nessun controllo della CLI confronta i testi.
- Prima di archiviare un Drift, l'agente rilegge il punto del codice che scriverà in Where in the code e archivia solo se il codice fa davvero ciò che dice What happens; se il codice fa già ciò che dice What should happen non c'è nessun Drift. Vale per ogni lavoro che archivia Drift: scansione, pre-flight, scansione di fine corsa, realizzazione di un Task e import, compresi i sotto-agenti che confrontano le Machine. È un'indicazione per l'agente e le skill: la creazione controlla solo che Where in the code ci sia.
- Chi registra il Drift assegna `critical` in tutte le modalità. Vale `true` solo se è urgente una posizione del developer su quel caso; gravità tecnica, complessità, modifica strutturale richiesta o lavoro mancante, da soli, non bastano. Non c'è un classificatore separato. I Drift precedenti senza il campo valgono non critici.
- La Proposal allegata a un nuovo Drift dev'essere una Draft o aperta e non già allegata a un altro Drift aperto; altrimenti la creazione del Drift è rifiutata, dicendo perché (approvata, rifiutata, scartata, o allegata al Drift `<id>`). Una Proposal è allegata a un Drift aperto quando un Drift aperto la nomina; un Drift risolto non trattiene più la sua Proposal.
- Tenere ciò che dovrebbe succedere su un Drift con una Proposal allegata, nello stesso passo, rifiuta la Proposal aperta con il feedback «Drift <id> resolved by fixing the code» oppure scarta la Draft, senza feedback; una Proposal già approvata, rifiutata o scartata resta com'è. Le Proposal che la richiedono restano bloccate, come per ogni rifiuto o scarto.
- Fixing the code of a Drift that has options requires the number of one of them, counted from 1 in the order they are written; it is refused, saying that an option must be chosen, when none is given or the number is not that of an option, and the Drift stays Open. The developer may add a note, free text kept with the choice. A Drift without options accepts no option, and its code is fixed without choosing; a note is accepted in both cases. Accepting the attached Proposal and dismissing take neither an option nor a note: given one, they are refused.
- Fixing the code creates a Task titled "Fix code to match the Model: <Drift title>" (or "…the Requirements: …" when the Drift points only to Requirements), pointing to the Drift's references, linked to the Drift, with these as its body, in this order: What happens and What should happen, then the chosen option with its title and text and the developer's note when given, then Where in the code when the Drift has it. The chosen option's number and the note are kept in the Drift. It is a Technical Task exactly when the Drift points only to Requirements.
- Quando il codice di un Drift viene corretto, ogni suo riferimento che non si risolve più è sostituito, nel Task di correzione, dal contenitore più vicino che si risolve ancora: lo Stato o la Machine che conteneva lo Stato o la Transition, il proprietario di un Evento, l'Area di una sezione di Requisito. Una Machine, una Feature, un Actor o un'Area spariti non hanno contenitore e sono lasciati fuori; i doppioni si uniscono. Titolo e tipo del Task (tecnico o no) si decidono dai riferimenti del Drift, non da quelli sostituiti. Se il Drift punta al Modello e dopo la sostituzione non resta alcun riferimento del Modello, correggere il codice è rifiutato e il Drift resta Open: il rifiuto dice che i suoi elementi del Modello non esistono più e che il Drift si può solo chiudere (scartandolo o accettando la Proposal allegata). La stessa regola vale per la decisione `fix-code` di una risoluzione.
- The agent writes What happens and What should happen for a programmer who reads the Drift at a glance, not as a code review: what the System does and what it should do, in terms of behaviour and the words of the domain ("the cart total ignores the coupon"), not how the code does it. These are guidelines for the agent and the skills; nothing refuses a Drift for its style or length.
- The two sides and the options name no variable, function, class, field or file, unless the difference cannot be understood without it; then they name only the one or two that matter, as inline code. Where the code was seen goes only in Where in the code: files, and the code element when it helps, with no line numbers (they go stale) and no long pieces of code.
- The texts are Markdown, written to be read quickly: short paragraphs, a bulleted list when there are several separate points, bold for the one or two terms that carry the difference, no headings inside a section and no tables, about 100 words per side. Each fix option is a different way to reach what should happen, not a step of one plan, and says in terms of behaviour what changes and what it costs; about 60 words each, no headings or tables inside an option. These are guidelines for the agent and the skills, like the rest of this style.
- Accepting the attached Proposal is refused when the Drift has none, and when the Proposal cannot be approved; the refusal names the reason: still being written, rejected, discarded, already approved, stale, invalid or waiting for others.
- Dalla riga di comando, chiudere un Drift senza modifiche è rifiutato quando ha una Proposal allegata, in qualunque stato; il rifiuto dice di accettare quella Proposal o di correggere il codice.
- Dal pannello, Dismiss Drift chiude un Drift aperto senza modifiche (`resolution: dismissed`) anche quando ha una Proposal allegata: nello stesso passo scarta la Proposal, in scrittura o aperta, senza feedback; una Proposal già approvata, rifiutata o scartata resta com'è. Le Proposal che la richiedono restano bloccate, come per ogni scarto. È rifiutato, senza cambiare nulla e dicendo perché, quando il Drift non è più aperto o sta in una Proposal di risoluzione in scrittura o aperta; l'host lo rifiuta anche mentre un agente risolve i Drift.
- Approvare una risoluzione risolve, nello stesso passo, ogni Drift della sua lista ancora aperto con la decisione registrata, con le regole della riga di comando: `fix-code` crea il Task di correzione con l'opzione e la nota registrate e muove l'origine come scritto sotto; `proposal` e `dismissed` chiudono il Drift con quella `resolution`, e `dismissed` vale anche quando una Proposal è allegata. Ogni Drift risolto così prende `resolvedBy`. La Proposal allegata a ciascuno è rifiutata con il feedback «Drift <id> resolved by Proposal <id>», o scartata senza feedback se è una Draft; una già approvata, rifiutata o scartata resta com'è. Un Drift della lista già risolto in altro modo è saltato senza errore, e l'approvazione dice quali.
- Il rifacimento della Proposal obsoleta di un Drift non esiste più: `trama drift replace-proposal` è tolto, e una Proposal allegata obsoleta resta com'è finché il Drift non è risolto.
- A Drift remembers the Task the agent was implementing when it filed it (its origin); a Drift filed by a Scan has none. The origin must be an existing Task.
- Fixing the code of a Drift with an origin that is not Done moves that Task to To do and clears its mark of being taken, then the origin waits for the fix Task as described for blocked Tasks. Accepting the attached Proposal or dismissing a Drift leaves its origin where it is. Once a Drift is resolved it no longer blocks anything.
- Un Drift nuovo può nominare i Task che lascia liberi, ciascuno con un motivo non vuoto: ognuno dev'essere un Task che il Drift bloccherebbe (l'origine o un Task non Done che riguarda la stessa cosa), altrimenti la creazione è rifiutata nominandolo. Un Task lasciato libero non è bloccato da quel Drift; tutti gli altri, compresi quelli nati dopo, seguono la regola dei blocchi. L'elenco non cambia più dopo la creazione. Con `trama.experimentalDriftBlocker` acceso l'agente che registra il Drift giudica ogni Task che bloccherebbe, origine compresa, e lascia libero chi la differenza non tocca; spento, non nomina nessun Task.
- Con il blocco acceso, un Drift che alla creazione non blocca nessun Task, non è critico né ricorrente e non è ammissibile per la delega corrente entra, alla fine del lavoro, nella risoluzione `nonBlocking` del lavoro (`rules#drift-resolution`). Sono indicazioni per le skill: la CLI non le verifica.
- Chiudere senza modifiche il Task di correzione di un Drift in Code to be fixed (vedi `rules#task`) porta nello stesso passo il Drift a `dismissed`; è l'unico modo in cui un Drift già risolto cambia risoluzione, e `trama drift move` su un Drift risolto resta rifiutato. Il Drift dismesso così non torna a `fix-code` se il Task lascia Done, non può essere il precedente di un Drift ricorrente, come ogni Drift dismesso, e non frena la riarchiviazione della stessa differenza (vedi sopra).
